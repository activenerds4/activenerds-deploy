# Secrets Management & Zero-Trust IaC Guide

**A static secret in your infrastructure-as-code is a static credential in production — and static credentials are the most common breach vector.** Infrastructure-as-code (Terraform, Pulumi, OpenTofu) often needs secrets: database passwords, API keys, cloud credentials. Storing those secrets in the IaC state, in CI variables, or in plaintext files recreates the static credential problem at the infrastructure layer. This guide covers the zero-trust alternative: dynamic secrets with short-lived leases, ephemeral environments with auto-expiring credentials, and automated rotation that removes static secrets from IaC entirely.

## 1. The IaC Secrets Problem

Infrastructure-as-code needs secrets to provision resources — a database password to create the RDS instance, an API key to configure the SaaS integration. Where those secrets live determines the security posture.

### Where Secrets Hide in IaC

| Location | Risk | Common? |
|---|---|---|
| Plaintext in `.tf` files | Committed to Git, visible to all | Should never happen |
| Terraform state file | Often in remote state, sometimes in Git | Very common, high risk |
| CI/CD variables | Static, long-lived, over-broad | Common |
| Environment variables at runtime | Better, but still static | Common |
| A secrets manager (Vault, AWS SM) | Dynamic, short-lived | The goal |

<Callout variant="warning" title="Terraform state is a secret store (a bad one)">
  Terraform stores the resources it creates in its state file — including secrets. A database password created by Terraform ends up in the state file. If that state is in Git (a common mistake), the secret is in Git history forever. Even in remote state, the state file is a plaintext secret store with none of a real secret manager's controls (rotation, access logging, lease expiry). Never store state in Git, and treat state files as sensitive — they contain your secrets.
</Callout>

### The Static Secret Lifecycle in IaC

```text
1. Engineer creates a secret (DB password, API key)
2. Secret stored in IaC state / CI variable
3. IaC uses the secret to provision resources
4. Secret lives indefinitely (until manually rotated)
5. Engineer leaves → secret still works
6. Secret compromised → still works until rotation
7. Rotation: manual, risky, often skipped
```

This is the same static credential problem from keyless CI/CD, applied to infrastructure. The solution is the same: make secrets dynamic and short-lived.

## 2. Dynamic Secrets & Leases

Dynamic secrets are generated on-demand, with a limited lifetime (a lease). Instead of one long-lived secret, every consumer gets a unique, short-lived secret that expires automatically.

### The Dynamic Secret Model

```text
Static secret:
  One secret → used by everyone → lives forever → manual rotation

Dynamic secret:
  Each consumer requests a secret → gets a unique one → expires after lease
  No shared secret, no manual rotation, per-consumer audit trail
```

### Why Dynamic Secrets Are More Secure

| Property | Static secret | Dynamic secret |
|---|---|---|
| Lifetime | Indefinite | Minutes to hours (lease) |
| Sharing | One secret, many consumers | Unique per consumer |
| Rotation | Manual | Automatic (lease expiry) |
| Revocation | Rotate (affects everyone) | Let lease expire (affects one) |
| Audit | "Secret was used" | "This consumer used this specific secret" |
| Compromise window | Until rotation (months) | Lease lifetime (minutes) |

<Callout variant="tip" title="Lease expiry is automatic rotation">
  A dynamic secret with a 1-hour lease is rotated every hour — automatically, with no process to forget. The "rotation problem" of static secrets (manual, risky, often skipped) disappears entirely. The secret simply ceases to exist after its lease. This is why dynamic secrets are fundamentally more secure: rotation isn't a process you have to run; it's a property of the secret.
</Callout>

### The Lease Lifecycle

```text
1. Consumer requests a secret (IaC run, application startup)
2. Secrets manager generates a unique secret
3. Secret provisioned in the target (DB user created, API key issued)
4. Lease granted (TTL: e.g., 1 hour)
5. Consumer uses the secret
6. Lease expires → secret automatically revoked (DB user dropped, key deactivated)
7. (If consumer still needs it, it requests a new one)
```

The secret exists only for the duration it's needed. There's no long-lived secret to compromise.

## 3. HashiCorp Vault for IaC

HashiCorp Vault is the most capable dynamic secrets engine. It generates secrets for many backends (databases, cloud providers, PKI) on-demand, with leases and automatic revocation.

### Vault Dynamic Secrets for Databases

Vault's database secrets engine creates unique database credentials per request:

```text
1. Vault is configured with a privileged DB connection (the "root" cred)
2. IaC/application requests a DB credential from Vault
3. Vault creates a unique DB user + password (e.g., "v-token-abc123")
4. Vault grants that user the configured permissions
5. Vault returns the credential with a lease (e.g., 1 hour)
6. On lease expiry, Vault drops the DB user (secret revoked)
```

The IaC never sees a long-lived DB password. Each run gets a unique credential that expires.

### Terraform + Vault Integration

Terraform has a Vault provider that fetches secrets at plan/apply time:

```hcl
# Fetch a dynamic DB credential from Vault
data "vault_generic_secret" "db" {
  path = "database/creds/my-role"
}

# Use the dynamic credential to provision a resource
resource "aws_db_instance" "app" {
  username = data.vault_generic_secret.db.data["username"]
  password = data.vault_generic_secret.db.data["password"]
  # ...
}
```

The credential is fetched at apply time, used to provision, and expires after the lease. It's not stored in state (it's a data source, not a resource), so the state file doesn't contain the secret.

<Callout variant="note" title="Data sources don't persist secrets in state">
  A Terraform `data` source fetches information at plan/apply time but doesn't store it in state the way a `resource` does. Using `data "vault_generic_secret"` to fetch a dynamic secret means the secret is used during the run but not persisted in the state file. This is the key to keeping secrets out of state: fetch them as data sources, don't define them as resources.
</Callout>

### Vault for Cloud Credentials

Vault can also generate short-lived cloud credentials (AWS STS, GCP service account tokens) via its cloud secrets engines. This extends the dynamic secret model to cloud access:

```text
1. IaC requests AWS credentials from Vault
2. Vault calls STS to generate short-lived AWS creds (1 hour)
3. IaC uses the creds to provision AWS resources
4. Creds expire after 1 hour (automatic)
```

No long-lived AWS keys in IaC — the same keyless pattern, brokered through Vault.

## 4. AWS Secrets Manager for IaC

For AWS-native stacks, AWS Secrets Manager provides secret storage with automatic rotation, integrated with IAM.

### Secrets Manager vs Vault

| Dimension | AWS Secrets Manager | HashiCorp Vault |
|---|---|---|
| Secrets type | Stored secrets + rotation | Dynamic generation + stored |
| Rotation | Built-in for supported services (RDS, etc.) | Custom rotation for any backend |
| Multi-cloud | AWS only | Multi-cloud |
| Dynamic generation | Limited (mostly stored + rotated) | Full dynamic generation |
| Operation | Managed service | Self-hosted (or HCP) |

<Callout variant="tip" title="Secrets Manager for AWS-native, Vault for multi-cloud">
  If you're fully on AWS, Secrets Manager is simpler (managed, no infrastructure). If you're multi-cloud or need true dynamic generation (not just rotation of stored secrets), Vault is more capable. Many teams use both: Secrets Manager for AWS-native secrets (RDS rotation), Vault for dynamic generation across clouds.
</Callout>

### Terraform + Secrets Manager

```hcl
# Fetch a secret from AWS Secrets Manager
data "aws_secretsmanager_secret_version" "db" {
  secret_id = "prod/db/credentials"
}

# Use the secret (parsed from JSON)
resource "aws_db_instance" "app" {
  username = jsondecode(data.aws_secretsmanager_secret_version.db.secret_string)["username"]
  password = jsondecode(data.aws_secretsmanager_secret_version.db.secret_string)["password"]
  # ...
}
```

Secrets Manager handles rotation for supported services (RDS, Redshift, DocumentDB) via Lambda rotation functions. The IaC fetches the current value; rotation happens out-of-band.

### The Rotation Function

For services without built-in rotation, you write a Lambda rotation function:

```text
1. Secrets Manager triggers rotation (on schedule)
2. Lambda generates a new secret
3. Lambda updates the target (DB, service) with the new secret
4. Lambda updates Secrets Manager with the new value
5. Lambda verifies the new secret works
6. Old secret retired (kept briefly for fallback, then removed)
```

This automates rotation for any secret, on any schedule — daily, weekly, or per the compliance requirement.

## 5. Ephemeral Environments

Ephemeral environments — spun up per PR, torn down after merge — are where dynamic secrets shine. Each environment gets its own credentials, created on-demand, destroyed with the environment.

### The Ephemeral Environment Model

```text
PR opened
  → IaC provisions an ephemeral environment
    → Dynamic secrets generated (DB, cache, API keys)
      → Environment runs with unique credentials
        → PR merged or closed
          → Environment destroyed
            → Secrets auto-revoked (leases expire or are revoked)
```

No secrets persist after the environment is destroyed. Each PR gets a fresh, isolated environment with credentials that exist only for its lifetime.

### Why This Is Zero-Trust

| Property | Static environments | Ephemeral + dynamic secrets |
|---|---|---|
| Credential lifetime | Indefinite | Environment lifetime (hours) |
| Credential sharing | Shared across envs | Unique per environment |
| Stale credentials | Accumulate over time | None — destroyed with env |
| Cross-env leakage | Possible (shared creds) | Impossible (unique creds) |
| Blast radius | Compromised env exposes shared creds | Compromised env exposes only its own (expired) creds |

<Callout variant="warning" title="Static environments accumulate secrets">
  A long-lived staging environment accumulates secrets over time — old API keys, rotated DB passwords that weren't fully retired, test credentials left by departed engineers. Each is a potential breach path. Ephemeral environments eliminate this accumulation: the environment and all its secrets are destroyed on every PR cycle. There's nothing to accumulate.
</Callout>

### The IaC Pattern

```hcl
# Ephemeral environment per PR (unique names, unique secrets)
resource "random_password" "db" {
  length = 32
}

resource "aws_db_instance" "ephemeral" {
  name             = "pr-${var.pr_number}"
  username         = "pr_${var.pr_number}"
  password         = random_password.db.result
  # ... (destroyed when the PR environment is torn down)
}
```

The `random_password` resource generates a unique secret per environment. When the environment is destroyed (PR closed), the password resource is destroyed too — it doesn't persist in state or anywhere else.

## 6. Automated Rotation Architecture

For secrets that must persist (production databases, long-lived service integrations), automated rotation is the zero-trust control. The secret exists, but it rotates on a schedule without human intervention.

### The Rotation Architecture

```text
[Rotation trigger: schedule or event]
       ↓
[Rotation service generates new secret]
       ↓
[Target updated with new secret (DB, service, IaC)]
       ↓
[Secret store updated with new value]
       ↓
[New secret verified (test connection)]
       ↓
[Old secret retired (after grace period)]
       ↓
[Consumers pick up new secret (via secret store)]
```

### Rotation Patterns

| Pattern | How it works | Use case |
|---|---|---|
| Dual-key rotation | Two valid keys; rotate one at a time | Zero-downtime rotation |
| Blue-green rotation | New secret deployed, old retired after verification | Safe rotation |
| Immediate rotation | Old secret invalidated immediately | High-security, brief downtime |
| Lease-based rotation | Secret expires; new one generated | Dynamic secrets (no rotation needed) |

<Callout variant="tip" title="Dual-key rotation for zero downtime">
  For secrets that consumers use continuously (a DB password an app connects with), dual-key rotation avoids downtime: keep both old and new secrets valid during rotation. Deploy the new secret to consumers; once all consumers use the new one, retire the old. This is how you rotate a production DB password without dropping connections.
</Callout>

### Consumer Update Mechanism

Rotation is only useful if consumers pick up the new secret. The mechanisms:

- **Pull model** — consumers poll the secret store (Vault, Secrets Manager) and use the current value. Rotation is transparent; consumers get the new value on next poll.
- **Push model** — the rotation service notifies consumers (webhook, config reload) to re-fetch. Faster, but requires notification infrastructure.
- **Restart model** — consumers restart to pick up the new secret. Simple, but causes brief downtime.

For most cases, the pull model (consumers poll the secret store with a short interval) is simplest and sufficient. The consumer always uses the current secret value; rotation is automatic and transparent.
