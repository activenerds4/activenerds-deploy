**Design for Performance**

→ Verify exact figures (over-commit ratios, ESA hardware requirements, NIC speeds, DPU support/offload scope, NSX Edge sizing) against the current VCF 9.0, vSAN, vSphere and NSX documentation and the exam guide. Values below are typical design guidance, not authoritative limits.

---

## 0. Performance Fundamentals

| Concept | Meaning |
|---|---|
| **Performance (P in AMPRS)** | Meeting throughput, latency, IOPS, response-time and scalability targets |
| **Performance SLA** | Measurable targets, e.g., "DB write latency &lt; 2 ms", "99th percentile response &lt; 200 ms", "40 Gbps north-south" |
| **Bottleneck principle** | Overall performance is limited by the **slowest layer**: CPU, memory, storage, network, or the application |
| **Contention vs capacity** | Many SLA failures are **contention** (noisy neighbours, over-commit) rather than raw lack of capacity |
| **Baseline and measure** | Define metrics up front (latency, IOPS, throughput, CPU ready, memory ballooning/swapping) and validate with testing |
| **Trade-offs** | Higher performance usually costs more (hardware, headroom) and may reduce consolidation ratio, flexibility, or capacity efficiency |

**Design flow:** requirement → SLA metrics → identify workload profile (CPU/memory/IO/network bound) → size and isolate each layer with headroom → validate with load testing → monitor with **VCF Operations**.

## 1. Compute (CPU)

| Decision | Options | Guidance / trade-off |
|---|---|---|
| **vCPU:pCPU ratio** | Low for critical/latency-sensitive (near 1:1), higher for general/dev | Higher ratio = better consolidation, higher **CPU ready** risk |
| **Right-sizing vCPUs** | Match vCPU to actual need | Over-allocated vCPUs hurt scheduling (more cores to schedule) and can **reduce** performance |
| **CPU selection** | Higher clock vs higher core count | Clock for single-thread/latency-bound apps; cores for throughput/parallel |
| **NUMA** | Keep VMs within a NUMA node where possible; align vCPU/memory to NUMA topology | Crossing NUMA nodes adds memory latency; relevant to large VMs (wide VMs) |
| **Reservations / shares / limits** | CPU reservations for critical VMs; shares for relative priority | Reservations guarantee but reduce flexibility and affect HA admission control |
| **DRS** | Fully automated; set migration threshold; VM-host rules | Balances load; affinity rules constrain it; consider predictive DRS |
| **EVC / mixed CPUs** | Homogeneous hosts preferred | EVC masks features to the lowest baseline: compatibility vs performance |
| **Dedicated clusters** | Separate clusters for latency-sensitive, GPU, or noisy workloads | Isolation from contention; lower consolidation |
| **Hardware features** | Latest CPU generation, hyper-threading policy, power management (High Performance profile) | BIOS power profile can materially affect latency |
| **GPU / accelerators** | GPU-certified hosts, vGPU or passthrough, separate cluster | AI/VDI SLAs; profile sizing and licensing |

**Exam signals**
- "High CPU ready time on a critical cluster" → reduce over-commit, right-size vCPUs, add hosts, or isolate workloads in a dedicated cluster.
- "Large in-memory database VM" → NUMA-aware sizing, high clock CPUs, dedicated host/cluster.

## 2. Memory

| Decision | Guidance / trade-off |
|---|---|
| **Capacity planning** | Size to **active** memory plus headroom, not just allocated; keep host memory out of ballooning/swapping |
| **Over-commit** | Conservative or none for critical workloads; moderate for general |
| **Reservations** | Full reservation for latency-critical VMs avoids ballooning/swap; affects HA admission control and consolidation |
| **Memory tiering** | NVMe-based memory tiering (where supported in the vSphere version) extends capacity cost-effectively; **trade-off**: tier 2 slower than DRAM, so use for suitable workloads |
| **NUMA/memory locality** | Keep memory local to vCPU; avoid NUMA imbalance |
| **Large pages** | Benefit memory-intensive apps |
| **Ballooning/swap indicators** | Treat as signs of contention and fix capacity or reservations |
| **Failure headroom** | N+1/N+2 memory reserve, since HA restart needs free memory |

**Exam signals**
- "Memory-intensive apps with strict latency" → reservations, no over-commit, NUMA alignment.
- "Reduce DRAM cost for large, less latency-sensitive memory footprints" → **memory tiering** (verify version support and workload suitability).

## 3. Storage (vSAN ESA, NVMe, Storage Policies)

### 3.1 vSAN ESA vs OSA

| | **vSAN ESA** | **vSAN OSA** |
|---|---|---|
| **Hardware** | NVMe-based, ESA-certified ReadyNodes | Hybrid or all-flash with disk groups (cache + capacity) |
| **Architecture** | Single storage pool; no cache/capacity tier split; optimised log-structured data path | Disk groups with cache tier |
| **Performance** | Higher IOPS/lower latency; **RAID-5/6 erasure coding with minimal performance penalty** | Erasure coding has noticeable write penalty; mirroring (RAID-1) preferred for performance |
| **Efficiency** | Better space efficiency, always-on compression | Dedupe/compression optional, with overhead |
| **Network need** | Higher bandwidth (25/100 GbE recommended) | 10/25 GbE common |
| **Choose when** | New builds, strict performance SLAs, modern NVMe hardware | Existing hardware, hybrid, non-NVMe |

### 3.2 Storage Design Decisions

| Decision | Guidance |
|---|---|
| **Device type** | NVMe (high endurance/performance class) for demanding SLAs; match endurance class to write intensity |
| **Device count per host** | More devices = more parallelism and throughput |
| **Controller/HBA** | Certified, adequate queue depth, firmware as per compatibility guide |
| **Network for storage** | Dedicated/protected vSAN traffic, **25/100 GbE**, MTU 9000, redundant uplinks, NIOC shares; ESA can saturate 10 GbE |
| **Hosts per cluster** | More hosts spread I/O and rebuild load |
| **Slack space** | ~25-30% free to avoid performance degradation during rebuild/rebalance |
| **Rebuild / resync impact** | Adaptive resync; plan headroom so rebuilds don't breach SLA |
| **Data services** | Compression, dedupe, encryption add CPU/IO overhead: enable only when required (ESA reduces penalty) |
| **Workload isolation** | Separate cluster or policy for noisy/latency-critical workloads; IOPS limits for noisy neighbours |
| **Supplemental storage** | External arrays (FC/NVMe-oF where supported) for specific high-performance or capacity needs |
| **Remote datastore / disaggregation** | Scale storage independently; note extra network dependency |

### 3.3 Storage Policies (SPBM) and Performance

| Policy setting | Performance effect |
|---|---|
| **FTT (failures to tolerate)** | Higher FTT = more writes/replicas; more capacity and overhead |
| **RAID-1 (mirroring)** | Best write performance, 2×/3× capacity |
| **RAID-5/6 (erasure coding)** | Capacity-efficient; **ESA: minimal penalty**, OSA: write penalty |
| **IOPS limit** | Caps noisy neighbours; protects other workloads |
| **Stripe width** | More stripes can increase parallelism (use cautiously; ESA manages this adaptively) |
| **Object space reservation** | Thick vs thin: guarantees capacity, reduces flexibility |
| **Storage tier / site disaster tolerance** | Stretched cluster adds inter-site write latency (writes acknowledged at both sites) |
| **Encryption** | Small overhead; plan CPU/AES-NI |

**Key takeaways**
- **ESA + NVMe + high-speed network** is the default answer for **strict performance SLAs** on new builds.
- **Use different storage policies per workload class** (critical DB vs general VM) rather than one policy for all.
- A **stretched cluster adds latency to writes**; if latency SLA is tight, evaluate local cluster plus DR/replication.
- **Slack space and rebuild headroom** are performance requirements, not just capacity ones.
- Storage performance problems are frequently **network** problems (uplink speed, MTU mismatch, oversubscription).

**Exam signals**
- "Low latency database with RAID-5 space efficiency" → **ESA** (erasure coding without large penalty).
- "Existing hybrid hardware with strict latency SLA" → upgrade to **all-flash/ESA** or isolate critical workloads on all-flash/RAID-1.
- "One tenant's batch jobs impact others' storage latency" → **IOPS limits** via storage policy, separate cluster.

## 4. Networking (NSX, TEPs, DPUs/SmartNICs, Bandwidth)

### 4.1 Physical and Host Networking

| Decision | Guidance |
|---|---|
| **NIC speed** | 25 GbE minimum for modern designs; **100 GbE** for ESA, dense hosts, Edge nodes, or high-throughput workloads |
| **NIC count** | ≥2 for redundancy; 4 if separating storage/overlay traffic |
| **Fabric** | Spine-leaf, low oversubscription (lower ratios for storage/high-throughput), ECMP |
| **MTU** | 9000 for vSAN/vMotion; ≥1600 (9000 common) for overlay, consistent end to end; larger MTU reduces per-packet overhead |
| **Traffic isolation / QoS** | **NIOC shares/reservations/limits** per traffic type (management, vSAN, vMotion, VM, NSX) |
| **Teaming policy** | Load-based teaming or LACP (if supported) to spread load |
| **Offloads** | TSO, LRO, RSS, checksum offload, **Geneve offload** on NICs; ensure drivers/firmware support |

### 4.2 NSX TEPs and Overlay Performance

| Decision | Guidance / trade-off |
|---|---|
| **TEP count** | Multiple TEPs per host (one per uplink) spread overlay traffic across uplinks |
| **TEP MTU** | ≥1600; **9000 recommended** for throughput; mismatch causes fragmentation/drops |
| **Overlay NIC offload** | Choose NICs that support **Geneve (overlay) offload** to avoid CPU overhead |
| **Enhanced Datapath / DPDK-style modes** | For NFV/telco-style high packet-rate workloads (verify supported features and VCF 9.0 applicability) |
| **Underlay** | Low-latency L3 fabric; ECMP for east-west |
| **VLAN vs overlay** | VLAN-backed segments avoid encapsulation overhead for specific performance-critical traffic; overlay gives agility (trade-off) |
| **Distributed routing** | Prefer distributed (DR) components: east-west traffic routed on hosts, not through Edge |

### 4.3 NSX Edge Performance

| Decision | Guidance |
|---|---|
| **Form factor** | **Bare-metal Edge** for highest throughput/packet rate; **VM Edge** (S/M/L/XL) for flexibility |
| **Sizing** | By throughput, connection counts, number of stateful services (NAT, LB, VPN, firewall) |
| **T0 mode** | **Active/Active + ECMP** for throughput; **Active/Standby** for stateful services (limits throughput to one node) |
| **Edge cluster** | Dedicated Edge cluster to avoid contention with workloads; scale out by adding Edge nodes/clusters |
| **Stateful service placement** | Spread across T1s/Edge clusters to avoid single Edge bottleneck |
| **Uplinks** | High-speed NICs (25/100 GbE), dual ToR, BGP with ECMP |

### 4.4 DPUs / SmartNICs

| Aspect | Guidance |
|---|---|
| **What they are** | NICs with onboard processors (DPUs) that **offload** networking/security services from host CPU (vSphere Distributed Services Engine; NSX offload) |
| **Benefits** | Frees host CPU cycles, higher throughput, lower latency/jitter, **isolation of infrastructure services** from workload CPU (security boundary) |
| **Best for** | High east-west traffic with distributed firewall/overlay processing, high-density hosts, strict network SLAs, security-sensitive environments |
| **Trade-offs** | **Higher hardware cost**, hardware/firmware/driver compatibility constraints, supported feature/offload scope and version limits, extra lifecycle considerations (DPU firmware/ESXi on DPU) |
| **Design checks** | Verify HCL support for DPU model, VCF 9.0 / vSphere / NSX version support, supported cluster/domain types, operational skills |

**Exam signals**
- "Distributed firewall and overlay processing consuming too much host CPU" → **DPU/SmartNIC offload** (if hardware/support allows), or add hosts/CPU.
- "Need security isolation of network services from workload" → DPU-based offload.

### 4.5 Bandwidth Allocation

| Traffic type | Design notes |
|---|---|
| **vSAN** | Highest priority for storage SLAs; dedicated NIC pair or guaranteed shares |
| **vMotion** | Burst-heavy; limit or use shares to avoid impacting VM/vSAN traffic |
| **VM / overlay (NSX)** | Production traffic; protect with shares/reservations |
| **Management** | Low bandwidth; ensure reservation for availability |
| **Backup/replication** | Schedule/limit to avoid peak impact |
| **NIOC** | Define **shares** (relative priority under contention), **reservations** (guaranteed minimum), **limits** (cap); shares only matter during contention |

**Key takeaways**
- Use **converged 25/100 GbE with NIOC** to guarantee bandwidth, or **dedicate NICs** to storage when strict isolation is needed.
- Protect **vSAN** and **latency-sensitive production traffic** with shares/reservations.
- Prefer **distributed routing** and **L3 ECMP fabric** for east-west scale; use **bare-metal Edge + A/A + ECMP** for north-south throughput.

## 5. Isolation and Noisy-Neighbour Strategy

| Technique | Use |
|---|---|
| **Dedicated cluster/domain** | Strict SLA workloads separated from general |
| **Resource reservations/shares** | Guarantee or prioritise CPU/memory |
| **Storage IOPS limits** | Cap noisy VMs |
| **NIOC** | Network bandwidth control |
| **Dedicated Edge cluster** | Isolate north-south processing |
| **DRS rules** | Separate heavy VMs; keep latency-sensitive near their dependencies |
| **Capacity headroom** | Avoid saturation |

## 6. Scenario Cheat Sheet

| Scenario | Design decision |
|---|---|
| Latency-sensitive OLTP database, strict SLA | Dedicated cluster, low vCPU ratio, memory reservations, NUMA-aligned VMs, **vSAN ESA on NVMe**, 25/100 GbE, RAID-1 or ESA RAID-5/6 per policy |
| Space-efficient storage without major write penalty | **ESA** with RAID-5/6 |
| Noisy neighbour hurting others | Storage **IOPS limits**, separate cluster, NIOC, DRS rules |
| High north-south throughput (e.g., 40+ Gbps) | **Bare-metal Edge**, T0 **Active/Active ECMP**, 100 GbE NICs, dedicated Edge cluster |
| Stateful NAT/VPN heavy at edge | T0 **Active/Standby** or distribute services across multiple T1/Edge; size Edge (L/XL or bare metal) |
| Host CPU consumed by network/security processing | **DPU/SmartNIC offload** (if supported), NIC offloads, or additional host capacity |
| Backup window degrades production | Schedule/limit backup traffic, NIOC limits/shares, separate backup network |
| vSAN latency spikes during rebuild | Increase slack space, adequate network bandwidth, adaptive resync, more hosts |
| Tight write latency across two sites | Stretched cluster adds inter-site latency: assess local cluster + replication/DR instead |
| Overlay throughput below expectation | Check **MTU end to end**, TEP/uplink distribution, Geneve offload support on NICs |
| AI/GPU workload SLA | GPU-certified hosts in dedicated cluster, high-speed networking, vGPU profile sizing |
| Mixed CPU generations reduce performance | Separate clusters per generation; avoid EVC downgrade for critical workloads |
| Need to prove SLA compliance | Baseline + load test; monitor with **VCF Operations** (latency, CPU ready, IOPS, throughput) |

## 7. Performance Trade-offs (AMPRS Lens)

| Choice | Improves | Costs |
|---|---|---|
| Low over-commit / reservations | P | Lower consolidation (cost), HA admission impact |
| vSAN ESA + NVMe + 100 GbE | P, efficiency | Hardware cost, certified hardware needed |
| RAID-1 vs RAID-5/6 (OSA) | P (RAID-1) | Capacity |
| Dedicated clusters/Edge | P, S (isolation) | Cost, management overhead (M) |
| Bare-metal Edge | P | Cost, flexibility |
| DPU offload | P, S | Hardware cost, compatibility and lifecycle complexity |
| Stretched cluster | A, R | Write latency (P), bandwidth demands |
| Encryption/dedupe/compression | S / efficiency | CPU/IO overhead |

---

## 8. Exam Traps

- **ESA ≠ OSA**: ESA needs NVMe ReadyNodes and gives RAID-5/6 without major penalty; don't assume OSA behaviour.
- **More vCPUs ≠ more performance**; over-sized VMs can slow down.
- **Active/Standby T0** limits throughput to one Edge node; use **A/A + ECMP** for throughput.
- **Shares only apply under contention**; use **reservations** for guaranteed minimums.
- **MTU mismatch** is a leading hidden cause of poor overlay/vSAN performance.
- **Stretched cluster** = availability benefit but **write-latency cost**.
- **DPUs** offload and isolate but add **cost and compatibility constraints**.
- Performance needs **headroom**: running at the limit causes SLA breaches, especially during failures/rebuilds.

---

## 9. Quick Recall

- **Compute**: right-size vCPUs, low over-commit for critical, NUMA alignment, dedicated clusters, high-performance power profile.
- **Memory**: size to active memory, reservations for critical, memory tiering for cost-efficient capacity (verify support).
- **Storage**: **ESA + NVMe + 25/100 GbE + MTU 9000**; per-workload storage policies; IOPS limits; slack ~25-30%.
- **Network**: multi-TEP, MTU ≥1600 (9000 common), NIC offloads, **NIOC shares/reservations**, distributed routing.
- **Edge**: bare metal + A/A ECMP for throughput; A/S for stateful; dedicated Edge cluster.
- **DPU/SmartNIC**: offload and isolate host services; higher cost and compatibility checks.
- **Always**: define SLA metrics, isolate, keep headroom, validate with testing, monitor with VCF Operations.
