**Design for Manageability**

→ Verify exact VCF 9.0 lifecycle tooling, upgrade sequencing, scale maximums and capacity features against the current VCF 9.0 documentation and exam guide. In VCF 9.0 lifecycle responsibilities are split between **SDDC Manager** (domain/infrastructure lifecycle) and **fleet management in VCF Operations** (management-component lifecycle across the fleet), which replaces the older Aria Suite Lifecycle role. Confirm the current split before the exam.

---

## 0. Manageability Fundamentals

| Concept | Meaning |
|---|---|
| **Manageability (M in AMPRS)** | Ease and consistency of deploying, operating, monitoring, patching, scaling and troubleshooting |
| **Design goals** | Standardise, automate, centralise, reduce variation, minimise operational risk and effort |
| **Operational drivers** | Skills available, change windows, compliance cadence, number of sites/domains |
| **Trade-off** | More standardisation and automation = easier operations but less flexibility; more domains/instances = isolation but more to manage |

**Design principle:** *Consistency is the foundation of manageability.* Homogeneous hardware, validated BOM, naming/tagging standards, and VCF-managed lifecycle reduce risk and effort.

## 1. Lifecycle Management

### 1.1 Who Manages What

| Tool | Scope | Typical function |
|---|---|---|
| **VCF Installer** | Day-0 | Bring-up of the first instance and management domain |
| **SDDC Manager** | Per **VCF instance** | Create/expand/remove workload domains, add/remove clusters and hosts, patch/upgrade ESXi, vCenter, NSX, and vSAN per the validated BOM, certificate and password management, backup configuration, inventory |
| **Fleet management (VCF Operations)** | **Fleet** (multiple instances) | Lifecycle of management components (e.g., VCF Operations, VCF Automation, logs/networks components), fleet-wide visibility and consistency |
| **vSphere Lifecycle Manager (vLCM)** | Per cluster | Image-based host lifecycle (ESXi, firmware, drivers) driven by cluster images; SDDC Manager orchestrates |
| **VCF Operations** | Fleet | Monitoring, compliance, configuration drift visibility |

### 1.2 Lifecycle Design Decisions

| Decision | Options | Guidance / trade-off |
|---|---|---|
| **Upgrade approach** | VCF-orchestrated (SDDC Manager/fleet management) vs manual component updates | VCF-orchestrated keeps components on a **validated BOM** (supported combinations); manual updates risk unsupported combinations |
| **Update sequencing** | Management domain first, then workload domains; management components before workload infrastructure (per VCF guidance) | Follow documented order; **management domain version must be ≥ dependent domains** as documented |
| **Image management** | **vLCM images** (desired state) with vendor firmware/driver add-ons (HSM) | Consistent image per cluster; reduces drift |
| **Host update method** | Rolling updates using vMotion/maintenance mode; parallel cluster updates where supported | Capacity headroom (N+1) needed so hosts can be drained; parallelism speeds up but raises risk |
| **Live patching / minimal downtime options** | Use where supported to reduce reboots | Verify applicability/version support |
| **Maintenance windows** | Per domain/cluster staggering; change-approval process | Avoid patching all domains simultaneously; protect availability |
| **Pre-checks and validation** | Run SDDC Manager/VCF pre-checks before upgrade; verify backups | Reduces failed upgrades |
| **Backup before change** | Backup SDDC Manager, vCenter, NSX, management components | Recoverability (**R**) for failed change |
| **Rollback strategy** | Snapshots/backups for management VMs, image rollback for hosts | Define before executing change |
| **Certificates and credentials** | Centralised certificate management (CA integration), password rotation | Security and operational hygiene |
| **Domain/instance cadence** | Align versions across domains/instances; avoid long-term version drift | Fewer supportability and interoperability issues |
| **Brownfield vs greenfield** | Convert/import existing vs new build | Brownfield: validate prerequisites and supported versions; greenfield simpler |
| **Skills/operations model** | In-house vs managed service | Skills gap = risk; transfer via managed service or training |

### 1.3 Key Takeaways (Lifecycle)

- Use **SDDC Manager** for **infrastructure lifecycle** (hosts, vCenter, NSX, vSAN, domains); use **fleet management** for **management-component lifecycle across instances**.
- Lifecycle operations are **BOM-driven**: VCF validates the supported combination of component versions.
- **Do not patch VCF-managed components outside VCF tooling** unless documented; it breaks inventory consistency and supportability.
- Adequate **capacity headroom is a lifecycle prerequisite** (hosts must be evacuated to patch).
- **Separate workload domains = independent upgrade cadence**, but a **shared NSX** or shared components can couple upgrades.
- Always **back up before upgrade** and run **pre-checks**.

## 2. Scalability

### 2.1 Scaling Dimensions

| Dimension | How VCF scales | Design consideration |
|---|---|---|
| **Scale up** | Larger hosts (more CPU/memory/storage per host) | Fewer hosts, bigger failure domain per host; licensing impact |
| **Scale out (hosts)** | Add hosts to a cluster | Cluster maximums (vSphere/vSAN), network/rack capacity, vSAN rebalance |
| **Scale out (clusters)** | Add clusters to a domain | Domain/vCenter maximums; separate by workload class |
| **Scale out (domains)** | Add workload domains | Each domain adds vCenter (+ optional NSX); management domain load |
| **Scale out (instances/fleet)** | Add VCF instances | Fleet-level management; regional/regulatory scale |
| **Storage** | Add disks/nodes (vSAN), remote datastores, supplemental storage | Balance with compute; vSAN rebalance |
| **Network** | Add leaf/spine capacity, Edge nodes, uplinks | Edge cluster scaling, T0/T1 limits, NSX configuration maximums |
| **Management plane** | Upsize/scale-out management appliances; HA form factors | Management domain capacity must grow with fleet |

### 2.2 Scalability Design Decisions

| Decision | Guidance |
|---|---|
| **Design to configuration maximums** | Know vCenter, cluster, NSX and vSAN limits (check Configuration Maximums); leave **headroom below limits** |
| **Domain sizing strategy** | Fewer, larger domains (simpler, shared limits) vs more, smaller domains (isolation, smaller blast radius, independent lifecycle) |
| **Modular building blocks** | Standardised host/cluster "pods" (fixed host profile and count) for predictable scaling and procurement |
| **Network scalability** | Spine-leaf with spare ports/uplinks; planned IP/VLAN/TEP address space; oversubscription ratio tracked |
| **NSX scale** | Size NSX Manager appliance (small/medium/large) and Edge nodes for forecast objects; add Edge clusters before reaching limits |
| **Management domain headroom** | Reserve capacity for additional vCenters/NSX/management components as domains and instances grow |
| **Fleet scale** | Move to multi-instance when approaching limits, for geographic or compliance reasons, or for blast-radius control |
| **Automation** | Use templates/IaC for repeatable expansion (add host, add cluster, add domain) |
| **Address plan** | Reserve IP pools, TEP ranges, VLANs, ASNs for growth |
| **Growth forecast** | Base on business projections (new apps, M&A, AI/GPU demand) from requirements |

### 2.3 Key Takeaways (Scalability)

- **Scale out by standard building blocks** (hosts → clusters → domains → instances) while staying within **documented maximums**.
- Scaling **beyond one domain/instance** is often a **design (isolation/compliance) choice**, not just a limit workaround.
- **Plan for the management plane scaling** too; many designs fail by under-sizing the management domain.
- **IP/VLAN/TEP address space and network ports** are common hidden scaling limits.
- **Scale-up vs scale-out**: large hosts reduce host count but increase blast radius per host and need greater N+1 reserve.

## 3. Capacity Management

### 3.1 Concepts

| Concept | Meaning |
|---|---|
| **Capacity** | Available CPU, memory, storage, network, and management-plane resources |
| **Headroom** | Reserved capacity for failures (HA), maintenance, growth, and peaks |
| **Utilisation vs demand** | Current usage vs peak/forecast demand |
| **Right-sizing** | Aligning VM resources to actual needs (reclaim idle/over-provisioned) |
| **Over-commitment** | Allocating more virtual resources than physical (CPU commonly; memory with care; storage via thin provisioning) |
| **Forecasting** | Trend-based projection of when resources will run out |

### 3.2 Capacity Design Decisions

| Decision | Guidance |
|---|---|
| **Failure reserve** | **N+1** minimum (N+2 for critical/large clusters); **50%** per site in stretched clusters |
| **vSAN slack space** | Keep ~25-30% free for rebuilds, rebalancing, maintenance; include FTT/RAID overhead in usable capacity |
| **CPU/memory ratios** | Define vCPU:pCPU and memory over-commit **per workload class** (lower for critical/latency-sensitive) |
| **Storage overhead** | Account for FTT/RAID overhead, dedupe/compression assumptions, snapshots, and thin-provisioning risk |
| **Network capacity** | Track uplink utilisation, oversubscription, Edge throughput, inter-site bandwidth |
| **Management domain capacity** | Include all management components (including HA forms), logs/metrics growth, backups |
| **Thresholds and alerts** | Set capacity thresholds (e.g., warning/critical) with alerts and review cadence |
| **Capacity tooling** | **VCF Operations**: capacity analysis, "time remaining", what-if scenarios, rightsizing, reclamation, cost/showback |
| **Review process** | Regular capacity review (e.g., monthly/quarterly), tied to procurement lead times |
| **Procurement lead time** | Trigger expansion **before** headroom is consumed (account for hardware lead time) |
| **Workload governance** | Quotas and lease policies via **VCF Automation** to prevent sprawl |
| **Workload placement** | DRS and (where used) affinity rules; separate clusters by workload class |

### 3.3 Capacity by Domain

| Domain | Capacity focus |
|---|---|
| **Management domain** | Fleet growth (additional vCenters, NSX Managers, VCF Operations/Automation, logs/metrics retention), backups, HA headroom, upgrade headroom |
| **Workload domain** | Workload demand forecast, HA/maintenance headroom, vSAN slack, Edge/network throughput, GPU capacity (if applicable), growth by business unit |
| **Edge clusters** | Throughput, session/connection counts, number of T0/T1 services |
| **Network fabric** | Port count, uplink bandwidth, TEP/IP/VLAN space |

### 3.4 Key Takeaways (Capacity)

- Capacity design = **demand + failure reserve + maintenance reserve + growth**.
- **Headroom is required for lifecycle operations** (host evacuation) and for **availability** (HA).
- Use **VCF Operations** for **forecasting and right-sizing**, and **VCF Automation** quotas/leases for **governance**.
- Track **management domain** capacity separately; it is a common bottleneck.
- Tie capacity triggers to **procurement lead time**.

## 4. Other Manageability Decisions

| Area | Decisions |
|---|---|
| **Standardisation** | Standard host profiles, cluster templates, naming conventions, tagging, folder/resource-pool structure |
| **Monitoring & logging** | Centralised via **VCF Operations** and **VCF Operations for logs**; alert routing to ITSM |
| **Configuration management / compliance** | Compliance benchmarks, drift detection, desired-state images |
| **Access management** | **VCF Identity Broker**/SSO, RBAC roles per team, least privilege, audit trails |
| **Automation** | Templates, IaC, APIs for repeatable operations (**VCF Automation**) |
| **Documentation & runbooks** | Operational runbooks, as-built documentation, change management |
| **Certificate lifecycle** | Central CA integration and renewal automation |
| **Backup management** | Policy, schedule, retention, test restores |
| **Support model** | Roles/responsibilities, escalation, vendor support contracts |

## 5. Scenario Cheat Sheet

| Scenario | Design decision |
|---|---|
| Many sites, need consistent patching | Multi-instance fleet with **fleet management**, per-instance SDDC Manager, staggered windows |
| Business units need independent upgrade timing | Separate **workload domains** (dedicated vCenter, preferably dedicated NSX) |
| Small ops team, limited skills | Standardised **consolidated/standard** architecture, VCF-orchestrated lifecycle, automation, managed service option |
| Hosts drift from desired firmware/driver baseline | **vLCM image-based** cluster management with vendor add-on |
| Upgrading a cluster at capacity limit | Insufficient headroom → add host/capacity first, or lower utilisation (headroom prerequisite) |
| Workload growth 30% in 12 months | Capacity forecast in **VCF Operations**, add hosts/clusters before headroom is exhausted; check domain limits |
| Approaching vCenter or cluster maximum | Add **new cluster/workload domain** rather than exceed configuration maximums |
| Management domain nearing capacity as fleet grows | Add hosts/storage to management domain; right-size appliances; consider HA/size implications |
| Developers over-provision VMs | Rightsizing in VCF Operations, quotas/leases in VCF Automation |
| Need to patch with minimal downtime | Rolling updates with N+1 headroom, live patching where supported, staggered clusters |
| Mixed manual patching of components | Risk: out-of-BOM combinations → move to **VCF-orchestrated** lifecycle |
| Compliance requires proven configuration baselines | Compliance monitoring in VCF Operations, desired-state images, documented standards |

---

## 6. Exam Traps

- **SDDC Manager** = infrastructure/domain lifecycle per instance; **fleet management** = management components across the fleet. Don't swap them.
- **Manual patching outside VCF** = supportability/BOM risk.
- **Headroom is not "wasted"**: it enables HA and rolling upgrades.
- **Shared NSX across domains** couples lifecycle and increases blast radius.
- **More domains/instances** improve isolation but **increase management overhead**.
- **Ignoring management domain capacity** is a classic design flaw.
- **Over-reliance on thin provisioning/over-commit** without monitoring = capacity risk.
- Scalability limits include **IP/VLAN/TEP space and physical ports**, not just compute.

---

## 7. Quick Recall

- **Lifecycle**: VCF Installer (Day-0) → **SDDC Manager** (domains, hosts, vCenter/NSX/vSAN, BOM-driven) + **fleet management** (management components across fleet) + **vLCM images** (hosts).
- **Always**: pre-checks, backups, headroom, staged windows, follow VCF upgrade order, avoid out-of-band patching.
- **Scalability**: host → cluster → domain → instance; respect **configuration maximums**; plan management-plane, network, and address-space growth.
- **Capacity**: demand + HA reserve + maintenance reserve + growth; vSAN slack ~25-30%; **VCF Operations** for forecasting/rightsizing; **VCF Automation** quotas and leases.
- **Trade-off**: standardisation and automation raise manageability; extra domains/instances raise isolation but also management effort.
