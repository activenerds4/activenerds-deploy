## 1. Learning Objectives

After this guide you should be able to:

1. Explain how VCF centralizes certificate and credential lifecycle through SDDC Manager.
2. Configure a Certificate Authority (Microsoft, OpenSSL, or third-party) in SDDC Manager.
3. Walk through the CSR → sign → install workflow for each CA type.
4. Distinguish **Update**, **Rotate**, and **Remediate** for passwords.
5. Configure scheduled password rotation and know its prerequisites.
6. Identify common failure causes and troubleshooting steps.

## 2. Security Compliance in VCF: The Big Picture

VCF is an opinionated, integrated stack. Security is handled by combining:

| Area | Mechanism | Where managed |
|---|---|---|
| Certificates | CA integration, CSR generation, automated install | SDDC Manager → Security / Workload Domain → Security |
| Credentials | Inventory of service/admin accounts, rotate/update/remediate | SDDC Manager → Security → Password Management |
| Configuration hardening | VMware security configuration guides (STIG-style baselines, PCI/NIST guidance), lockdown mode, syslog, NTP | vSphere / NSX / Aria Operations compliance packs |
| Access control | SSO identity sources, RBAC roles (ADMIN, OPERATOR, VIEWER) | SDDC Manager → Administration → Single Sign On / Users |
| Backup of configuration | SDDC Manager, vCenter, NSX backup to SFTP | SDDC Manager → Administration → Backup |

**Key principle:** Do not change certificates or passwords of VCF-managed components directly in the component UI. SDDC Manager keeps an inventory; out-of-band changes cause drift, which breaks lifecycle operations (upgrades, expansion, rotation).

## 3. Certificate Management

### 3.1 What SDDC Manager Manages

SDDC Manager can generate CSRs and replace certificates for:

- vCenter Server (machine SSL certificate)
- NSX Manager (cluster VIP and node certificates)
- SDDC Manager appliance itself
- Other VCF-managed components depending on release (for Aria Suite products, certificates are generally handled through Aria Suite Lifecycle Manager and its Locker)

**ESXi hosts:** Certificate handling is performed through vCenter (VMCA by default). Do not assume the SDDC Manager workflow covers ESXi in the same way as vCenter/NSX; verify per release.

### 3.2 Default State

Out of the box, vCenter certificates are signed by **VMCA** (VMware Certificate Authority) and NSX/SDDC Manager use self-signed or VMware-issued certificates. Browsers and integrations will flag these as untrusted. Replacing them with enterprise CA-signed certificates is a standard day-2 task.

### 3.3 Certificate Authority Options

| CA Type | How it works | Automation level |
|---|---|---|
| **Microsoft CA** | SDDC Manager submits CSRs directly to AD CS web enrollment (certsrv) using a service account and certificate template | Fully automated: generate CSR, request, install |
| **OpenSSL CA** | SDDC Manager acts as a built-in signing CA (you supply CA details) | Fully automated; self-signed root, so trust must be distributed manually |
| **Third-party / Other CA** | You generate CSRs, send to your CA, upload the signed bundle | Manual: generate CSR, download, sign externally, upload chain + cert, install |

### 3.4 Configuring Microsoft CA Integration

**Prerequisites**

- Microsoft AD Certificate Services with **Certificate Authority Web Enrollment** role enabled (HTTPS `certsrv` endpoint).
- A certificate template suitable for server authentication, with SANs allowed and subject supplied in the request. The template must be published on the CA.
- A service account with **Request Certificates** (Enroll) permission on the template and permission to use web enrollment.
- Network connectivity from SDDC Manager to the CA on 443, and DNS resolution of the CA FQDN.
- SDDC Manager must trust the CA chain (import the root/issuing CA into SDDC Manager trust store when prompted or ahead of time).
- Time sync (NTP) across SDDC Manager, CA, and components; certificate validity errors often trace back to clock skew.

**Steps (UI)**

1. SDDC Manager → **Administration → Security → Certificate Authority** (location varies slightly by release).
2. Select **Microsoft** and choose **Edit**.
3. Enter: CA Server URL (e.g., `https://ca01.corp.local/certsrv`), template name, username, and password.
4. Save. SDDC Manager validates connectivity and credentials.

**API equivalent:** `PUT /v1/certificate-authorities` (with CA type, server URL, template, credentials).

### 3.5 Configuring OpenSSL CA

1. Choose **OpenSSL** as the CA type.
2. Provide the Common Name, Organization, OU, Locality, State, and Country for the CA.
3. SDDC Manager creates the signing CA. Download and distribute the root certificate to clients that must trust VCF endpoints.

Use case: labs, POCs, isolated environments. Not typical for production enterprises that already have a PKI.

### 3.6 Certificate Replacement Workflow (CSR → Sign → Install)

Performed per workload domain: **Inventory → Workload Domains → [domain] → Security → Certificates**.

**Workflow A: Microsoft or OpenSSL CA (automated)**

1. **Generate CSRs:** select the resources (vCenter, NSX, etc.), choose the key size (typically 2048 or higher), key algorithm (RSA), and enter subject details (Organization, OU, Locality, State, Country, plus SANs as required).
2. **Generate Signed Certificates:** select the configured CA. SDDC Manager submits the CSRs and retrieves the signed certificates.
3. **Install Certificates:** SDDC Manager replaces certificates on the selected components and restarts affected services as needed.
4. **Verify:** check the Certificates tab for new expiry dates and issuer.

**Workflow B: Third-party CA (manual)**

1. **Generate CSRs** as above, then **Download CSR** bundle.
2. Submit CSRs to your CA and receive signed certificates.
3. Build the files: each leaf certificate plus the **full chain** (root and intermediates). Ensure correct order and PEM format.
4. In SDDC Manager choose **Upload and Install**, upload the chain and the per-resource certificates, and apply.
5. Verify trust and expiry.

**API flow:** `POST /v1/domains/{id}/csrs` → `PUT /v1/domains/{id}/certificates` (generate/sign) → `PATCH /v1/domains/{id}/certificates` (install/replace). (Endpoint names are exam-relevant at the concept level, not memorization level.)

### 3.7 Operational Considerations

- **Order and scope:** You can replace certificates for one resource or several at once. Replacing the SDDC Manager certificate affects UI/API trust for admins and automation.
- **Impact:** Service restarts occur. Perform during a maintenance window. Expect brief management-plane disruption for the replaced component.
- **Trust propagation:** After replacement, components that talk to each other (e.g., NSX ↔ vCenter, SDDC Manager ↔ vCenter) must trust the new chain. SDDC Manager handles this for VCF-managed components when you use its workflow; manual replacement does not.
- **Monitoring:** SDDC Manager displays certificate expiry in the domain's Security tab. Track expiring certificates well ahead of renewal, since the CSR → sign → install cycle may need change-control approval.
- **SANs and FQDNs:** SANs should include FQDN and, where required, short name and IP. Mismatches cause integration failures after install.
- **Key size and algorithm:** SHA-2 signing is required; weak keys are rejected.

### 3.8 Common Certificate Failures

| Symptom | Likely cause | Fix |
|---|---|---|
| CA validation fails when saving Microsoft CA config | Wrong URL (missing `/certsrv`), template name wrong, account lacks enroll rights, CA not trusted | Correct URL/template, grant enroll permission, import CA chain |
| Signed certificate generation fails | Template does not allow SAN in request, template not published, NTP skew | Fix template settings, publish template, sync time |
| Install fails on a component | Chain incomplete or wrong order, SAN/FQDN mismatch | Rebuild chain, regenerate CSR with correct SANs |
| Integrations break after replacement | Peer components do not trust new chain | Use SDDC Manager workflow; re-establish trust |

## 4. Password Management

### 4.1 What Gets Managed

SDDC Manager maintains an inventory of credentials for VCF components, including:

- ESXi host root accounts
- vCenter Server root and SSO administrator (`administrator@vsphere.local`) accounts
- NSX Manager admin, audit, and root accounts, and NSX Edge accounts
- SDDC Manager-managed service accounts (accounts created automatically by VCF for inter-component communication)
- Integrated products depending on release

View under **Administration → Security → Password Management**, filtered by workload domain and resource.

### 4.2 The Three Operations

| Operation | What it does | When to use |
|---|---|---|
| **Update** | You supply a specific new password; SDDC Manager changes it on the component and updates its inventory | You must set a known value (e.g., policy requirement, break-glass procedure) |
| **Rotate** | SDDC Manager generates random compliant passwords and applies them | Routine hygiene, compliance schedules, after staff turnover |
| **Remediate** | You supply the **current** actual password so SDDC Manager's inventory matches the component. No password is changed on the component | Password was changed outside SDDC Manager, or the credential shows a disconnected/mismatched state |

**Exam gotcha:** Remediate fixes SDDC Manager's *record*; Update and Rotate change the *component*. If a rotate fails because the stored password is wrong, remediate first, then rotate.

### 4.3 Prerequisites and Behavior

- The workload domain must be in an **Active** state, with no conflicting running tasks (upgrade, expansion, other credential operations).
- Components must be reachable and the stored credential must currently be valid.
- New passwords must meet each component's complexity policy. Rotated (generated) passwords meet policy automatically; manually supplied ones are validated.
- To view a rotated password, you can retrieve it through SDDC Manager's credentials view or the API (requires appropriate role). Handle retrieved credentials under your organization's secrets-management policy.
- Operations run as tracked tasks; review Tasks panel for status and failure detail.

### 4.4 Scheduled (Automatic) Rotation

SDDC Manager can auto-rotate selected credentials on a recurring interval.

- Interval options are in days (commonly **30, 60, or 90**) and are configured per credential or resource type.
- In recent releases, VCF-managed **service accounts** are automatically rotated on a schedule by default (commonly 30 days); administrator-level accounts are typically opt-in.
- Auto-rotation is enabled via the **Schedule Rotation** action in Password Management (or the credentials API with an auto-rotate policy).
- Rotation is skipped or fails if the domain is not Active or the stored password is out of sync; failed schedules show in Tasks and alerts.

**Design guidance (instructor opinion):** align the rotation interval with organizational compliance (e.g., PCI-DSS expects periodic changes; NIST guidance has moved toward change-on-compromise for human passwords, but machine/service credentials still benefit from frequent automated rotation). Avoid rotating admin accounts on a schedule that outpaces your ability to retrieve and record the new values if you depend on them for break-glass access.

### 4.5 Password Expiry Beyond SDDC Manager's Control

Local OS and appliance accounts have their own expiry settings (e.g., vCenter root and SDDC Manager local accounts). If an account expires and SDDC Manager's rotation cannot log in, you must restore access, then remediate. Review expiry policies on appliances and include them in operational runbooks.

### 4.6 Troubleshooting Password Operations

| Symptom | Likely cause | Fix |
|---|---|---|
| Rotate fails on a credential | Stored password out of sync, account locked/expired, component unreachable | Remediate, unlock/reset account, check connectivity |
| Credential shows as disconnected | Password changed out of band | Remediate with the current password |
| Operation blocked immediately | Domain not Active or another task running | Complete/clear the conflicting task |
| New password rejected | Does not meet component complexity | Use rotate, or supply a compliant password |

## 6. Exam Tips

1. **SDDC Manager is the source of truth.** If the question involves replacing certs or rotating passwords on VCF-managed components, the correct answer uses SDDC Manager, not the component UI.
2. **Three CA types:** Microsoft and OpenSSL are automated; third-party is manual CSR/upload. Know which one requires uploading a chain.
3. **Microsoft CA needs:** web enrollment (certsrv), a published template, an enroll-capable service account, and trust.
4. **Update vs Rotate vs Remediate:** user-chosen password / system-generated password / sync inventory to reality. This is a favorite distractor set.
5. **Active domain required** for credential operations; look for "operation blocked" scenarios.
6. **Scheduled rotation intervals** are in days; service accounts rotate by default in current releases.
7. **Full chain matters:** third-party installs fail when intermediates are missing or ordered incorrectly.
8. **SAN/FQDN correctness** shows up in "integration breaks after replacement" scenarios.
9. **Time sync** is the hidden root cause in many certificate and authentication failures.
10. **Read the version.** If a question names VCF 9.0, expect some of these tasks to be surfaced through VCF Operations/fleet management; for 5.x questions, expect SDDC Manager.

## 7. Practice Questions

### Question 1

An administrator configured Microsoft CA integration in SDDC Manager. Saving the configuration fails with an authentication/validation error. The CA is reachable and the service account password is correct. The template `VCF-WebServer` exists on the CA. What is the **most likely** missing configuration?

A. The ESXi hosts do not trust the root CA
B. The service account lacks Enroll permission on the template, or the template is not published on the CA
C. SDDC Manager backups are not configured
D. The workload domain is in a Failed state

**Answer: B**

**Explanation:** Microsoft CA integration relies on web enrollment with a template. The service account must have permission to request certificates using that template, and the template must be published (issued) by the CA. ESXi host trust (A) is unrelated to saving the CA configuration. Backups (C) have no bearing on CA validation. A domain's state (D) affects domain-level operations, not saving the CA settings. Also verify the URL includes `/certsrv` and the CA chain is trusted by SDDC Manager.

---

### Question 2

An engineer changed the NSX Manager `admin` password directly in the NSX UI during an incident. The next day, a scheduled password rotation for that credential fails in SDDC Manager. What should the engineer do **first** to restore normal management?

A. Run **Rotate** again; SDDC Manager will overwrite the password
B. Run **Remediate** and supply the current NSX `admin` password so the SDDC Manager inventory matches
C. Redeploy NSX Manager from SDDC Manager
D. Replace the NSX Manager certificate

**Answer: B**

**Explanation:** The stored credential in SDDC Manager no longer matches the actual password, so rotation cannot authenticate. **Remediate** updates SDDC Manager's record to match the component without changing the component password. After remediation, rotation or update can proceed normally. Re-running Rotate (A) will fail again for the same reason. Redeployment (C) is excessive and unrelated. A certificate replacement (D) does not affect credential synchronization.

---

### Question 3

Your organization uses an internal enterprise CA that is **not** Microsoft AD CS. Security requires replacing the vCenter and NSX Manager certificates in a workload domain. Which workflow is correct?

A. Select OpenSSL in SDDC Manager; it will sign certificates against the enterprise CA automatically
B. Generate CSRs in SDDC Manager, download them, have the enterprise CA sign them, then use **Upload and Install** with the certificates and full chain
C. Replace certificates directly in the vSphere Client and NSX UI to avoid inventory conflicts
D. Configure scheduled password rotation, which also renews certificates

**Answer: B**

**Explanation:** For a third-party CA, SDDC Manager cannot submit requests directly, so the process is manual: generate and download CSRs, obtain signed certificates, and upload them (with the complete chain of root and intermediates) for installation through SDDC Manager. OpenSSL (A) is SDDC Manager's own built-in CA and does not integrate with an external enterprise CA. Replacing certificates directly on components (C) bypasses SDDC Manager's workflow and trust propagation, and risks drift. Password rotation (D) manages credentials, not certificates.
