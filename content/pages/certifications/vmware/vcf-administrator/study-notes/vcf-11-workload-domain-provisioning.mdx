## 1. Learning Objectives

After this module you should be able to:

- Explain the role of **network pools** and configure them correctly.
- Describe the **host commissioning** workflow and the pre-checks that gate it.
- Size a **VI workload domain** and understand its impact on the management domain.
- Walk through **VI workload domain creation** end to end.
- Perform **host and cluster expansion**, **host removal**, and **decommissioning**.
- Troubleshoot the most common validation failures.

## 2. Key Concepts Refresher

| Term | Meaning |
|---|---|
| **Management domain** | First domain, created at bring-up. Hosts management vCenter, NSX Manager, SDDC Manager, and VCF operations components. |
| **VI workload domain (WLD)** | Domain for tenant/application workloads. Each WLD has its **own dedicated vCenter** (deployed in the management domain) and an NSX Manager cluster (dedicated or shared, depending on version/options). |
| **Network pool** | A named set of networks (vMotion, vSAN, NFS, iSCSI) with VLAN, MTU, subnet, gateway, and IP ranges. SDDC Manager draws host IPs for these networks from the pool. |
| **Commissioned host** | A host validated and added to SDDC Manager inventory as **unassigned**, tied to one network pool and one storage type. |
| **Decommissioned host** | A host removed from SDDC Manager inventory (must be unassigned first). |
| **Cluster** | A vSphere cluster in a WLD; a WLD can contain multiple clusters. |

**Mental model:** `Network pool → Commission hosts → Create WLD (or add cluster/host) → Operate → Remove host → Decommission`.

## 3. Network Pool Configuration

### 3.1 Purpose
SDDC Manager automatically assigns IP addresses to ESXi VMkernel adapters for **vMotion**, **vSAN**, and optionally **NFS** and **iSCSI**. It does this from network pools so you never type host VMkernel IPs during domain creation.

→ The **management** network is **not** part of a network pool. The host's management IP/FQDN is supplied when the host is commissioned (it must already exist on the host).

### 3.2 What a pool contains

| Network type | Required? | Settings |
|---|---|---|
| vMotion | Yes | VLAN ID, MTU, subnet/mask, gateway, IP inclusion range(s) |
| vSAN | Only if hosts will use vSAN | Same settings |
| NFS | Only if using NFS as principal/supplemental storage | Same, plus NFS server details at domain/cluster creation |
| iSCSI | Only if using iSCSI | Same |

### 3.3 Design guidelines
- **MTU**: 1500–9000. Use **9000 (jumbo frames)** for vMotion and vSAN where the physical fabric supports it end-to-end. An MTU mismatch is a classic cause of failed vSAN/vMotion validation.
- **IP ranges**: size each range to cover **current hosts plus growth**. Each host consumes one IP per network in the pool.
- **VLANs/subnets** must be routable/trunked on the physical switches to every host that uses the pool.
- **Pool-to-cluster relationship**: all hosts in one cluster must come from the **same network pool**.
- Use **separate pools** for different racks/L3 domains, different storage types, or different clusters that need different subnets.

### 3.4 Lifecycle rules (frequently tested)
- A pool that is **in use** (hosts commissioned or assigned) **cannot be deleted**.
- You can generally **add IP ranges** to an existing pool. You cannot remove or change a range that has IPs allocated.
- Core attributes (VLAN, subnet, gateway, MTU) of a pool in use are **not freely editable** in a way that would disrupt existing hosts. Plan correctly the first time.
- The management domain's pool is created automatically during bring-up from the deployment parameters.

### 3.5 Creating a pool (UI summary)
1. SDDC Manager → **Administration → Network Settings → Network Pool Settings**.
2. **Create Network Pool** → name it.
3. Select the network types to include (vMotion, vSAN, NFS, iSCSI).
4. For each: enter **VLAN ID, MTU, network, subnet mask, default gateway**, and **IP range(s)**.
5. Save. The pool is now selectable during host commissioning.

## 4. Host Commissioning and Pre-Checks

### 4.1 Why commission?
Commissioning validates a host and makes it available in the **free (unassigned) pool** so it can be consumed by a new WLD, a new cluster, or a cluster expansion.

### 4.2 Pre-requisites checklist

**Hardware/software**
- Hardware is on the **VMware Compatibility Guide** (vSAN ReadyNode if using vSAN).
- ESXi installed at a version **compatible with the VCF Bill of Materials (BOM)**, same build family as other hosts in the target cluster.
- Identical (or compatible) CPU generation, NICs, and storage layout within a cluster.
- For vSAN: disks present, **unclaimed and clean** (no stale partitions/vSAN config).

**Network/identity**
- Management IP configured; host reachable from SDDC Manager.
- **Forward (A) and reverse (PTR) DNS** records resolve correctly for the host FQDN.
- **NTP** configured and in sync; **SSH** enabled.
- Valid **root credentials**.
- ESXi **certificate** should match the FQDN (regenerate the self-signed cert after setting the hostname, otherwise thumbprint/FQDN validation can fail).
- A pre-existing **network pool** with enough free IPs for the host.

**State**
- Host is not already managed by another vCenter and has **no VMs** or leftover configuration.
- Default standard switch (vSwitch0) and management port group are as expected; no unexpected extra configuration.

### 4.3 The commission workflow
1. **Inventory → Hosts → Commission Hosts**.
2. Acknowledge the pre-requisite checklist.
3. Add hosts **one at a time or in bulk via a JSON file** (best for large builds).
4. For each host provide: **FQDN, storage type (vSAN / NFS / VMFS on FC / etc.), network pool, username/password**.
5. Click **Validate All**. SDDC Manager checks FQDN resolution, credentials, SSH, ESXi version/BOM compatibility, thumbprint, storage readiness, and network pool capacity.
6. Fix any failures and revalidate. Once all pass, **Next → Commit** (Commission).
7. Host appears as **Unassigned** in the inventory.

### 4.4 Common validation failures

| Symptom | Likely cause | Fix |
|---|---|---|
| FQDN validation fails | Missing/incorrect forward or reverse DNS | Correct DNS; flush caches |
| Credential/SSH failure | Wrong root password or SSH disabled | Fix password; enable SSH |
| Thumbprint / certificate error | Cert generated before hostname was set | Regenerate certificate on the host and restart services |
| Version incompatibility | ESXi build not aligned to BOM | Re-image or upgrade ESXi |
| Network pool error | Pool has insufficient free IPs, or wrong pool selected | Extend IP range / choose correct pool |
| Storage check fails | Disks not clean / wrong storage type selected | Wipe disks; choose correct storage type |
| Host already in use | Still joined to a vCenter or has VMs | Remove from old vCenter; clean host |

### 4.5 Decommissioning
- Only **unassigned** hosts can be decommissioned.
- Decommissioning removes the host from SDDC Manager inventory and releases its IPs back to the network pool.
- **Re-image the host** before reusing it in VCF; do not just recommission a dirty host.

## 5. Sizing a VI Workload Domain

### 5.1 Compute and minimums
- **vSAN-backed VI WLD:** minimum **3 hosts** (4 is recommended so you can tolerate host maintenance plus a failure/rebuild).
- **Non-vSAN principal storage (NFS, FC VMFS, etc.):** commonly a **minimum of 2 hosts** for a vSphere HA cluster, but confirm your version.
- Size clusters with **N+1 (or N+2)** host capacity for HA admission control and maintenance mode.
- Check **Configuration Maximums** for hosts per cluster and clusters/WLDs per VCF instance. Do not memorize numbers beyond what the blueprint lists; know *where* to look.

### 5.2 vSAN capacity sizing
Account for **storage policy overhead** and **slack space**:

| Policy (OSA example) | Approx. raw capacity consumed per 1 TB of usable data |
|---|---|
| FTT=1, RAID-1 | ~2.0 TB |
| FTT=1, RAID-5 | ~1.33 TB |
| FTT=2, RAID-6 | ~1.5 TB |
| FTT=2, RAID-1 | ~3.0 TB |

- Keep roughly **25–30% free** capacity for rebuilds, rebalancing, and snapshots/swap overhead.
- RAID-5/6 require a minimum number of hosts (RAID-5 needs 4; RAID-6 needs 6 in OSA; ESA behavior differs and adapts to cluster size).
- Decide **OSA vs. ESA** up front. ESA has stricter hardware requirements (NVMe-based ReadyNodes).

### 5.3 Management domain impact (often overlooked)
Every new VI WLD **adds VMs to the management domain**:

- **One new vCenter Server** (size: tiny / small / medium / large / x-large, chosen by expected host and VM counts).
- **NSX Manager cluster** (typically 3 nodes + VIP) unless the domain is configured to share an existing NSX instance.

So before you create a WLD, verify the management domain has enough **CPU, memory, and storage** for these appliances.

### 5.4 vCenter sizing quick reference (vSphere 8-era)

| Size | Hosts | VMs |
|---|---|---|
| Tiny | up to 10 | up to 100 |
| Small | up to 100 | up to 1,000 |
| Medium | up to 400 | up to 4,000 |
| Large | up to 1,000 | up to 10,000 |
| X-Large | up to 2,000 | up to 35,000 |

### 5.5 NSX considerations
- Plan **TEP IP addressing** (IP pool or DHCP) and **overlay transport VLAN**; MTU on the transport network must be **at least 1600** (9000 recommended).
- Plan for **NSX Edge cluster** deployment after the domain exists (a separate SDDC Manager workflow) if you need north-south connectivity, Tier-0/Tier-1 gateways, or AVN-style networks.

## 6. VI Workload Domain Creation

### 6.1 Pre-requisites
- Management domain healthy; sufficient capacity.
- **DNS** forward/reverse records for the **new vCenter**, **each NSX Manager node**, and the **NSX VIP**.
- **At least the minimum number of commissioned (unassigned) hosts** in the appropriate network pool with matching storage type.
- Licensing/subscription available for the components (workflow differs between 5.x license keys and 9.0 licensing).
- Backup of SDDC Manager and management components recommended before major changes.
- Time sync (NTP) and valid DNS across all components.

### 6.2 Step-by-step (conceptual UI flow)
1. **Inventory → Workload Domains → + Workload Domain → VI - Workload Domain**.
2. **Storage selection:** choose principal storage (vSAN, NFS, VMFS on FC, vVols, depending on version).
3. **Name:** domain name, organization name, and SSO option (e.g., join the management SSO domain or an isolated domain, where supported).
4. **Compute:** vCenter FQDN, IP address, subnet mask, gateway, root password, and vCenter size.
5. **Networking:** NSX Manager FQDNs/IPs and VIP, admin password; select or define **overlay networking** (TEP IP assignment, transport VLAN).
6. **Storage parameters:** for vSAN, choose OSA/ESA, failures to tolerate, and dedup/compression where applicable. For NFS/FC, provide share or LUN info.
7. **Host selection:** pick unassigned hosts and the **network pool**. Configure each host's **vSphere Distributed Switch** profile (uplinks, traffic type assignments, MTU).
8. **Licensing:** assign license keys/subscription as required.
9. **Review** all parameters → **Finish**.
10. Monitor the **task** in SDDC Manager. Expect a long-running orchestrated workflow (vCenter deploy → NSX deploy → cluster build → vDS/vSAN/NSX configuration).

### 6.3 Validate first
SDDC Manager runs **validation** before deployment (and the API offers `POST /v1/domains/validations`). Validation catches DNS, IP conflicts, host readiness, and capacity issues **before** any change is made.

### 6.4 Post-creation
- Verify the new vCenter appears in inventory and the domain status is **Active**.
- Deploy an **NSX Edge cluster** if north-south connectivity is required.
- Configure **Backup** (SFTP) and **Certificate** management, and register identity sources as required.
- Apply any vSphere/NSX customizations (VM classes, content libraries, etc.) outside the SDDC Manager lifecycle only where supported.

### 6.5 Failed workflows
- Review the **task and subtask** details; SDDC Manager supports **Retry** for most failed steps once the root cause is fixed.
- Logs: `/var/log/vmware/vcf/domainmanager/` on SDDC Manager (and related service logs) for deeper analysis.
- Do **not** manually delete half-built vCenter/NSX appliances; use SDDC Manager's retry or the documented cleanup/support procedure.

## 7. Host Expansion and Removal

### 7.1 Add a host to an existing cluster (scale out)
**Pre-reqs:** target cluster exists; host is **commissioned, unassigned, same network pool and storage type** as the cluster, with compatible hardware and ESXi version.

1. **Workload Domains → (domain) → Clusters → (cluster) → Actions → Add Host**.
2. Select the host(s) from the unassigned list.
3. Provide or confirm licensing.
4. Validate → Finish.

SDDC Manager installs/validates VCF components, joins the host to vCenter, configures the vDS, VMkernel adapters (IPs from the pool), and NSX transport node settings, and for vSAN claims disks and expands the vSAN datastore.

### 7.2 Add a new cluster to a workload domain
Use when you need a **different hardware profile, storage type, or network pool**, or a separate failure/management boundary. Select **Add Cluster**, pick hosts and networking, and configure the storage parameters for that cluster.

### 7.3 Remove a host from a cluster (scale in)
1. **Clusters → (cluster) → Hosts → Remove Host** (select host).
2. For vSAN: SDDC Manager places the host in maintenance mode with **full data migration (evacuation)** where capacity allows. Ensure sufficient free capacity on remaining hosts.
3. SDDC Manager removes the host from NSX, the vDS, and vCenter inventory.
4. The host returns to the **Unassigned** state.
5. Optionally **decommission** the host to remove it from SDDC Manager entirely.

**Constraints:**
- You cannot remove a host if it would drop the cluster below its **minimum host count** (e.g., 3 for vSAN) or violate FTT/HA requirements.
- Sufficient capacity must exist to evacuate data and satisfy HA admission control.

### 7.4 Delete a cluster or workload domain
- **Delete cluster:** hosts return to unassigned; VMs on the cluster must be handled beforehand.
- **Delete workload domain:** removes the domain's vCenter and NSX (if dedicated) from the management domain, and releases hosts as unassigned. This is **destructive**; there is a confirmation step.
- The management domain cannot be deleted through this workflow.

### 7.5 Operational best practices
- Always **commission before you consume**; never add hosts to a cluster via vCenter directly (unsupported, creates configuration drift from SDDC Manager's view).
- Scale clusters by adding hosts in a **consistent, balanced** way.
- Reimage and decommission retired hosts cleanly.
- Run a vSAN health check and an SDDC Manager health/pre-check before and after changes.

## 8. Exam Tips

1. **Order of operations** is a favorite: *Network pool → Commission → Create WLD/cluster → Add/Remove host → Decommission.*
2. **Network pool contents:** vMotion, vSAN, NFS, iSCSI. **Management is not in the pool.**
3. A **network pool in use cannot be deleted.** You can extend IP ranges.
4. **Commissioned hosts are Unassigned** until consumed by a domain/cluster. Only unassigned hosts can be **decommissioned**.
5. **DNS (forward and reverse)** is the number-one cause of failed validations. Check it first in troubleshooting scenarios.
6. **Every VI WLD gets its own vCenter**, deployed in the **management domain**. Therefore, management domain capacity is a sizing constraint.
7. **vSAN minimums:** 3 hosts minimum for a VI WLD; 4 recommended. Cannot remove hosts below the minimum.
8. **All hosts in a cluster share one network pool and storage type.**
9. **Use SDDC Manager, not vCenter,** to add/remove hosts and clusters in a VCF-managed domain.
10. **Bulk commission via JSON** is the efficient answer for large host counts.
11. **MTU questions:** vSAN/vMotion often 9000; NSX TEP at least 1600. MTU mismatches cause validation or connectivity failures.
12. **"Retry" before "rebuild":** failed workflow tasks can usually be retried after fixing the root cause.
13. Read the question for the **scenario keyword** (e.g., "unassigned," "in use," "minimum hosts," "different storage type") because they usually point directly to the right constraint.

### Quick-recall table

| Task | Where/Who | Key gate |
|---|---|---|
| Create network pool | SDDC Manager → Network Settings | VLAN, MTU, subnet, IP range |
| Commission host | SDDC Manager → Hosts | DNS, SSH, NTP, cert, BOM-compatible ESXi |
| Create VI WLD | SDDC Manager → Workload Domains | Min hosts, DNS for vCenter/NSX, mgmt capacity |
| Add host | SDDC Manager → Cluster | Unassigned, same pool/storage type |
| Remove host | SDDC Manager → Cluster | Min host count, vSAN evacuation capacity |
| Decommission | SDDC Manager → Hosts | Must be unassigned; reimage before reuse |

## 9. Practice Questions

### Question 1
An administrator is commissioning five new ESXi hosts in SDDC Manager. **Validate All** fails for every host with an FQDN error, even though the hosts respond to ping by IP address. What should the administrator check **first**?

- A. The vSAN network MTU in the network pool
- B. Forward and reverse DNS records for each host FQDN
- C. Whether the hosts have been added to the management vCenter
- D. The NSX TEP IP pool configuration

**Answer: B**

**Explanation:** Commissioning validation checks that each host FQDN resolves forward (A record) and reverse (PTR record). A host being reachable by IP does not prove DNS is correct. The vSAN MTU (A) and NSX TEP pool (D) are not part of host FQDN validation and are used later in domain/cluster creation. Hosts must **not** be joined to the management vCenter (C); they should be standalone, unassigned hosts.

---

### Question 2
A VCF administrator wants to remove a host from a 3-node vSAN cluster in a VI workload domain to repurpose it. What is the expected outcome?

- A. The removal succeeds and the host becomes unassigned
- B. The removal succeeds and the host is automatically decommissioned
- C. The removal is blocked because the cluster would fall below the minimum host count for vSAN
- D. The removal succeeds but vSAN data is lost on the removed host

**Answer: C**

**Explanation:** A vSAN-backed cluster in a VI workload domain requires a **minimum of three hosts**. SDDC Manager will not allow a removal that violates this minimum (nor FTT/HA requirements). The administrator must first **add a host** to the cluster (or choose a different design), then remove the target host. When removal is allowed, the host goes to **unassigned**, not decommissioned (B), and data is **evacuated** rather than lost (D).

---

### Question 3
An administrator needs to add four hosts to a new cluster that will use a different VLAN and subnet for vMotion and vSAN than the existing clusters. Which approach is correct?

- A. Edit the VLAN and subnet of the existing network pool, then commission the hosts
- B. Create a new network pool with the new VLAN/subnet settings, commission the four hosts into it, then add the cluster
- C. Commission the hosts into any pool and change their VMkernel IPs manually in vCenter after the cluster is created
- D. Add the hosts to the existing cluster and move them to a new cluster later with vCenter

**Answer: B**

**Explanation:** Network pools define the network settings that SDDC Manager applies to hosts in a cluster, and all hosts in a cluster must use the **same pool**. A pool that is in use should not be repurposed for different VLANs/subnets (A). Manual VMkernel changes in vCenter (C) bypass SDDC Manager and cause drift. Moving hosts between clusters in vCenter (D) is unsupported for VCF-managed domains. The supported workflow is: **create new pool → commission hosts to it → Add Cluster**.
