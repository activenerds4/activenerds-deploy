## 1. SDDC Manager in VMware Cloud Foundation

**SDDC Manager** is the central management interface for many VCF infrastructure operations. It provides visibility into the VCF environment and orchestrates important lifecycle and infrastructure workflows.

From an administrator's perspective, think of SDDC Manager as the place where you:

- Review the overall VCF environment
- Inspect domains and infrastructure inventory
- Work with hosts and clusters
- Commission eligible ESXi hosts into the VCF inventory
- Decommission hosts when they are being removed from service
- Start and track supported workflows
- Review system and component status
- Investigate workflow failures and warnings

### Mental model

```text
                 SDDC Manager
                      │
       ┌──────────────┼──────────────┐
       │              │              │
   Inventory       Workflows       Status
       │              │              │
 Hosts/domains    Tasks & jobs    Health/state
       │              │              │
       └──────────────┼──────────────┘
                      │
                VCF infrastructure
```

The important exam concept is that SDDC Manager provides **centralized visibility and orchestration** rather than simply being another vSphere client.

# 2. Dashboard Navigation

The dashboard is designed to provide an operational overview before an administrator drills into a specific object or workflow.

When approaching a dashboard-navigation question, identify what the question is asking:

- **Where is the object?** → Think inventory.
- **What operation is running?** → Think workflow/task tracking.
- **Is the environment healthy?** → Think status/health monitoring.
- **How do I add or remove infrastructure?** → Think host/domain lifecycle operations.

### Navigation strategy

Do not memorize menu names in isolation. Instead, associate each navigation area with its purpose.

| Operational need | Think about |
|---|---|
| Find ESXi hosts | Inventory |
| Review workload/management domains | Domain inventory |
| Add an eligible host | Commissioning |
| Remove a host | Decommissioning |
| See whether an operation is still running | Workflow/task status |
| Investigate a warning or failure | System/status monitoring |
| Understand what SDDC Manager knows about infrastructure | Inventory |

→ **Exam tip:** If the question says **“where can I see…”**, identify whether it is asking for inventory, workflow, or system-status information before selecting an answer.

# 3. Inventory Management

Inventory management is about understanding what infrastructure SDDC Manager recognizes and manages.

Depending on the VCF release and configuration, inventory views can expose information about:

- Domains
- Hosts
- Clusters
- Network infrastructure
- VCF-managed resources
- Lifecycle-related state
- Infrastructure relationships

The key distinction is:

→ **Inventory tells you what exists and how VCF sees it.**

It is different from workflow tracking, which tells you what operations are being executed.

---

## 3.1 Host Inventory

Host inventory is particularly important because hosts are the physical compute building blocks of VCF domains.

A host may be:

- Available for use
- Commissioned into VCF
- Assigned to a domain/cluster
- Under an operation
- Being prepared for removal
- Decommissioned or removed from active VCF use

When troubleshooting a host-related problem, first establish its **inventory state** before assuming that the host itself is unhealthy.

---

# 4. Host Commissioning

**Commissioning** is the process of bringing an eligible ESXi host under VCF's management so that it can be used for supported VCF infrastructure operations.

A simplified flow is:

```text
Eligible ESXi host
       │
       ▼
Add/commission host
       │
       ▼
Validation / configuration
       │
       ▼
VCF inventory
       │
       ▼
Available for domain/cluster operations
```

The exact screens, prerequisites, and workflow steps depend on the VCF release.

### Typical considerations

Before commissioning, verify prerequisites such as:

- Correct ESXi version for the target VCF release
- Network reachability
- Correct credentials
- Required DNS/name-resolution configuration
- Appropriate management-network configuration
- Host compatibility with the intended domain/cluster
- Hardware compatibility
- No conflicting prior VCF configuration

### Why commissioning matters

Commissioning changes the host from an externally managed or available resource into infrastructure that VCF can manage through its lifecycle and domain operations.

→ **Exam distinction:** Commissioning is not simply “turning on” an ESXi host. It is an inventory/lifecycle operation that prepares the host for VCF management.

---

# 5. Host Decommissioning

**Decommissioning** is the controlled process of removing a host from VCF management.

A simplified conceptual flow is:

```text
VCF-managed host
       │
       ▼
Prepare for removal
       │
       ▼
Decommission workflow
       │
       ▼
Host removed from active VCF inventory
```

The exact workflow depends on the host's role, domain, cluster configuration, and VCF release.

### Before decommissioning

An administrator should consider:

- Are workloads still running on the host?
- Is the host part of a cluster that can tolerate its removal?
- Are there dependencies on the host?
- Is the host required for availability/capacity?
- Does the supported VCF workflow need to be used?
- Is the intended removal permanent or temporary?

### Why the workflow matters

Simply removing or altering a VCF-managed host outside the supported lifecycle process can create an inconsistent management state.

→ **Exam tip:** When a question asks how to remove a VCF-managed host, look for the answer that uses the **supported SDDC Manager/VCF lifecycle workflow**, rather than an arbitrary direct removal from a lower-level management interface.

---

# 6. Workflow Tracking

SDDC Manager performs many operations as workflows rather than instantaneous configuration changes.

Examples can include:

- Host commissioning
- Host decommissioning
- Domain operations
- Cluster operations
- Lifecycle operations
- Infrastructure configuration changes

A workflow can have states such as:

```text
Queued
  │
  ▼
Running
  │
  ├──► Completed
  │
  └──► Failed
```

A workflow may also expose intermediate steps, tasks, progress, warnings, or error information.

---

## 6.1 Why workflow tracking matters

Suppose an administrator commissions a host and immediately checks the inventory.

If the operation is still running, the final state may not yet be visible.

The correct troubleshooting sequence is:

1. Identify the workflow.
2. Determine its current state.
3. Review the individual steps/tasks.
4. Identify any failure or warning.
5. Read the relevant error information.
6. Correct the underlying condition.
7. Retry or resume the supported operation as appropriate.

### Exam trap

Do **not** assume:

→ “The workflow page shows a problem, therefore the host is broken.”

A workflow failure can be caused by:

- Incorrect credentials
- Network reachability
- DNS problems
- Configuration mismatch
- Unsupported host state
- Capacity or dependency conditions
- A failed subtask

The workflow is the **operation**; the host is the **resource being operated on**.

---

# 7. System Status Monitoring

Status monitoring answers a different question from inventory:

→ **Inventory:** “What resources does VCF know about?”

→ **Status:** “What is the current condition/state of those resources or services?”

→ **Workflow:** “What operation is currently being performed, and did it succeed?”

This three-way distinction is highly useful for the exam.

| Question | Primary concept |
|---|---|
| What hosts exist? | Inventory |
| What domain contains the host? | Inventory |
| Is a host/service healthy? | Status/health |
| Is a commissioning operation running? | Workflow |
| Why did commissioning fail? | Workflow details + system/infrastructure status |
| What resources are currently managed? | Inventory |

---

# 8. Status Monitoring and Troubleshooting

When a dashboard indicates a warning or failure, avoid immediately making changes.

Use a structured process:

### Step 1 — Identify the affected object

Determine whether the issue concerns:

- Host
- Cluster
- Domain
- Network
- VCF management component
- Lifecycle operation

### Step 2 — Check current status

Determine whether the condition is:

- Healthy
- Warning
- Failed
- Unavailable
- In progress
- Unknown

### Step 3 — Check workflow history

If an operation was recently launched, determine whether the status problem is related to that workflow.

### Step 4 — Review details

Look for:

- Error messages
- Failed substeps
- Timestamps
- Affected resources
- Dependencies
- Recommended corrective action

### Step 5 — Correct the root condition

Only after identifying the cause should you make the required configuration change.

### Step 6 — Revalidate

Confirm that:

- The workflow completed successfully
- The object returned to the expected state
- Inventory reflects the intended configuration
- No related warnings remain

# 9. Inventory vs Workflow vs Status — The Exam Framework

Use this simple three-question framework:

```text
             What are you trying to know?
                         │
          ┌──────────────┼──────────────┐
          │              │              │
       WHAT EXISTS?   WHAT IS RUNNING?  HOW IS IT?
          │              │              │
       Inventory       Workflow        Status
```

### Inventory = WHAT

Examples:

- Which hosts are managed?
- Which domain contains a host?
- Which clusters exist?

### Workflow = WHAT IS HAPPENING

Examples:

- Is commissioning running?
- Did decommissioning complete?
- Which workflow step failed?

### Status = HOW IT IS

Examples:

- Is the system healthy?
- Is the host available?
- Is a component reporting an error?

This framework can eliminate several plausible but incorrect exam answers.

| Operation | Direction | Main purpose |
|---|---|---|
| Commissioning | Into VCF management | Prepare an eligible host for VCF-managed infrastructure |
| Decommissioning | Out of VCF management | Safely remove a host from VCF-managed infrastructure |
| Workflow tracking | N/A | Monitor the operation and its individual steps |
| Status monitoring | N/A | Determine current health/state |
| Inventory management | N/A | View and manage recognized infrastructure |

# 11. Operational Scenario

### Scenario

An administrator starts commissioning an ESXi host. Several minutes later, the host is not available for the expected next operation.

A weak troubleshooting approach would be:

→ “The host must be broken. Reinstall ESXi.”

A better VCF administrator approach is:

1. Open the relevant workflow/task.
2. Determine whether commissioning is still running.
3. If failed, identify the exact failed step.
4. Review the error.
5. Verify host prerequisites such as network connectivity, DNS, credentials, and compatibility.
6. Correct the issue.
7. Retry the supported workflow.
8. Verify that inventory and status now show the expected state.

This is exactly the type of reasoning an administrator should apply in an exam scenario.

---

# 12. Exam Tips

1. **Remember the three-way distinction:** inventory = what exists, workflow = what is happening, status = how it is.
2. **Commissioning brings an eligible host into VCF management.**
3. **Decommissioning is the controlled removal of a VCF-managed host.**
4. **Use supported VCF lifecycle workflows** rather than making arbitrary lower-level changes to VCF-managed infrastructure.
5. **A workflow failure does not automatically mean hardware failure.** Read the failed step and error.
6. **Check status before changing configuration.** The current state can explain why an operation is blocked.
7. **Expect asynchronous operations.** A newly launched workflow may not immediately produce its final inventory state.
8. **For “where do I look?” questions**, classify the information as inventory, workflow, or status first.
9. **For troubleshooting questions**, identify the affected object, check status, inspect workflow details, then correct the root cause.
10. **Version matters.** Exact UI labels, workflows, prerequisites, and supported operations can change between VCF releases. For the exam, use the terminology and procedures in the release covered by the official blueprint.

# Practice Questions

## Question 1

An administrator has started commissioning an ESXi host and wants to determine whether the operation is still running or has failed at a particular step. Where should the administrator focus first?

A. The host's virtual-machine inventory  
B. The workflow/task details for the commissioning operation  
C. The datastore browser  
D. The VM console

**Answer: B**

### Explanation

Commissioning is performed as a VCF workflow. Workflow details show whether the operation is queued, running, completed, or failed and can expose the step that caused a failure. The other choices do not directly provide commissioning workflow state.

---

## Question 2

Which statement best distinguishes inventory management from system-status monitoring in SDDC Manager?

A. Inventory identifies managed resources, while status monitoring indicates their current condition/state  
B. Inventory is used only for failed hosts, while status is used only for healthy hosts  
C. Inventory performs all workflows, while status monitoring performs host commissioning  
D. There is no functional distinction between inventory and status

**Answer: A**

### Explanation

Inventory answers **what resources VCF knows about and how they are organized**. Status monitoring answers **what condition those resources or services are currently in**. Workflow tracking is a third, separate concept concerned with operations being executed.

---

## Question 3

A VCF-managed ESXi host must be removed from service. Which approach is most appropriate?

A. Delete the host immediately from whichever lower-level interface is available  
B. Power off the host and wait for SDDC Manager to discover the change  
C. Use the supported VCF/SDDC Manager decommissioning workflow and verify its completion  
D. Remove the host's DNS record first and ignore the VCF inventory

**Answer: C**

### Explanation

A VCF-managed host should be removed through the supported lifecycle/decommissioning process. This allows SDDC Manager to update its inventory and perform the required checks and orchestration. Directly manipulating the host outside the supported workflow can leave the VCF management state inconsistent.

- [ ] How to distinguish inventory from workflow tracking?
<details>
<summary>Explanation</summary>
In VMware Cloud Foundation (SDDC Manager), the distinction comes down to **Static Data (What exists)** versus **Dynamic Execution (What is happening)**.

---

### 1. Inventory (The Static View)

**Inventory** represents the **state and configuration database** of managed objects in your environment. It answers the question: *"What components exist in my cloud, and how are they configured right now?"*

* **Scope:** Physical ESXi hosts, clusters, workload domains, network pools, licenses, storage targets, and deployed management appliances.
* **Characteristics:**
* **Declarative / Persistent:** Represents current physical or logical assets.
* **Source of Truth:** Used by SDDC Manager to calculate dependencies, check pre-flight health, and validate BOM (Bill of Materials) compliance.
* **Primary Interface Location:** UI menus like **Inventory `→` Hosts**, **Domains**, **Network Pools**, or **License Keys**.



---

### 2. Workflow Tracking (The Dynamic View)

**Workflow Tracking** (or Task / Progress Tracking) represents the **execution engine and task history**. It answers the question: *"What automated process is running, what steps has it executed, and did it succeed or fail?"*

* **Scope:** Long-running orchestration jobs such as domain creation, host commissioning, cluster scaling, patch upgrades, certificate replacements, or password rotations.
* **Characteristics:**
* **Procedural / Imperative:** Represents step-by-step state changes over time.
* **Sub-Task Breakdown:** Displays granular API execution steps, sub-task progress bars, elapsed time, logs, and error stack traces if a step fails.
* **Primary Interface Location:** UI menus like **Tasks / Activity Panel**, **LCM Update Progress**, or the `/v1/tasks` API endpoint.



---

### Core Comparison Matrix

| Attribute | Inventory | Workflow Tracking |
| --- | --- | --- |
| **Primary Question** | *"What assets exist in the system?"* | *"What is SDDC Manager currently doing?"* |
| **Data Nature** | State & Configuration Data | Execution Logs & Task Status |
| **Time Horizon** | Current Point-in-Time | Real-time Active / Historical Log |
| **Failure Indication** | Degraded Health / Non-Compliant status | Task Error / Failed Step Execution |
| **SDDC Manager API** | `/v1/hosts`, `/v1/domains`, `/v1/clusters` | `/v1/tasks`, `/v1/tasks/{id}` |

---

### How They Interact

Workflows modify Inventory. When you initiate a workflow (e.g., *Commission Host* or *Create Workload Domain*):

1. **Workflow Tracking** takes over to execute, log, and monitor the multi-step deployment process.
2. Once the workflow successfully completes, the newly provisioned host or domain is committed to the **Inventory** database.

- [ ] How to distinguish workflow state from system status?
<details>
<summary>Explanation</summary>
To distinguish **Workflow State** from **System Status** in VMware Cloud Foundation (SDDC Manager / VCF Operations), think of it as the difference between an **Action in Progress** (In Motion) vs. **Health of an Asset** (At Rest).

---

### 1. Workflow State ("In Motion")

**Workflow State** tracks the **transient execution of an automated task or process**. It answers: *"What process is currently running, where is it in the pipeline, and did the orchestration succeed or fail?"*

* **Nature:** Procedural, time-bound, and step-by-step.
* **Scope:** Operations like *Create Workload Domain*, *Rotate Passwords*, *Cluster Expansion*, or *LCM Patch Update*.
* **Key States:**
* `Queued` / `In Progress` / `Running`
* `Completed` / `Successful`
* `Failed` / `Error` (often accompanied by sub-task execution logs or retry prompts)


* **Where to Find It:** Tasks / Activity Panel, Workflow Execution Logs, or via the `/v1/tasks` API endpoint.

---

### 2. System Status ("At Rest")

**System Status** (or Entity/Inventory Status) reflects the **current health and operational availability of a component**. It answers: *"Is this managed resource functional, compliant, and ready to serve workloads right now?"*

* **Nature:** Declarative, ongoing, and state-persistent.
* **Scope:** Physical or logical entities like vCenter Server, ESXi Hosts, NSX Managers, or Workload Domains.
* **Key States:**
* `Active` / `Healthy` / `Green`
* `Degraded` / `Warning` / `Yellow`
* `Error` / `Inactive` / `Red` / `Unreachable`


* **Where to Find It:** Inventory dashboards (Hosts, Domains, Services), SOS Health Check utility output, or underlying SDDC database tables (`psql platform`).

---

### How They Interact (The "Sticky Error" Pitfall)

A common point of confusion occurs because **a Workflow State directly impacts System Status**:

```text
 ┌──────────────────────────┐         Fails         ┌──────────────────────────┐
 │  Workflow State:         ├──────────────────────►│  System Status:          │
 │  Rotate vCenter Password │                       │  vCenter = ERROR         │
 └──────────────────────────┘                       └────────────┬─────────────┘
                                                                 │ Blocks
                                                                 ▼
                                                    ┌──────────────────────────┐
                                                    │  LCM Pre-checks Fail     │
                                                    └──────────────────────────┘

```

1. **Failure Spillover:** If a workflow (such as a password rotation or host commissioning step) fails midway through execution, SDDC Manager automatically flips the targeted asset's **System Status** from `ACTIVE` to `ERROR` to prevent further actions on an unstable resource.
2. **The "Sticky State" Trap:** Even after you manually resolve the underlying issue on the appliance (e.g., manually fix the password desync), the **System Status** inside the inventory may remain stuck in `ERROR` until you clear/retry the failed **Workflow State** or run an API/database status remediation (`status: ACTIVE`).

---

### Comparison Matrix

| Attribute | Workflow State | System Status |
| --- | --- | --- |
| **Primary Question** | *"What action is being executed right now?"* | *"Is this component healthy and available?"* |
| **Target Object** | Orchestration Task / Job ID | Physical Host, VM, Appliance, or Domain |
| **Lifespan** | Temporary (starts when triggered, ends when complete) | Continuous (monitored perpetually) |
| **Example Values** | `IN_PROGRESS`, `SUCCESSFUL`, `FAILED` | `ACTIVE`, `DEGRADED`, `ERROR`, `UNREACHABLE` |
| **Primary Action on Failure** | Review sub-task logs, fix parameters, and **Retry Task** | Remediate hardware/service health, or clear entity error flag |
</details>
- [ ] What host commissioning accomplishes?
<details>
<summary>Explanation</summary>
**Host commissioning** is the formal onboarding workflow in VMware Cloud Foundation (VCF) that transitions a raw, freshly imaged physical ESXi host into SDDC Manager's **unassigned inventory**, making it ready for deployment into a cluster.

Before a physical server can be added to a Management Domain or VI Workload Domain, SDDC Manager must validate its configuration and ingest its metadata. Host commissioning accomplishes this through four core actions:

---

### 1. Registration in SDDC Manager Inventory

It registers the physical server's FQDN, root credentials, management IP, hardware specifications, and serial numbers into the SDDC Manager inventory database.

* **Target State:** The host transitions to the `UNASSIGNED_USABLE` state.
* **Storage Assignment:** The host is tagged for a specific primary storage protocol (e.g., vSAN, NFS, or Fibre Channel).

---

### 2. Association with VCF Network Pools

Host commissioning binds the host's physical network adapters (pNICs) to a predefined **VCF Network Pool**. SDDC Manager uses this mapping to automatically allocate IP addresses and VLAN tags for host infrastructure interfaces:

* **vMotion** (`vmk1`)
* **vSAN** (`vmk2`)
* **Host TEPs** for NSX overlay traffic (`vmk10`/`vmk11`)

---

### 3. Automated Validation & Compatibility Checks

During commissioning, SDDC Manager executes pre-flight checks against the host to verify that:

* **DNS & NTP:** Bi-directional DNS (Forward and PTR reverse lookups) and time synchronization match the rest of the VCF instance.
* **Hardware & BOM Alignment:** CPU, RAM, and storage controllers match VMware Bill of Materials (BOM) compatibility.
* **Storage Readiness:** Drives are clean, unpartitioned, and ready for vSAN or external storage datastore creation.
* **Credentials & SSL:** SSH access, root passwords, and host SSL thumbprints/fingerprints validate cleanly.

---

### 4. Creation of a Free Capacity Pool

Commissioning does **not** immediately start running workloads or put the host into a cluster. Instead, it creates an available **resource pool** of validated, hardware-ready hosts.

Once commissioned, these hosts can be consumed on demand to:

* Expand an existing cluster (Cluster Expansion).
* Build a brand-new VI Workload Domain.

---

### Summary Workflow Context



→ **Formula:** `Bare-Metal ESXi Host  --[Host Commissioning]-->  UNASSIGNED_USABLE Pool  --[Cluster Add]-->  Active VCF Cluster`


</details>
- [ ] What host decommissioning accomplishes?
<details>
<summary>Explanation</summary>
**Host decommissioning** is the inverse of host commissioning in VMware Cloud Foundation (VCF). It is the formal offboarding workflow that completely removes an **unassigned physical ESXi host** from SDDC Manager's management control and inventory database.

---

### Prerequisites Before Decommissioning

A host **cannot** be decommissioned while actively participating in a cluster.

Before host decommissioning can be triggered:

1. The host must first be removed from its vSphere cluster and VI Workload Domain (via a **Remove Host / Cluster Contraction** workflow in SDDC Manager).
2. The host must sit in the **Unassigned (`UNASSIGNED_USABLE`)** state in SDDC Manager's host inventory.

---

### What Host Decommissioning Accomplishes

#### 1. Removal from SDDC Manager Inventory

SDDC Manager completely unregisters the host from its internal inventory database (`psql`). The host's metadata, FQDN, serial numbers, SSH keys, and host record are permanently purged from VCF management tracking.

#### 2. Network Pool & IP Reclamation

SDDC Manager releases all static IP address allocations tied to that host back into its assigned **Network Pool**.

* The reserved IP addresses for **vMotion** (`vmk1`), **vSAN** (`vmk2`), and **NSX Host TEPs** (`vmk10`/`vmk11`) are marked as free and available for reuse by future host commissioning tasks.

#### 3. Security & Access Reset

* **SSH Key Disassociation:** Standard SSH trust keys and management certificates established between SDDC Manager and the host are revoked.
* **Credential Vault Cleanup:** SDDC Manager purges the host's stored root credentials and SSL thumbprints from its secure credential vault.

#### 4. Return to a Standalone Bare-Metal State

The physical server transitions back to an independent, bare-metal ESXi host. It is completely disconnected from VCF automation and can now be safely:

* Re-commissioned into a different VCF Instance or Network Pool.
* Repurposed for non-VCF workloads or standalone vSphere clusters.
* Retired, RMA'd, or returned to hardware vendor leases.

---

### Commissioning vs. Decommissioning Summary

| Action | Starting State | Ending State | Key Operations Handled |
| --- | --- | --- | --- |
| **Commissioning** | Bare-Metal ESXi | `UNASSIGNED_USABLE` Pool | Validates hardware, assigns to Network Pool, reserves IPs, adds to VCF inventory |
| **Decommissioning** | `UNASSIGNED_USABLE` Pool | Standalone / Managed Outside VCF | Releases IP allocations, purges credentials/certs, removes from VCF inventory |
</details>
- [ ] Why supported lifecycle workflows matter?
<details>
<summary>Explanation</summary>
Using **supported lifecycle workflows** in VMware Cloud Foundation (VCF) matters because SDDC Manager manages a tightly coupled, hyper-converged software stack (ESXi, vCenter, NSX, vSAN, and VCF Operations).

Attempting to perform lifecycle operations manually or using out-of-band tools breaks the core automation engine and creates critical technical risks:

---

### 1. Preserving the SDDC Manager "Source of Truth"

SDDC Manager maintains an internal inventory database (`psql`) tracking the state, version, certificates, and relationships of every host, appliance, and cluster.

* **Supported Workflow:** SDDC Manager executes the change and simultaneously updates its inventory database.
* **Manual / Out-of-Band Change:** If you update ESXi or vCenter directly via vSphere Lifecycle Manager (vLCM) or CLI, SDDC Manager's database becomes desynchronized. It will report incorrect versions, fail pre-checks, or mark components in an `ERROR` system status.

---

### 2. Strict Bill of Materials (BOM) & Interoperability Validation

VCF releases are tested as an integrated, single unit known as the **Bill of Materials (BOM)**. SDDC Manager automatically enforces compatibility matrices across all components.

* **Supported Workflow:** SDDC Manager only permits upgrades to certified, cross-validated build numbers (e.g., ensuring a specific NSX build is fully compatible with the vCenter and ESXi versions being deployed).
* **Manual / Out-of-Band Change:** Patching a single component out of order can introduce breaking API changes, unsupported driver/firmware combinations, or broken inter-appliance communications.

---

### 3. Automated Order of Operations & Rollback Safety

Updating an SDDC stack requires a strict execution sequence to prevent management disconnects (e.g., upgrading NSX control planes before transport nodes, or updating vCenter before ESXi hosts).

* **Supported Workflow:** Lifecycle workflows handle host evacuations (vMotion), maintenance mode toggles, pre-flight health checks, database backups, and step-by-step orchestrations automatically.
* **Manual / Out-of-Band Change:** Skipping order-of-operations steps risks dropping the control plane mid-update or breaking vSAN storage quorum during host reboots.

---

### 4. Supportability and Vendor SLA Compliance

Broadcom/VMware Global Support Services (GSS) requires environments to stay within validated VCF upgrade paths.

* Environments with out-of-band modifications or desynchronized SDDC databases often require manual database repairs before official patches or upgrades can be applied.

---

### Summary Context



→ **Formula:** `Supported Workflow  →  Automated BOM Checks + Strict Order Execution + Database Sync = Stable Cloud Stack`


</details>
- [ ] How to investigate a failed workflow?
<details>
<summary>Explanation</summary>
To investigate a failed workflow in VMware Cloud Foundation (SDDC Manager), follow these diagnostic steps to locate the exact sub-task failure, inspect the relevant log files, and determine the root cause.

1. **Identify the Task ID in SDDC Manager UI:** 1-2 mins.
In the SDDC Manager UI, open the **Tasks** panel (bottom bar or left navigation) and click on the failed task. Locate the **Task ID** (e.g., `a1b2c3d4-e5f6-...`) and note the specific sub-task where the progress bar halted.

*How to verify:* You can see the full execution tree and confirm which specific step returned an `ERROR` state.


2. **Inspect the Failed Task via SDDC Manager REST API:** 2 mins.
If the UI does not show enough detail, SSH into the SDDC Manager appliance as `vcf` (then `su` to `root`) and query the API directly using `curl`:

```bash
curl -k -X GET "https://localhost/v1/tasks/<TASK_ID>" -H "Accept: application/json" | jq .

```

*How to verify:* The JSON output will display the exact `errorCause`, `message`, and nested `subTasks` containing the failing component API call.


3. **Tail the Central Operations Log (domainmanager.log):** 3-5 mins.
Most domain operations, provisioning, and workflow orchestrations log directly to `domainmanager.log`. Search for your Task ID or recent thread errors:

```bash
tail -n 200 -f /var/log/vmware/vcf/domainmanager/domainmanager.log | grep -i "ERROR"

```

*How to verify:* You will see the specific Java stack trace or exception that triggered the workflow rollback or failure.


4. **Check Component-Specific Log Files:** Step-dependent.
Depending on which service was executing during the failure, navigate to the specific log file:

* **Lifecycle Management (LCM) / Upgrades:** `/var/log/vmware/vcf/lcm/lcm.log`
* **Host Commissioning / Pre-checks:** `/var/log/vmware/vcf/sddc-support/sos.log`
* **Password & Certificate Operations:** `/var/log/vmware/vcf/operationsmanager/operationsmanager.log`
* **NSX or vCenter Operations:** Review `/var/log/vmware/vcf/domainmanager/domainmanager.log` or check the target vCenter (`/var/log/vmware/vpxd/vpxd.log`) or NSX Manager (`/var/log/proton/nsxapi.log`) directly.

*How to verify:* The component log will confirm if the issue was caused by an authentication failure, network timeout, DNS PTR resolution failure, or locked resource.


5. **Run the SOS Utility to Capture a Health Summary:** 5 mins.
Execute the VCF Support and Maintenance (SOS) tool to run health checks against the environment and gather a diagnostic bundle:

```bash
/opt/vmware/sddc-support/sos --health-check

```

*How to verify:* The SOS output will display a pass/fail matrix across DNS, NTP, services, and storage health to confirm if an underlying infrastructure issue caused the failure.

- [ ] Why a workflow failure does not automatically mean hardware failure?
<details>
<summary>Explanation</summary>
A workflow failure in VMware Cloud Foundation (VCF) indicates that an **orchestration process failed to complete its state machine**, which is far more commonly caused by software, configuration, or environmental issues than broken server hardware.

SDDC Manager workflows combine hundreds of automated sub-tasks—API calls, SSH commands, database updates, and network handshakes—across multiple distributed appliances. A failure simply means one of those procedural steps returned an unexpected code or timed out.

---

### Common Non-Hardware Causes of Workflow Failures

#### 1. Software & Environmental Prerequisites (Most Common)

* **DNS Mismatches:** Missing or inaccurate reverse lookup (PTR) records for ESXi hosts, vCenter, or NSX Managers.
* **NTP Clock Drift:** Time divergence greater than 60 seconds between ESXi hosts, appliances, or NTP servers, causing Kerberos or TLS authentication handshakes to fail.
* **IP Conflicts & Unreachable Gateways:** An assigned IP address is already occupied on the subnet, or a gateway ping check fails.
* **Firewall / Port Blocks:** Required ports (e.g., SSH `22`, HTTPS `443`, NSX overlay `4789`, or API ports) are blocked between SDDC Manager and target endpoints.

#### 2. Authentication & Security Misconfigurations

* **Credential Desynchronization:** Expired root or admin passwords, or a password that was updated on an appliance out-of-band without updating SDDC Manager's vault.
* **TLS Certificate Trust Errors:** Untrusted, expired, or invalid SSL/TLS certificates blocking secure HTTPS REST API communication between management components.

#### 3. SDDC Manager Database or Service Desync

* **Resource Lock Constraints:** A previous task failed or sat abandoned, leaving an inventory object locked in a `PENDING` or `IN_PROGRESS` state in the `psql` database, blocking new workflows.
* **Stale Internal Cache:** Service microservices (`domainmanager`, `lcm`, or `operationsmanager`) experiencing memory pressure or unhandled exceptions that clear upon a simple service restart (`systemctl restart ...`).

#### 4. Host Software State

* **Dirty Disk / Existing Partitions:** During host commissioning or vSAN cluster creation, the workflow will fail if ESXi local drives contain pre-existing VMFS partitions or RAID signatures that SDDC Manager refuses to overwrite automatically.
* **Maintenance Mode Conflicts:** An ESXi host is stuck in maintenance mode or running lingering VMs that prevent an automated host reboot.

---

### Genuine Hardware Failures (The Minority of Cases)

Hardware issues usually only cause workflow failures when they directly disrupt the underlying hypervisor or network path:

* **Dead Physical NIC (pNIC):** A broken network cable or bad SFP module causing TEP or Management interfaces to go offline during network pool assignment.
* **Drive Controller / Disk Failure:** A drive dropping offline completely during a vSAN claim step.
* **RAM / CPU Faults:** Hardware Purple Screen of Death (PSOD) on an ESXi host during a reboot cycle.

---

### Summary Verification

To verify whether a failure is hardware or software-driven:

1. **Check Component Reachability:** Ping the host and access its IPMI/iLO/iDRAC console. If the physical server is powered on and accessible via its out-of-band management console, the physical hardware is likely healthy.
2. **Review `domainmanager.log`:** Tailing `/var/log/vmware/vcf/domainmanager/domainmanager.log` on SDDC Manager will usually reveal software exceptions (such as `HttpClientErrorException`, `DNSLookupException`, or `AuthFailure`) rather than hardware errors.
</details>
- [ ] Why inventory may not immediately show the final state of an in-progress operation?
<details>
<summary>Explanation</summary>
In VMware Cloud Foundation (VCF) and SDDC Manager, the inventory does not immediately reflect the final target state during an operation because **inventory reflects validated state, while workflows represent state transitions**.

This delay is an intentional architectural design driven by several key factors:

---

### 1. Intermediate and Transition States

An orchestration workflow (such as creating a Workload Domain, adding a cluster, or updating an appliance) consists of dozens or hundreds of sub-tasks executed sequentially.

* **To prevent false assumptions:** If SDDC Manager updated the inventory state to `ACTIVE` or `COMPLETE` at the start of a task, other automated services or administrators might attempt to deploy workloads to a resource that is only half-configured.
* **Transient States:** During an operation, an asset often transitions through temporary intermediate states (e.g., `PENDING`, `CONFIGURING`, or `PROVISIONING`). The final state is only written once the entire workflow completes successfully.

---

### 2. Transactional Integrity & Rollback Safety

SDDC Manager treats major operations as **atomic transactions**.

* **Staging vs. Committing:** Configuration changes, IP allocations, and host assignments are held in a staging or running state within the execution engine.
* **Rollback Protection:** If a workflow fails at step 80 out of 100, the automation engine attempts to roll back the changes or flag the asset as `ERROR`. If the inventory had already been updated to show the final `ACTIVE` state, the source-of-truth database would become corrupt relative to the physical infrastructure.

---

### 3. Decoupled Asynchronous Architecture

SDDC Manager's architecture separates the **Task/Workflow Engine** from the **Inventory Database**:

1. **Execution Phase:** The Task Engine (`domainmanager` / REST API) asynchronously executes API calls against target endpoints (vCenter, ESXi, NSX).
2. **Validation Phase:** Once the task engine finishes, it runs a post-validation check to confirm the target appliance or host is responding correctly on the network and meeting BOM specifications.
3. **Commit Phase:** Only after post-validation passes does the Task Engine issue a `COMMIT` to update the central database (`psql`) and refresh the API inventory cache.

---

### 4. UI/API Caching and Polling Intervals

In some cases, the underlying database has actually updated, but the SDDC Manager UI or REST API endpoint appears delayed:

* **Background Sync:** SDDC Manager periodically polls underlying components (like vCenter or NSX) to verify status rather than maintaining a constant real-time stream for every single asset parameter.
* **Browser/API Cache:** The UI web interface caches inventory views and updates them periodically or upon an explicit page refresh/task completion event.

---

### How to Verify the True Current State

If you need to verify whether an operation is still actively modifying an asset versus finished:

* **Check Active Tasks:** Go to **Tasks** in SDDC Manager or run `curl -k https://localhost/v1/tasks/<TASK_ID>` to see if sub-tasks are still executing.
* **How to verify success:** Once the task status changes to `SUCCESSFUL`, refresh the inventory view or query the inventory API (`/v1/hosts` or `/v1/domains`). The state will update from its transient state to its final `ACTIVE` state.
</details>
- [ ] How to use dashboard/status information to begin troubleshooting?
<details>
<summary>Explanation</summary>
To use the SDDC Manager dashboard and status indicators as an effective troubleshooting starting point, follow a systematic top-down triage process. Dashboards isolate whether an issue is isolated to a specific component, caused by an active workflow, or tied to an environmental dependency.

---

### Triage Workflow Using Dashboards & Statuses

1. **Check System Health & Active Workflows:** 1 min.
Look at the main SDDC Manager dashboard indicators:

* **System Health Banner / Status:** Identify if the overall status is `Green (Healthy)`, `Yellow (Degraded)`, or `Red (Error)`.
* **Tasks / Activity Panel:** Check for any active, stuck, or recently failed workflows (`IN_PROGRESS` or `FAILED`).

*How to verify:* Confirm whether an active workflow failure caused the system status to flip to `ERROR`.


2. **Isolate the Affected Functional Area:** 2 mins.
Drill down into the specific dashboard view based on the alert or symptom:

* **Domains View:** Check if the status error is isolated to a single VI Workload Domain or spans the entire Management Domain.
* **Hosts View:** Filter hosts by state (`UNASSIGNED_USABLE`, `ACTIVE`, or `ERROR`) to pinpoint whether a specific physical host is experiencing hardware, connectivity, or maintenance mode issues.
* **Services View:** Check the operational status of core control plane services (SDDC Manager microservices, vCenter Server, and NSX Managers).

*How to verify:* You will narrow the scope from the entire VCF instance down to a single host, appliance, or domain.


3. **Cross-Reference Dashboard Alarms with Environment Dependencies:** 2 mins.
If the status shows `DEGRADED` or `UNREACHABLE`:

* Check if the affected appliance or host is reachable via ping/SSH.
* Verify underlying infrastructure dependencies that commonly trigger dashboard warnings: DNS PTR lookups, NTP clock sync, or expired TLS certificates.

*How to verify:* Run a quick `sos --health-check` from the SDDC Manager CLI to validate overall environment health against the dashboard findings.


---

### Dashboard Status Indicator Matrix

| Indicator | Status Meaning | Immediate Action |
| --- | --- | --- |
| **Green (Active / Healthy)** | Component is operating normally within BOM constraints. | No action required. |
| **Yellow (Degraded / Warning)** | Non-critical fault, certificate nearing expiration, or soft resource limit reached. | Review alerts tab for expiring certs or capacity warnings. |
| **Red (Error / Unreachable)** | Critical service failure, desynchronized credentials, or broken task workflow. | Open **Tasks**, inspect `domainmanager.log`, and verify host/appliance connectivity. |
| **In Progress / Locked** | An automated workflow is actively modifying the asset's state. | Allow the task to finish; do not attempt manual out-of-band changes. |

- [ ] Why exact UI terminology and workflow behavior should be matched to the VCF release covered by the exam?
<details>
<summary>Explanation</summary>
Matching exact UI terminology and workflow behavior to the specific VMware Cloud Foundation (VCF) release covered by an exam is critical for three primary reasons:

---

### 1. Renamed & Evolved Product Architecture

VMware frequently renames, merges, or introduces new core components between major releases. Selecting a term or tool from a different version—even if it performs a similar function—will mark the question incorrect.

* **VCF 4.x / 5.x vs. VCF 9.x:**
* In VCF 4/5, the deployment engine is called **Cloud Builder**, and configuration inputs are provided via the **Deployment Parameter Sheet**.
* In VCF 9, Cloud Builder is retired and replaced by the **VCF Installer**, and the configuration sheet evolved into the **Planning & Preparation (P&P) Workbook** / **VCF Deployment Specification JSON**.
* Operational fleet management transitioned from **Aria Operations / SDDC Manager UI** into **VCF Operations** and **VCF Management Services**.



---

### 2. Changed Administrative & Task Workflows

Exam questions often test the precise step-by-step sequence in the UI. A workflow that was required in VCF 4.x may be automated, moved, or deprecated in VCF 5.x or VCF 9.

* **Validation Workflow:**
* In legacy Cloud Builder, validation was an inline step during initial workbook upload.
* In VCF 9, the workflow follows a formal **Validate-Then-Deploy** engine that validates software packages against the **Local/Online Depot** before execution and supports live in-line remediation.


* **Storage Options:**
* Earlier VCF exams strictly enforced **vSAN** as the only valid primary storage choice for the Management Domain.
* Recent releases (VCF 5.2 / VCF 9) introduced supported workflows for **External Storage (NFS / Fibre Channel)** as the primary datastore during bring-up.



---

### 3. Precision in Multiple-Choice Distractors

Exam writers deliberately create "distractor" options using terminology from older or newer VCF releases to test whether you know the exact release specification:

```text
Question: Which tool is used to execute the initial Management Domain bring-up?
 ❌ Option A: Cloud Builder (Correct for VCF 4/5, but incorrect if the exam tests VCF 9)
 ❌ Option B: SDDC Manager (Incorrect; SDDC Manager is deployed BY the bring-up engine)
 ─────────
 ──► Correct Answer depends entirely on the VCF version specified in the exam track!

```

---

### Summary Rule for Exam Preparation

Always verify the **exam blueprint version** (e.g., VCP-VCF 5.x vs. VCP/VCAP VCF 9.x) before studying. Memorize the exact UI navigation paths, wizard step names, and feature terminology designated for that specific release.
</details>
