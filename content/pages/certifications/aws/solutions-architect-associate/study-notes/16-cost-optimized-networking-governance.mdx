## 1. Architectural Overview & Fundamentals

<AccordionGroup type="single">
<AccordionItem title="Deep-Dive: Where network money goes">

Rates change, so learn the **shape**, not the numbers:

* **Data transfer in** from the internet is free; **out to the internet** is charged per GB (with a small monthly free allowance).
* **Cross-AZ** traffic within a Region is charged in both directions per GB; keeping chatty tiers in the same AZ (while preserving availability) reduces cost.
* **Cross-Region** transfer is charged per GB.
* **Traffic within the same AZ over private IPs** is free; using public or Elastic IPs for in-VPC traffic can add charges.
* **Public IPv4 addresses** are billed hourly, including those attached to running resources, so eliminate unnecessary public addresses.
* **NAT gateways** bill hourly per gateway plus per GB processed, which can dominate costs for data-heavy private workloads.

</AccordionItem>
<AccordionItem title="Deep-Dive: NAT gateway per AZ versus shared">

One NAT gateway per AZ is the **high-availability** design and avoids cross-AZ data charges, but multiplies the hourly cost. A single shared NAT gateway is cheaper for dev and test but is a single point of failure and incurs cross-AZ traffic. A **NAT instance** can be cheaper at low volumes but you manage patching, scaling, and failover. Prefer **gateway endpoints** for S3 and DynamoDB, which bypass NAT entirely and are free.

</AccordionItem>
</AccordionGroup>

| Decision | Lower-cost choice | Trade-off |
|---|---|---|
| Private subnets reaching S3 or DynamoDB | Gateway VPC endpoint (no charge) | None for these two services |
| Private subnets reaching other AWS services at high volume | Interface endpoints (hourly plus per GB, often below NAT processing) | Per-endpoint per-AZ charge |
| Dev or test outbound internet | Single shared NAT gateway or NAT instance | Reduced availability |
| Production outbound internet | NAT gateway per AZ | Higher fixed cost, better HA |
| A few VPCs need connectivity | VPC peering (no hourly attachment fee; standard data transfer applies) | Non-transitive, no overlapping CIDRs |
| Many VPCs and on-premises | Transit Gateway (hourly per attachment plus per GB) | Operational simplicity versus cost |
| Global content delivery | CloudFront (cached responses, lower egress than serving from origin; origin-to-CloudFront transfer is free) | Cache design effort |
| Hybrid steady high volume | Direct Connect (lower per-GB data transfer out, port hours) | Setup lead time and fixed cost |
| Hybrid low volume or temporary | Site-to-Site VPN (hourly plus data transfer) | Throughput limits per tunnel |
| Non-HTTP global acceleration | Global Accelerator (hourly fee plus premium data transfer) | Choose for performance and static IPs, not for savings |

## 2. Core Mechanisms & Flow

```
Before (expensive)                              After (optimized)

Private subnet --> NAT GW --> Internet GW       Private subnet --> S3 gateway endpoint --> S3  (free)
        --> S3 (NAT per-GB charge)              Private subnet --> interface endpoint --> other AWS APIs
                                                Users --> CloudFront --> origin  (cache hit = no origin egress)
App tier AZ-a <--cross-AZ--> DB AZ-b            Read replica in each AZ, readers in same AZ as clients
```

**Other cost-aware designs:** consolidate multiple ALBs using host- and path-based routing; apply **throttling** (API Gateway usage plans, WAF rate-based rules) to cap abusive or runaway traffic; right-size VPN and Direct Connect bandwidth (multiple VPN connections with Transit Gateway ECMP to aggregate bandwidth versus one Direct Connect port); use Route 53 alias records to AWS resources, which are free to query.

### Cost management tools

| Tool | Purpose | Key facts |
|---|---|---|
| AWS Cost Explorer | Visualize, filter, and forecast costs and usage | Group by service, account, tag; recommendations for rightsizing and commitments |
| AWS Budgets | Alerts and automated actions | Cost, usage, Reserved Instance and Savings Plans coverage and utilization budgets; actions can apply IAM or SCP policies |
| AWS Cost and Usage Report | Most detailed billing data | Delivered to S3; query with Athena; supports resource-level data |
| Cost allocation tags | Attribute cost to teams or projects | Must be **activated** in the Billing console before they appear in cost reports; apply tag policies via Organizations |
| Consolidated billing (Organizations) | One bill, pooled volume discounts | Reserved Instance and Savings Plans benefits can be shared across accounts |
| AWS Compute Optimizer | Right-sizing recommendations | EC2, EBS, Lambda, Auto Scaling groups |
| Savings Plans | Commitment discounts | Covered in the previous module |

## 3. Configuration & Practical Implementation

```bash
# Budget with an email alert at 80% of a monthly limit
aws budgets create-budget --account-id 111111111111 \
  --budget '{"BudgetName":"monthly-prod","BudgetLimit":{"Amount":"5000","Unit":"USD"},
    "TimeUnit":"MONTHLY","BudgetType":"COST"}' \
  --notifications-with-subscribers '[{"Notification":{"NotificationType":"ACTUAL",
    "ComparisonOperator":"GREATER_THAN","Threshold":80,"ThresholdType":"PERCENTAGE"},
    "Subscribers":[{"SubscriptionType":"EMAIL","Address":"finops@example.com"}]}]'

# Cost by service for last month, grouped by a cost allocation tag
aws ce get-cost-and-usage --time-period Start=2026-10-01,End=2026-11-01 \
  --granularity MONTHLY --metrics UnblendedCost \
  --group-by Type=TAG,Key=project
```

## 4. Final Exam Playbook: Decision Cheat Sheet

| If the stem says... | Choose... |
|---|---|
| Least operational overhead | Managed or serverless (Lambda, Fargate, Aurora, DynamoDB, S3) |
| Decouple, buffer spikes | SQS (plus SNS for fan-out; EventBridge for event routing) |
| Existing JMS or AMQP app, no code changes | Amazon MQ |
| Orchestrate multi-step workflow | Step Functions |
| Automatically rotate DB credentials | Secrets Manager |
| Block SQL injection or rate limit at the edge | AWS WAF (with CloudFront or ALB) |
| Org-wide restriction on accounts | Service control policies |
| Governed multi-account setup quickly | Control Tower |
| Exclusive single-tenant key control | CloudHSM |
| Scale reads on relational DB | Read replicas or Aurora readers, plus ElastiCache |
| Failover of RDS within Region | Multi-AZ |
| Static IPs, TCP or UDP, fast regional failover | Global Accelerator (NLB behind) |
| Cacheable global HTTP content | CloudFront |
| Connect many VPCs and on-premises | Transit Gateway |
| Private S3 access with no extra cost | Gateway endpoint |
| Unknown S3 access pattern | Intelligent-Tiering |
| Long-term compliance archive | Glacier Deep Archive with Vault Lock or Object Lock (Compliance mode) |
| Interruptible batch compute | Spot (with queue and checkpointing) |
| Steady predictable compute across services | Compute Savings Plan |
| Ad hoc SQL on S3 | Athena with partitioned Parquet |
| Streams to S3 without custom code | Firehose |

**Final tactics:** read the last sentence of the stem first to find the actual requirement; eliminate answers that violate any stated constraint; prefer AWS-native managed solutions over custom code; and answer every question, because there is no guessing penalty.

## 5. Exam Traps & Common Distractors

- **Trap 1:** Sending S3 traffic through a NAT gateway when a free gateway endpoint exists.
- **Trap 2:** Using one NAT gateway in a design that claims production high availability.
- **Trap 3:** Using Transit Gateway for two VPCs when peering is cheaper and sufficient.
- **Trap 4:** Forgetting to activate cost allocation tags, then wondering why they are missing in reports.
- **Trap 5:** Treating Budgets as a spending limit. Budgets alert (and can trigger actions); they do not by themselves stop spend.
- **Trap 6:** Choosing Direct Connect for a small, temporary, or urgent connection where a VPN is faster and cheaper.

## Self-Assessment & Exam Traps Checklist

- [ ] I can reduce NAT and data transfer costs in a VPC design.
<details>
<summary>Explanation</summary>

Use gateway endpoints for S3 and DynamoDB, interface endpoints for high-volume AWS API traffic, keep traffic within an AZ where possible, use CloudFront to cache content, remove unneeded public IPv4 addresses, and match NAT gateway count to availability needs (shared in dev, per AZ in production).

</details>

- [ ] I can choose between VPC peering and Transit Gateway on cost and scale.
<details>
<summary>Explanation</summary>

Peering has no hourly attachment fee and suits a small number of VPCs with simple connectivity. Transit Gateway adds hourly and per-GB charges but simplifies routing and supports transitive connectivity for many VPCs, VPNs, and Direct Connect.

</details>

- [ ] I can pick Direct Connect or VPN and size bandwidth sensibly.
<details>
<summary>Explanation</summary>

Direct Connect suits sustained high-volume transfer with consistent performance and lower per-GB egress rates. VPN suits quick, low-volume, or backup connectivity; aggregate several tunnels with Transit Gateway ECMP when more bandwidth is needed, and size to measured demand rather than peak guesses.

</details>

- [ ] I can use cost tools to find, allocate, and control spend.
<details>
<summary>Explanation</summary>

Cost Explorer visualizes and forecasts, Budgets alerts on thresholds and coverage, the Cost and Usage Report provides detailed data for analysis in Athena, activated cost allocation tags attribute spend to teams, and consolidated billing pools discounts across accounts.

</details>
