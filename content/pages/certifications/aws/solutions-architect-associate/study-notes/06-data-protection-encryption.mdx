## 1. Architectural Overview & Fundamentals

<AccordionGroup type="single">
<AccordionItem title="Deep-Dive: Envelope encryption">

KMS can directly encrypt only small payloads (up to 4 KB). For larger data, services use **envelope encryption**:

1. The service calls `GenerateDataKey` on a KMS key; KMS returns a plaintext data key and the same key encrypted under the KMS key.
2. The service encrypts the data locally with the plaintext data key, then discards the plaintext key.
3. The encrypted data key is stored alongside the data.
4. To decrypt, the service calls `Decrypt` on KMS with the encrypted data key, then decrypts the data locally.

KMS keys never leave KMS unencrypted, and every use is logged in CloudTrail.

</AccordionItem>
<AccordionItem title="Deep-Dive: Key policies and grants">

Every KMS key has a **key policy**, the primary access control. IAM policies can grant access to a key only if the key policy allows IAM policies to do so (the default policy delegates to the account). For **cross-account** use, both the key policy in the owning account and an IAM policy in the calling account must allow it. **Grants** provide temporary, programmatic delegation to AWS services.

</AccordionItem>
</AccordionGroup>

| Key type | Who manages | Rotation | Visibility / cost |
|---|---|---|---|
| AWS owned key | AWS | AWS-managed, invisible | Free, no CloudTrail visibility |
| AWS managed key (aws/s3, aws/ebs) | AWS, in your account | Automatic about every year, not configurable | Visible in KMS; no monthly key fee |
| Customer managed key | You | Optional automatic rotation (annual default, configurable period) or manual | Monthly fee plus request cost; full key policy control |
| Imported key material | You supply | Manual only | Use for strict key-origin requirements |
| AWS CloudHSM | You (single-tenant HSM, FIPS 140-2 Level 3) | You manage keys and HSM clusters | Choose when you need exclusive key control; KMS custom key store can front it |

## 2. Core Mechanisms & Flow

```
Client --TLS--> CloudFront / ALB (certificate from ACM) --TLS--> App --> S3 / EBS / RDS
                                                                       |
                         encrypt data with data key  <-- GenerateDataKey --  AWS KMS (CMK + key policy)
                                                                       |
                                                           CloudTrail logs every Encrypt/Decrypt
```

### Encryption at rest by service

| Service | Option | Exam nuance |
|---|---|---|
| Amazon S3 | SSE-S3 (default for new objects), SSE-KMS, DSSE-KMS, SSE-C, client-side | SSE-KMS adds audit and key control; S3 Bucket Keys reduce KMS request costs |
| Amazon EBS | KMS encryption of volumes, snapshots, and data in transit to the instance | Unencrypted snapshot can be copied to an encrypted snapshot, then restored |
| Amazon RDS | KMS at creation; covers storage, backups, replicas, snapshots | Cannot encrypt an existing unencrypted instance in place: snapshot, copy with encryption, restore |
| Amazon DynamoDB | Always encrypted at rest (AWS owned, AWS managed, or customer managed key) | Choose customer managed key for audit and control |
| Amazon EFS | KMS at creation; enforce TLS with the mount helper | Encryption at rest cannot be added later |

### Encryption in transit

* **AWS Certificate Manager (ACM):** provisions public TLS certificates for free, with automatic renewal when validated by DNS. Deploys to ELB, CloudFront (certificate must be in us-east-1), and API Gateway. Public ACM certificates **cannot be exported** or installed directly on EC2.
* Enforce HTTPS in S3 with a bucket policy condition `aws:SecureTransport` set to false and an explicit Deny.

## 3. Configuration & Practical Implementation

```json
{
  "Sid": "DenyUnencryptedTransport",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::example-data", "arn:aws:s3:::example-data/*"],
  "Condition": { "Bool": { "aws:SecureTransport": "false" } }
}
```

```bash
# Create a customer managed key and enable automatic rotation
aws kms create-key --description "app data key"
aws kms enable-key-rotation --key-id <key-id>

# Encrypt an unencrypted RDS instance: snapshot -> encrypted copy -> restore
aws rds create-db-snapshot --db-instance-identifier prod-db --db-snapshot-identifier prod-snap
aws rds copy-db-snapshot --source-db-snapshot-identifier prod-snap \
  --target-db-snapshot-identifier prod-snap-enc --kms-key-id <key-id>
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier prod-db-enc --db-snapshot-identifier prod-snap-enc
```

### Data protection, retention, and recovery

| Control | Protects against | Details |
|---|---|---|
| S3 Versioning (plus MFA Delete) | Accidental overwrite or delete | Keeps prior versions; combine with lifecycle to expire old versions |
| S3 Object Lock | Tampering for compliance | WORM; Governance mode (privileged users can override) versus Compliance mode (no one, including root, can delete until retention ends) |
| S3 Glacier Vault Lock | Policy changes on archives | Locks a compliance policy permanently |
| S3 Block Public Access | Accidental public exposure | Enable at account and bucket level |
| S3 replication (CRR/SRR) | Regional loss, compliance copies | Requires versioning on source and destination |
| AWS Backup | Centralized backup policy | Backup plans, cross-Region and cross-account copies, Vault Lock, supports EBS, RDS, DynamoDB, EFS, FSx, and more |
| Amazon Macie | Unknown sensitive data | Classifies S3 data and finds PII |

## 4. Exam Traps & Common Distractors

- **Trap 1:** Trying to enable encryption on an existing unencrypted RDS instance or EFS file system directly. Use snapshot copy (RDS) or create a new encrypted file system and migrate (EFS).
- **Trap 2:** Choosing KMS when the requirement is exclusive, single-tenant HSM control. That points to CloudHSM.
- **Trap 3:** Assuming Governance mode Object Lock satisfies strict regulations. Compliance mode prevents deletion even by root.
- **Trap 4:** Requesting an ACM public certificate for installation on an EC2 instance's web server. Terminate TLS at ELB or CloudFront instead.
- **Trap 5:** Forgetting that CloudFront certificates must be in us-east-1.
- **Trap 6:** Forgetting that cross-account KMS use needs both the key policy and an IAM policy in the caller account.
- **Trap 7:** Enabling replication without versioning. S3 replication requires versioning on both buckets.

## Self-Assessment & Exam Traps Checklist

- [ ] I can explain envelope encryption and why KMS uses it.
<details>
<summary>Explanation</summary>

KMS limits direct encryption to 4 KB, so services request a data key, encrypt data locally, and store the encrypted data key with the data. Only KMS can decrypt the data key, so access to data depends on permission to use the KMS key, and each use is auditable in CloudTrail.

</details>

- [ ] I can choose between AWS owned, AWS managed, and customer managed keys, or CloudHSM.
<details>
<summary>Explanation</summary>

Customer managed keys give control over key policy, rotation, and audit. AWS managed keys are convenient but not configurable. AWS owned keys are invisible and free. CloudHSM is for single-tenant, customer-controlled HSMs when regulations require exclusive key custody.

</details>

- [ ] I can encrypt an existing unencrypted RDS database.
<details>
<summary>Explanation</summary>

Take a snapshot, copy it with encryption enabled and a KMS key, and restore a new DB instance from the encrypted copy. Then redirect the application to the new endpoint. Encryption cannot be toggled on an existing instance.

</details>

- [ ] I can design WORM retention and backup protection for compliance.
<details>
<summary>Explanation</summary>

Use S3 Object Lock in Compliance mode with versioning for immutable object retention, Glacier Vault Lock for archive policies, and AWS Backup with Vault Lock plus cross-Region or cross-account copies for protected backups. Add lifecycle rules to enforce retention and expiry.

</details>
