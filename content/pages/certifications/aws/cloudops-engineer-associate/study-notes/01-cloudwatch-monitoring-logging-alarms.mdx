## 1. Metrics, Namespaces and Resolution

A metric is identified by **namespace + metric name + dimensions**. AWS services publish to `AWS/<Service>` namespaces; the CloudWatch agent publishes to `CWAgent` by default.

| Telemetry | Default granularity | Notes |
|---|---|---|
| EC2 basic monitoring | 5 minutes | Free, enabled by default |
| EC2 detailed monitoring | 1 minute | Extra cost, enable per instance or in launch template |
| Custom standard-resolution | 1 minute | `PutMetricData` |
| Custom high-resolution | 1 second | Alarms can evaluate at 10 or 30 seconds |

EC2 hypervisor-level metrics cover CPU, network and disk **I/O** but never **memory utilization or disk space used**. Those require the CloudWatch agent.

<AccordionGroup type="single">
<AccordionItem title="Deep-Dive: How the CloudWatch agent is configured and distributed">

The unified CloudWatch agent collects system-level metrics (memory, swap, disk used, processes via `procstat`) and log files from EC2, on-premises servers, containers.

* **Config:** JSON file generated by the wizard `amazon-cloudwatch-agent-config-wizard` or written by hand.
* **Distribution at scale:** store the JSON in **Systems Manager Parameter Store** (for example `AmazonCloudWatch-linux`) and apply it with `fetch-config -c ssm:<name>`. Install the agent itself with Run Command (`AWS-ConfigureAWSPackage`) or State Manager.
* **Permissions:** instance profile with `CloudWatchAgentServerPolicy` (publish metrics and logs). Writing the config to Parameter Store needs `CloudWatchAgentAdminPolicy`.
* **ECS:** run the agent as a **daemon service** (one task per container instance) or as a sidecar. Container Insights provides cluster, service and task metrics.
* **EKS:** install the **Amazon CloudWatch Observability** add-on (agent plus Fluent Bit) with an IAM role for the service account; Container Insights with enhanced observability follows.

</AccordionItem>
</AccordionGroup>

```bash
# Start the agent on an EC2 Linux instance using a config stored in Parameter Store
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
  -a fetch-config -m ec2 -s -c ssm:AmazonCloudWatch-linux

# Verify status
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a status
```

## 2. CloudWatch Logs

* **Hierarchy:** log group (retention, KMS encryption, access) contains log streams.
* **Retention:** default is **never expire**, so set a retention period to control cost.
* **Metric filters** turn matching log text into a metric you can alarm on (for example count of `ERROR`). They apply only to events ingested after creation.
* **Subscription filters** stream events in near real time to Kinesis Data Streams, Amazon Data Firehose, or Lambda (up to two filters per log group).
* **Logs Insights** is the query language for ad hoc analysis. **Export to S3** (`CreateExportTask`) is asynchronous and meant for archive, not real time.
* **Cross-account observability:** a monitoring account creates an Observability Access Manager (OAM) **sink**; source accounts create a **link**. This is how one account views metrics, logs and traces from many accounts and Regions.

```
 EC2 / ECS / EKS / Lambda
        |  logs                      +--> Metric filter --> Metric --> Alarm --> SNS
        v                            |
  CloudWatch Logs group ------------>+--> Subscription filter --> Firehose --> S3 / Kinesis / Lambda
        |
        +--> Logs Insights (ad hoc)  +--> Export task --> S3 (archive)
```

## 3. Alarms

| Concept | Detail |
|---|---|
| States | `OK`, `ALARM`, `INSUFFICIENT_DATA` |
| Evaluation | Period, evaluation periods, datapoints to alarm (M out of N) |
| Missing data | `missing`, `notBreaching`, `breaching`, `ignore` |
| Metric alarm actions | SNS, Auto Scaling policy, EC2 actions (stop, terminate, reboot, recover), Systems Manager actions |
| Composite alarm | Rule expression over other alarms with `AND`, `OR`, `NOT`, for example `ALARM(HighCPU) AND ALARM(HighLatency)` |
| Composite alarm actions | **SNS and Systems Manager only** (no EC2 or Auto Scaling actions) |

Alarms cannot call Lambda directly. Route **alarm to SNS to Lambda** or use the alarm state-change event on **EventBridge** (Module 02). Composite alarms reduce alert noise: build the child alarms with no actions and attach a single action to the composite.

```bash
aws cloudwatch put-composite-alarm \
  --alarm-name checkout-degraded \
  --alarm-rule 'ALARM("HighCPU") AND ALARM("High5xx")' \
  --alarm-actions arn:aws:sns:us-east-1:111122223333:ops-pager

aws cloudwatch put-metric-alarm --alarm-name cpu-recover \
  --namespace AWS/EC2 --metric-name StatusCheckFailed_System \
  --dimensions Name=InstanceId,Value=i-0abc1234567890def \
  --statistic Maximum --period 60 --evaluation-periods 2 --threshold 1 \
  --comparison-operator GreaterThanOrEqualToThreshold \
  --alarm-actions arn:aws:automate:us-east-1:ec2:recover
```

## 4. Dashboards, CloudTrail, Prometheus/Grafana, Bedrock

* **Dashboards** are global resources that can show widgets from **multiple accounts and Regions** (with cross-account observability or cross-account sharing set up). They can be shared via public link, specific email addresses (Cognito), or single sign-on.
* **CloudTrail** records API activity. **Event history** shows 90 days of management events. Create a **trail** (to S3, optionally CloudWatch Logs) for longer retention, data events (S3 objects, Lambda invokes) and organization-wide trails. **CloudTrail Insights** flags unusual API call rates. CloudTrail answers "who did what" and CloudWatch answers "how is it performing".
* **Amazon Managed Service for Prometheus** and **Amazon Managed Grafana** provide managed Prometheus-compatible metric storage and dashboards, typically for container workloads.
* **AI workloads:** Amazon Bedrock publishes runtime metrics to CloudWatch (invocations, latency, input and output token counts, throttles, errors). Enable **model invocation logging** to CloudWatch Logs or S3 to capture prompts and responses.
* **Serverless:** watch Lambda `Errors`, `Throttles`, `Duration`, `ConcurrentExecutions`, and enable X-Ray for tracing.

## 5. Notifications with SNS

* Alarms notify SNS topics directly. Other services (S3 event notifications, Auto Scaling notifications, AWS Backup, CloudFormation) publish to SNS if the **topic access policy** allows the service principal.
* A topic using **SSE with a customer managed KMS key** must grant the publishing service permission in the key policy, otherwise notifications silently fail.
* Email and SMS subscribers must **confirm** the subscription.

## 6. Exam Traps & Common Distractors

- **Trap 1:** "Memory utilization is not in CloudWatch." The answer is the CloudWatch agent, not detailed monitoring.
- **Trap 2:** Attaching an EC2 recover action to a **composite** alarm. Use a metric alarm for EC2 or Auto Scaling actions.
- **Trap 3:** Expecting a metric filter to backfill historical log data. It only evaluates new events.
- **Trap 4:** Choosing CloudTrail to graph CPU or CloudWatch to identify who deleted a resource. Match the tool to the question.
- **Trap 5:** Log group retention left at "never expire" when the scenario is about reducing cost.

## Self-Assessment & Exam Traps Checklist

- [ ] I can explain why memory metrics are absent by default on EC2 and how to collect them across a fleet.
<details>
<summary>Explanation</summary>

The hypervisor cannot see inside the guest OS, so memory used and disk space used are not published. Install the CloudWatch agent, store its JSON config in Parameter Store, and apply it with `fetch-config -c ssm:<name>` via Run Command or State Manager. The instance profile needs `CloudWatchAgentServerPolicy`. Metrics land in the `CWAgent` namespace.

</details>

- [ ] I can design an alarm that pages only when two conditions are true at the same time.
<details>
<summary>Explanation</summary>

Create two metric alarms without actions, then a composite alarm with `ALARM(A) AND ALARM(B)` and an SNS action. Composite alarms can only trigger SNS and Systems Manager, so any Auto Scaling or EC2 actions stay on the underlying metric alarms.

</details>

- [ ] I know how to make an alarm invoke a Lambda function.
<details>
<summary>Explanation</summary>

Alarms do not have a Lambda action. Either subscribe the Lambda function to the alarm's SNS topic, or create an EventBridge rule on the `CloudWatch Alarm State Change` event with Lambda as the target. EventBridge is preferred when you need filtering on specific alarm names or states.

</details>

- [ ] I can pick the right log delivery mechanism for real-time processing versus archival.
<details>
<summary>Explanation</summary>

Real-time or near real-time: **subscription filter** to Kinesis, Firehose, or Lambda. Archival: Firehose to S3 for continuous delivery, or a log group **export task** to S3, which is asynchronous. Ad hoc investigation: Logs Insights.

</details>
