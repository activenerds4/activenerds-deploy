GenAI observability extends classic monitoring (latency, errors) with **tokens, prompt quality, hallucination rate, guardrail interventions, retrieval quality, and tool-call behavior**. Know which AWS feature captures each signal.
</Callout>

## 1. The GenAI Observability Stack (Skills 4.3.1, 4.3.3)

| Signal | Source |
|---|---|
| Operational metrics (invocations, latency, errors, throttles, token counts) | CloudWatch `AWS/Bedrock` namespace metrics |
| Full request/response records | **Bedrock model invocation logging** to S3 and/or CloudWatch Logs (disabled until enabled) |
| Distributed traces | **AWS X-Ray** across API Gateway, Lambda, Bedrock calls, downstream services |
| FM interaction tracing | Bedrock Agents trace, AgentCore observability, custom spans for retrieval and tool calls |
| Business impact | Custom metrics (resolution rate, conversion, deflection), dashboards |
| Audit and compliance | CloudTrail, CloudWatch Logs with retention |
| Dashboards | CloudWatch dashboards, **Amazon Managed Grafana**, Amazon QuickSight for business views |

```
App --> metrics (CloudWatch: tokens, latency, guardrail hits, thumbs-up rate)
    --> traces (X-Ray: gateway > Lambda > retrieval > Bedrock)
    --> logs (invocation logs: prompt, response, modelId, usage) --> Logs Insights / Athena
    --> dashboards (ops + business) + alarms + anomaly detection
```

```bash
aws bedrock put-model-invocation-logging-configuration --logging-config '{
  "cloudWatchConfig": {"logGroupName": "/bedrock/invocations",
     "roleArn": "arn:aws:iam::111122223333:role/BedrockLogsRole"},
  "s3Config": {"bucketName": "my-invocation-logs", "keyPrefix": "bedrock/"},
  "textDataDeliveryEnabled": true, "imageDataDeliveryEnabled": false,
  "embeddingDataDeliveryEnabled": false }'
```

<Callout variant="warning" title="Exam Trap: Logging sensitive content">
Invocation logs contain prompts and completions, which may include PII. Encrypt the destination with KMS, restrict access, set retention (S3 Lifecycle, log group retention), and consider disabling text delivery for sensitive workloads.
</Callout>

## 2. Comprehensive GenAI Monitoring (Skill 4.3.2)

| What to track | How |
|---|---|
| **Token usage** (input/output per feature, per tenant) | Bedrock metrics plus custom dimensioned metrics |
| Cost anomalies | **AWS Cost Anomaly Detection**, Cost Explorer with tags |
| Token burst patterns | CloudWatch anomaly detection alarms on token metrics |
| Prompt effectiveness | Quality scores from automated evaluation, user feedback ratios |
| **Hallucination rate** | Grounding-check failure rate, sampled LLM-as-a-judge scoring, golden dataset runs |
| Response quality and drift | Scheduled evaluations; trend length, refusal rate, scores |
| Latency | `InvocationLatency`, time to first token from client instrumentation |
| Errors and throttles | `InvocationClientErrors`, `InvocationServerErrors`, `InvocationThrottles` |
| Guardrail activity | Guardrail intervention metrics and trace results |

```
CloudWatch alarm examples
 - OutputTokens SUM per 5 min > 2x baseline (anomaly detection band) --> page + throttle caller
 - InvocationThrottles > 0 for 3 of 5 periods --> scale-out / cross-Region / quota action
 - Grounding failure rate > 5% over 1 h --> open incident, rollback prompt version
```

## 3. Tool Performance Frameworks (Skill 4.3.4)

Agents and function-calling apps depend on tools; monitor them like services.

| Metric | Insight |
|---|---|
| Call counts per tool and per agent | Which tools matter; unused tools to remove |
| Success vs error rate, retry counts | Reliability |
| Tool latency distribution | Slow tools stall whole agent loops |
| Parameter validation failures | Poor tool descriptions or schemas |
| Multi-agent coordination traces | Handoffs, loops, redundant calls |
| Baselines for anomalies | Sudden spikes in a tool's calls may indicate a prompt injection or runaway loop |

Implement with structured logs (tool name, duration, status, request ID), CloudWatch custom metrics, and X-Ray subsegments per tool call.

## 4. Vector Store Operations (Skill 4.3.5)

| Area | Practice |
|---|---|
| Performance monitoring | Search latency (p50/p95/p99), indexing rate, CPU/memory (OpenSearch domain metrics, Aurora Performance Insights) |
| Index optimization | Automated routines for force-merge/refresh settings, HNSW parameter review, shard rebalancing, replica tuning |
| Data quality | Validation jobs: duplicates, empty chunks, missing metadata, dimension mismatches, orphaned vectors for deleted documents |
| Freshness | Track ingestion job status and lag between source change and index update |
| Retrieval quality | Scheduled relevance tests on known queries (Module 17) |

## 5. FM-Specific Troubleshooting Frameworks (Skill 4.3.6)

GenAI fails in ways traditional ML does not: fluent but wrong output, inconsistent results for the same input, silent quality degradation after a prompt or model update, and reasoning errors.

| Technique | Purpose |
|---|---|
| **Golden datasets** | Fixed inputs with known good answers; run regularly to detect hallucination or regression |
| **Output diffing** | Compare responses across versions or repeated runs for consistency; flag large semantic differences |
| **Reasoning path tracing** | Inspect agent traces or chain-of-thought sections to locate where logic went wrong |
| Specialized observability pipelines | Stream invocation logs through Kinesis/Firehose to S3 and Athena or OpenSearch for analysis |
| Version tagging | Tag every response with model ID, prompt version, guardrail version, retrieval config |

<AccordionGroup type="single">
<AccordionItem title="Deep-Dive: Building a monitoring pipeline for invocation logs">

Enable invocation logging to S3 for durable storage and CloudWatch Logs for near-real-time queries. For analytics at scale, partition S3 by date, catalog with AWS Glue, and query with Amazon Athena. For real-time anomaly detection, add a CloudWatch Logs subscription filter to Kinesis or Lambda that extracts fields (modelId, tokens, guardrail action) and publishes custom metrics. Sample a percentage of responses for automated LLM-as-a-judge scoring and publish the scores as metrics, giving trendable quality signals without scoring every request.

</AccordionItem>
</AccordionGroup>

## 6. Exam Traps & Common Distractors

- **Trap 1:** Using only CPU/latency dashboards for a GenAI app and missing quality and token signals.
- **Trap 2:** Assuming invocation logs exist without enabling logging.
- **Trap 3:** Monitoring only the model and ignoring tools, retrieval, and the vector store.
- **Trap 4:** Setting static token thresholds when anomaly detection fits variable traffic better.
- **Trap 5:** Detecting hallucination solely with user complaints instead of golden datasets and grounding metrics.

## Self-Assessment & Exam Traps Checklist

- [ ] I can list the signals of a complete GenAI observability design.
<details>
<summary>Explanation</summary>

Operational metrics, token and cost metrics, invocation logs, distributed traces, guardrail and quality metrics, retrieval and tool metrics, business KPIs, dashboards, and alarms with anomaly detection.

</details>

- [ ] I can configure and secure Bedrock model invocation logging.
<details>
<summary>Explanation</summary>

Enable logging with a destination (S3, CloudWatch Logs, or both), grant a role, choose which data types are delivered, encrypt with KMS, restrict access, and apply retention. Treat logs as sensitive data.

</details>

- [ ] I can monitor tools and agents.
<details>
<summary>Explanation</summary>

Record per-tool call counts, errors, latency, validation failures, and agent trace steps; establish baselines and alarm on deviations such as call spikes or loops.

</details>

- [ ] I can describe FM-specific failure detection.
<details>
<summary>Explanation</summary>

Use golden datasets for hallucination and regression detection, output diffing for consistency, reasoning path traces for logic errors, and version-tagged logs to correlate quality changes with prompt, model, or retrieval changes.

</details>
