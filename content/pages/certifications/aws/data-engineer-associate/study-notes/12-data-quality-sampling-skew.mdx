## 1. Data Quality Dimensions

| Dimension | Question | Example check |
|---|---|---|
| Completeness | Are required values present? | `IsComplete "customer_id"`, empty field count |
| Uniqueness | Any duplicates? | `IsUnique "order_id"` |
| Validity | Do values conform to format/range/domain? | `ColumnValues "status" in ["NEW","PAID","SHIPPED"]`, regex on email |
| Accuracy | Do values match reality or a trusted reference? | Reconcile to source totals |
| Consistency | Do related fields/datasets agree? | Cross-table referential check, `ReferentialIntegrity` |
| Timeliness / freshness | Is data recent enough? | `DataFreshness "ts" <= 1 hours` |
| Volume / row count | Within expected range? | `RowCount between 90000 and 110000`, anomaly detection |

## 2. Data Quality in the Pipeline (Skill 3.4.1)

```
 Ingest (raw) --> [DQ gate 1: schema, row count, nulls]
        |
 Transform  --> [DQ gate 2: business rules, referential integrity]
        |
        +--pass--> Publish (curated, catalog, Redshift)
        +--fail--> Quarantine bucket + SNS alert + stop/continue per policy
```

* Check during processing: empty or null fields, type mismatches, duplicates, out-of-range values, referential integrity, freshness.
* **Actions on failure:** fail the job, route bad records to a **quarantine/error** location, publish metrics to CloudWatch, alert via SNS, and continue with good rows if tolerable.
* Implement checks in **Glue ETL** (Evaluate Data Quality transform), **Spark/PyDeequ/Great Expectations** on EMR, **Lambda** validators, **Step Functions Choice states** based on check results, **SQL assertions** in Redshift/Athena.

## 3. AWS Glue Data Quality (Skills 3.4.1, 3.4.2)

* Built on the open-source **Deequ** library; rules written in **Data Quality Definition Language (DQDL)**.
* **Rule recommendation:** Glue analyzes your data and suggests rules automatically; you can edit them.
* Runs on **Data Catalog tables** (rulesets attached to tables; scheduled or on-demand evaluation runs) or **inside Glue ETL jobs** with the *Evaluate Data Quality* transform (visual or script).
* **Outputs:** quality score, per-rule pass/fail, row-level results (flag good vs bad rows), results to S3, CloudWatch metrics, **EventBridge** events for alerting.
* **Anomaly detection** learns statistics over time and flags unusual changes.
* Dynamic rules compare against previous runs (for example `RowCount > avg(last(5)) * 0.9`).

```
Rules = [
    IsComplete "order_id",
    IsUnique "order_id",
    ColumnValues "status" in ["NEW","PAID","SHIPPED","CANCELLED"],
    ColumnValues "amount" > 0,
    Completeness "customer_email" > 0.95,
    RowCount between 90000 and 110000,
    DataFreshness "updated_at" <= 24 hours,
    ReferentialIntegrity "customer_id" "ref.customers.customer_id" = 1.0
]
```

```python
# Glue job: evaluate rules and split good/bad rows
from awsgluedq.transforms import EvaluateDataQuality
dq = EvaluateDataQuality().process_rows(
    frame=orders_dyf,
    ruleset=ruleset,
    publishing_options={"dataQualityEvaluationContext": "orders_dq",
                        "enableDataQualityCloudWatchMetrics": True,
                        "enableDataQualityResultsPublishing": True},
    additional_options={"performanceTuning.caching": "CACHE_NOTHING"})
good = dq["rowLevelOutcomes"].filter(lambda r: r["DataQualityEvaluationResult"] == "Passed")
```

## 4. DataBrew: Quality Rules and Consistency (Skills 3.4.2, 3.4.3)

* **Profile jobs** compute statistics: missing/duplicate counts, distinct values, min/max, distribution, correlations, outliers; sample size configurable (full dataset or sample).
* **Data quality rulesets** (checks like column not null, value in range, unique, duplicates, row count) attached to a dataset and evaluated in profile jobs; **validation reports** in S3.
* **Investigate consistency:** compare columns and distributions across datasets, find inconsistent formats (dates, casing), standardize with recipe steps (format date, change case, replace values, fuzzy match), and **detect and handle outliers**.
* Output a cleaned dataset with a reusable recipe.

<AccordionGroup type="single">
<AccordionItem title="Deep-Dive: Sampling techniques (Skill 3.4.4)">

Sampling analyzes a representative subset when full scans are too slow or costly.

| Technique | Method | Use when |
|---|---|---|
| **Simple random** | Every row equally likely | Uniform data, quick profiling |
| **Systematic** | Every k-th row | Ordered data, low overhead (watch periodic patterns) |
| **Stratified** | Sample within each group in proportion | Preserve rare categories/segments |
| **Cluster** | Randomly pick whole groups, use all rows inside | Partitioned storage, cost-driven |
| **Reservoir** | Fixed-size sample from a stream of unknown length | Streaming profiling |
| **Head/limit (not a true sample)** | First N rows | Fast peek only; can be biased |

AWS touchpoints: DataBrew **sample size** and **sampling** settings; Spark `df.sample(fraction, seed)` / `sampleBy`; Athena `TABLESAMPLE BERNOULLI(10)` / `SYSTEM(10)`; Redshift `RANDOM() < 0.1`; Glue Data Quality sampling for faster evaluation.

Watch out for bias, rare event loss, and non-reproducible samples (set a seed).

</AccordionItem>
<AccordionItem title="Deep-Dive: Data skew mechanisms (Skill 3.4.5)">

**Skew** = uneven distribution of data across partitions/nodes/keys, causing straggler tasks and hot shards.

| Where | Symptom | Mitigation |
|---|---|---|
| Spark/Glue/EMR | One task much slower, executor OOM, long tail in Spark UI | **Salting** (append random suffix to hot keys, aggregate in two stages), **repartition** on a better key, **broadcast join** the small side, enable **Adaptive Query Execution** (`spark.sql.adaptive.skewJoin.enabled`), filter or isolate null/hot keys |
| Redshift | Uneven rows per slice (`SVV_TABLE_INFO.skew_rows`), slow queries | Choose a higher-cardinality **distribution key**, use `EVEN`/`AUTO`, `ALL` for small dimensions |
| Kinesis / MSK | Hot shard/partition, throttling on one shard | Higher-cardinality partition key, random suffix, more shards, on-demand |
| DynamoDB | Hot partition throttling | High-cardinality partition key, write sharding, on-demand, adaptive capacity |
| Athena/S3 | Skewed partitions (one giant partition) | Repartition by additional column, bucketing |
| Time-based skew | Today's partition huge, older tiny | Add secondary partition key (hour), compaction |

</AccordionItem>
</AccordionGroup>

## 5. Common Traps and Watchouts

* **"Define and run quality rules on Data Catalog tables, minimal code"** → Glue Data Quality (DQDL).
* **"Visual profiling and rules for analysts"** → DataBrew.
* **"Bad records must not block good ones"** → row-level outcomes with quarantine.
* **"Alert when quality fails"** → EventBridge/CloudWatch → SNS.
* **Adding nodes does not fix skew;** fix the key or use salting.
* **`LIMIT`/head is not random sampling.**
* **Referential integrity constraints in Redshift are informational;** enforce with checks.
* **Idempotent re-runs** are required after fixing bad data.

## Self-Assessment & Exam Traps Checklist

- [ ] I can write DQDL rules for completeness, uniqueness, validity, and freshness.
<details>
<summary>Explanation</summary>

Use `IsComplete`, `IsUnique`, `ColumnValues ... in [...]`/range comparisons, `Completeness ... > 0.95`, `RowCount between ...`, `DataFreshness ... <= 24 hours`, and `ReferentialIntegrity` for cross-table checks.

</details>

- [ ] I can place quality gates and describe failure handling.
<details>
<summary>Explanation</summary>

Gate after ingestion (schema, volume) and after transformation (business rules). On failure: stop or quarantine bad rows, emit metrics/events, notify via SNS, and keep the raw layer for reprocessing.

</details>

- [ ] I can choose Glue Data Quality vs DataBrew.
<details>
<summary>Explanation</summary>

Glue Data Quality for code/pipeline-integrated, scalable rules (DQDL, recommendations, anomaly detection). DataBrew for visual profiling, rulesets, and recipe-based cleaning by analysts.

</details>

- [ ] I can match a sampling technique to a scenario.
<details>
<summary>Explanation</summary>

Stratified to preserve rare groups, reservoir for streams, simple random for uniform data, systematic for ordered cheap sampling, cluster when sampling whole partitions is cheaper.

</details>

- [ ] I can recognize and fix skew in Spark, Redshift, Kinesis, and DynamoDB.
<details>
<summary>Explanation</summary>

Spark: salting, broadcast joins, AQE, repartition. Redshift: better dist key or EVEN/AUTO. Kinesis/DynamoDB: high-cardinality or sharded keys. Skew is a key-distribution problem, not a capacity problem.

</details>
