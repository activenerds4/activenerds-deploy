## Objective 2.1: Configure vSphere Supervisor Capabilities, Services, and Architecture Topologies


<AccordionGroup type="single">
<AccordionItem title="Deep-Dive: The Supervisor 5-IP Subnet Requirement Explained">

When enabling Workload Management (Supervisor) on a vSphere cluster, the wizard prompts for a contiguous CIDR or IP range. A recurring exam gotcha asks how many IPs are required.

The exact answer is **5 consecutive IP addresses**:

* **IP 1**: Supervisor Control Plane VM 01 (Management interface)
* **IP 2**: Supervisor Control Plane VM 02 (Management interface)
* **IP 3**: Supervisor Control Plane VM 03 (Management interface)
* **IP 4**: Floating Management IP — dynamic virtual IP bound to the active **etcd leader** node (note: this is for Kubernetes API management, distinct from the Workload Load Balancer VIP)
* **IP 5**: Temporary Rolling Upgrade / Patching Buffer IP — reserved so SDDC Manager can provision a temporary 4th node during zero-downtime control-plane upgrades before retiring the old node.

</AccordionItem>

<AccordionItem title="Deep-Dive: NSX Projects & VPCs in VCF 9 Kubernetes Tenancy">

In VCF 9, NSX introduces native **Projects and Virtual Private Clouds (VPCs)**:

* Previously, enabling a vSphere Namespace with NSX created a Tier-1 gateway and distributed routing configuration directly in the global NSX Manager space.
* With **NSX VPCs**, each development team or business unit is mapped to an **NSX Project**.
* When a vSphere Namespace is created, NSX automatically provisions a dedicated VPC with private subnets, NAT, and automated distributed firewall policies.
* This isolates networking configuration, eliminates global routing table bloat, and provides granular IPAM delegation to Kubernetes administrators.

</AccordionItem>

</AccordionGroup>


**What the Supervisor is:** a Kubernetes control plane built into vSphere. Activating a Supervisor on a cluster (or vSphere Zones) lets you run workloads declaratively: vSphere Pods, VM Service VMs, VKS clusters, and Supervisor Services, all scoped by vSphere Namespaces.

### Supervisor components

| Component | Role |
|---|---|
| **Supervisor control plane VMs** | 1 or 3 VMs (3 recommended/required for HA and mandatory on 3 zones). Each has its own IP; a **floating IP** is assigned to one VM (it follows the etcd leader), and a **5th IP** is reserved for patching - hence the required **block of 5 consecutive IPs** |
| **VKS + Cluster API** | Modules on the Supervisor that provision and lifecycle-manage VKS clusters |
| **Virtual Machine Service** | Declarative VM API; introduces **VM classes** (reusable hardware definitions); also builds the node VMs of VKS clusters |
| **Spherelet** | A kubelet ported natively to ESX; makes each host part of the Kubernetes cluster (for vSphere Pods) |
| **CRX (Container Runtime Executive)** | MicroVM with a paravirtualized Linux kernel using direct boot; the runtime boundary for vSphere Pods |

### Topologies

| Topology | Placement | HA |
|---|---|---|
| **Single zone** | One vSphere cluster | Host-level HA |
| **Three vSphere Zones** | Three clusters, one per zone; control plane VM in each zone | Cluster-level HA; control plane HA is **mandatory**; namespace resources drawn equally from all three clusters |

- Control plane VM sizing at activation: **Tiny** (2 CPU / 8 GB), **Small** (4 / 16 GB), **Medium** (8 / 16 GB), **Large** (16 / 32 GB), 32 GB storage each. **You can only scale up, never down.**
- A **vSphere Namespace** is the tenancy boundary: RBAC, resource limits, storage policies, VM classes, and content libraries are all set per namespace. Three runtimes are consumed through it: VMs, VKS clusters, vSphere Pods.

### Supervisor Services

| Aspect | Key points |
|---|---|
| **What** | Platform services (e.g., Harbor, Contour, ExternalDNS) installed on Supervisors, distributed as **service definition YAML + data values YAML** downloaded from the Broadcom support portal |
| **Lifecycle** | Add service to vCenter -> install a version on a Supervisor; a newer version **overrides** the older one; **only one version per Supervisor at a time**; deactivated versions cannot be installed |
| **Prechecks** | Compatibility prechecks run at install: **warnings** can be acknowledged and skipped; **errors** block installation. VCF 9.0 prechecks also verify the publisher identity of each service version |
| **Registry dependency** | A **regional Harbor** (installed through VCF Automation) is the central registry for Supervisor Services, VCF CLI plugins, and VKS standard packages |

**Key takeaways**
- Three control plane VMs are load balanced, but the **floating IP identifies the current etcd leader** - it is not a load-balancer VIP.
- Exam trap: 5 IPs for the control plane (3 VMs + 1 floating + 1 patching buffer), not 3 and not 4.
- Zones: exactly 3, one cluster each; management zones can be reserved for the control plane, and a namespace can use 1-3 different zones for isolation.
- Supervisor Services are **versioned, signed packages**, not random Helm charts; install/uninstall happens from Supervisor Management → Services in the vSphere Client with the *Manage Supervisor Services* privilege.

## Objective 2.2: Configure Supervisor Cluster Networking with VDS, NSX Segments, or VPCs and Apply Appropriate Load Balancing Solutions

| Decision point | VDS networking | NSX Segments | VCF Networking with VPC |
|---|---|---|---|
| **Workload network** | Distributed port groups assigned to namespaces; the one serving the Supervisor control plane is the **Primary Workload Network** (one per Supervisor, mandatory) | NSX segments per namespace; NCP creates a **shared T1 for system namespaces** and a **T1 + load balancer per namespace** | NSX VPCs in projects; a VPC per namespace (auto-created in the default project if not specified), plus a **system namespace VPC** and a **Supervisor Services VPC** created by NCP |
| **North-south** | External LB VIPs (Avi data network or FLB) | T0 gateway (BGP or static); **SNAT per namespace** from the egress pool | Centralized Transit Gateway on NSX Edge nodes for full NSX service access; VPC subnet access modes: **Private**, **Public (external)**, **Private TGW** |
| **Load balancer options** | **Foundation Load Balancer** or **Avi** | **NSX LB** or **Avi** | **NSX (Edge) LB** or **Avi** - and the VPC must use the **same LB as the Supervisor** |
| **Best for** | No NSX / simple VLAN environments | Classic NSX overlay isolation | VCF 9 default; full VCF Automation self-service |

### Load balancer choices

| LB | Layer | Notes |
|---|---|---|
| **Foundation Load Balancer** | L4 only | **Ships with vCenter**; deployed during Supervisor activation; **VDS only**; not for VPC or NSX segment networking; 1-2 VMs (active/standby with two); in a multi-zone Supervisor its VMs sit only on the first management zone |
| **NSX Load Balancer** | L4 | Embedded/T1 LB; one small LB instance per VKS cluster for its API server; one virtual server per LoadBalancer service |
| **Avi Load Balancer** | L4 + L7, WAF | Controller (control plane) + **Service Engines** (data plane VMs, first SE created only when the first virtual service exists; up to **1000 virtual services per SE**) + **AKO** (Avi Kubernetes Operator, installed on the Supervisor) |

**Key takeaways**
- The management network and workload network **must be different subnets** - same subnet is unsupported and causes errors.
- With NSX, workloads in the same namespace **share one SNAT IP**; east-west between namespaces needs no SNAT.
- Avi requirements: Controller gets a static IP (4 for a 3-node cluster: 3 + cluster VIP); SE management NIC on the Management Network, data NICs on the Data Network where VIPs live; SEs can use DHCP if available.
- **vSphere Pods require NSX-based networking** - on a VDS-only Supervisor you cannot run vSphere Pods (a frequent exam trap).
- DHCP for the management network is supported (must support client identifiers; control plane IPs cannot change), but **DHCP on workload networks is not supported with Supervisor Services on the VDS stack** - use static IPs there.

## Objective 2.3: Configure Supervisor Storage Policies and Persistent Volume Integration Across Zones

| Concept | Behavior |
|---|---|
| **Storage policy -> StorageClass** | Assigning a vSphere storage policy to a namespace creates a matching Kubernetes StorageClass, replicated to VKS clusters in that namespace. One policy = one StorageClass |
| **Binding modes** | Each StorageClass has two editions: **Immediate** and **WaitForFirstConsumer** (late binding). Late binding is used for topology-aware placement (e.g., StatefulSets spread across zones) |
| **Multi-zone requirement** | On a zoned Supervisor, namespaces must use **topology-aware storage policies**; non-topology-aware policies cannot be assigned |
| **Provisioning chain** | PVC in the VKS cluster -> **pvCSI** (in-cluster, uses a service account, no infra credentials) -> **CNS-CSI** on the Supervisor -> **CNS** in vCenter -> First Class Disk on a policy-compliant datastore |
| **Volume types in vSphere Pods** | Ephemeral VMDKs, persistent volume VMDKs, container image VMDKs; image cache + ephemeral placement policies are set when enabling the Supervisor, PV placement at namespace level |

**Key takeaways**
- Storage is **policy-driven end to end**: DevOps never touches datastores; they pick a StorageClass.
- A PVC created in the VKS cluster generates a matching PVC on the Supervisor; the bound PV/PVC pair is visible in both layers.
- Control plane VM placement, container image cache, and ephemeral disks each take a storage policy **at Supervisor activation** - a common exam detail.
- Datastores for expansion: VMFS, vSAN, vSAN Direct, vVols, NFS all support volume expansion.

## Objective 2.4: Configure VKS Identity and Access Using External Providers and Kubernetes Admin Credentials

| Method | How it works |
|---|---|
| **vCenter Single Sign-On** | Default; users/groups from SSO identity sources get namespace roles via vSphere permissions |
| **External OIDC identity provider** | Register the IDP once on the Supervisor (Supervisor Management → Supervisors → Configure → Identity Providers); **all VKS clusters on that Supervisor are automatically configured** with it. Requires Client ID, Client Secret, Issuer URL; optional Username Claim, Groups Claim, additional scopes, CA data |
| **Pinniped** | The authentication machinery: **Pinniped Supervisor + Concierge run on the Supervisor; only Concierge runs on VKS cluster nodes**. Registration updates all of them |
| **CLI login** | VCF CLI (with the VKS cluster plugin) or `kubectl vsphere` login; `vcf context use <cluster>` switches context |
| **Kubernetes admin credentials** | Every cluster has a `<cluster>-kubeconfig` Secret in its namespace on the Supervisor. Decode it (`kubectl get secret <name>-kubeconfig -o jsonpath='{.data.value}' \| base64 -d`) to connect directly as **kubernetes-admin**, bypassing SSO |

**Key takeaways**
- External IDP must support **OIDC**; the IDP is configured with the Supervisor's **callback URL** beforehand.
- The admin kubeconfig path is the break-glass option when SSO/IDP login fails - know where the secret lives (the namespace hosting the cluster, on the Supervisor context).
- Permissions on namespaces are vSphere permissions (View/Edit/Owner); inside VKS clusters you additionally have Kubernetes RBAC.

## Objective 2.5: Manage Kubernetes Releases and Content Libraries (Subscribed, Local, and Air-Gapped) for VKS Clusters

| Concept | Key points |
|---|---|
| **vSphere Kubernetes release (VKr)** | The signed, supported Kubernetes distribution for VKS clusters: Photon/Ubuntu OS + VKS core components (Antrea, Calico, etc.), shipped as an **OVA**; versioned to match Kubernetes; released **independently of vCenter** |
| **Subscribed content library** | Points at the publication URL (Software Depot `.../PROD/COMP/VKR/lib.json`, or the Broadcom public CDN `https://wp-content.broadcom.com/v2/latest/lib.json`). Sync modes: **Immediately** (metadata + images; deleted items linger locally) or **When needed** (metadata only, images fetched on publish/use - recommended to save storage). SSL thumbprint must be accepted |
| **Local content library (air-gapped)** | For internet-restricted environments: create a local library, download VKr OVA files manually, import them. **OVF default policy** is the only supported security policy; failing templates get the `Verification Failed` tag and their OVF files cannot sync |
| **Consumption** | `kubectl get kr` / `kubectl get kubernetesreleases` lists usable releases and Supervisor compatibility. The content library must be **associated with the Supervisor** |
| **Rolling update interaction** | Adding new VKr images does **not** trigger rolling updates; **switching the cluster to a different content library with differently-named images does** |

**Key takeaways**
- Exam trap: "which library type for an air-gapped site?" - **local**, not subscribed.
- You can only use releases returned by `kubectl get kr`; missing release = library not synced or not associated with the Supervisor.
- VKr naming is upstream-aligned: e.g., v1.28.x+vmware.y.

## Objective 2.5 (second listing - treated as 2.6): Configure CNIs, NSX Networking Objects, and TLS Certificates and Secure VKS Clusters

### CNI options

| CNI | Data plane | Notes |
|---|---|---|
| **Antrea (default)** | Open vSwitch | Default for new clusters; no need to specify in YAML |
| **Calico** | Linux bridge + BGP (iptables for policy) | Specify in cluster YAML or change the Supervisor default CNI |
| **Antrea NSX Routed** | NSX integration | Routable pod networking (pods reachable directly) |

### NSX objects created per VKS cluster (NSX networking)

| Object | Count / mapping |
|---|---|
| Tier-1 gateway + linked segment | One per cluster (node network); SNAT IP assigned |
| NSX load balancer (small) | One per cluster: virtual server for the API server on **port 8443** + server pool of the control plane nodes, plus HTTP/HTTPS ingress virtual servers |
| LoadBalancer services | One virtual server + server pool per service; external IP from the ingress pool |
| SNAT rules on T0 | One per namespace (and per cluster in NAT topology) using Floating IP pool addresses |
| DFW rules | For kube-dns (CoreDNS port) and the validator pod |

### TLS certificates

| Scope | Signer | Rotation |
|---|---|---|
| **Supervisor** | VMCA (vCenter trust domain) | **Automated since vSphere 8 U3**; manual (WCP Cert Manager tool) before that |
| **VKS cluster** | Kubernetes CA (Kubernetes trust domain) | **Automatic during rolling updates**; manual rotation by patching the KubeadmControlPlane (`rolloutAfter`), which rolls control plane nodes; kubelet certs rotate by default (`rotateCertificates: true`) |

**Pod security:** VKr 1.25+ uses **Pod Security Admission (PSA)**; VKr 1.24 and earlier use Pod Security Policies (PSP). Know which applies by release.

**Key takeaways**
- The VKS cluster API server endpoint is served on the cluster's LB virtual server on **port 6443/8443 depending on stack** - for NSX it is 8443 on the NSX LB.
- Cluster cert rotation = trigger a rolling update; Supervisor cert rotation = platform-managed (automated in current releases).
- Trusting private registries is done through cluster **trust variables / additional trusted CA certificates** in the cluster spec - not by editing nodes.

## Quick Recall Sheet

- Supervisor components: **control plane VMs (1 or 3, 5 IPs, floating IP = etcd leader), VKS+Cluster API, VM Service, Spherelet, CRX**.
- Control plane sizes: Tiny 2/8, Small 4/16, Medium 8/16, Large 16/32 - **scale up only**.
- Namespace = tenancy boundary: RBAC + limits + storage policies + VM classes + content libraries.
- Networking: **VPC (VCF 9 default) / NSX segments / VDS**; LB: **FLB (VDS only), NSX LB, Avi (SE max 1000 VS)**; VPC must match the Supervisor's LB.
- **vSphere Pods need NSX**; VDS = no pods. Mgmt and workload networks must be different subnets.
- Storage: policy -> StorageClass (Immediate + WaitForFirstConsumer editions); multi-zone = topology-aware policies; pvCSI -> CNS-CSI -> CNS.
- Identity: SSO default; external **OIDC** via Pinniped (Supervisor+Concierge on Supervisor, Concierge only on clusters); break-glass = `<cluster>-kubeconfig` secret.
- VKr = OVA-based K8s distribution; **subscribed** library (immediate vs when-needed sync) vs **local** library (air-gapped, OVF default policy).
- CNI: **Antrea default**, Calico optional, Antrea NSX Routed for routable pods. NSX per cluster: T1+segment, small LB (API on 8443), SNAT per namespace.
- TLS: Supervisor = VMCA (auto-rotation since 8 U3); VKS clusters = K8s CA, rotated by rolling updates; PSA for VKr 1.25+, PSP before.
