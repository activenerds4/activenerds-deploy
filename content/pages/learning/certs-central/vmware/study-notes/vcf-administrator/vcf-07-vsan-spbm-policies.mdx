## vSAN Storage Policy-Based Management (SPBM)

→ **Architecture note.** vSAN comes in two architectures: the **Original Storage Architecture (OSA)**, which uses disk groups (cache + capacity), and the **Express Storage Architecture (ESA)**, which uses a single-tier storage pool of NVMe devices. SPBM works the same way conceptually in both, but **minimum host counts and erasure-coding behavior differ**, and the exam may test that difference. This guide labels each fact as OSA, ESA, or both. Host-count and default-policy details evolve between releases, so confirm against the current VCF/vSAN documentation and your exam guide.

---

## 1. Learning Objectives

After this module you should be able to:

- Explain what **SPBM** is and how a policy translates into object placement.
- Select the correct **FTT** and **failure tolerance method** (RAID-1, RAID-5, RAID-6) for a requirement.
- Calculate **minimum hosts** and **capacity overhead** for each option (OSA and ESA).
- Describe other vSAN policy rules: stripe width, space reservation, IOPS limit, encryption, site disaster tolerance, and others.
- Assign and change policies at the VM, disk, and datastore-default levels, and explain **compliance** and **resync**.
- Describe how policies are scoped and managed across **VCF workload domains**.

## 2. SPBM Fundamentals

**Storage Policy-Based Management** is the vSphere framework that lets you declare *what* a workload needs (availability, performance, space efficiency, security) rather than *where* to put it.

How it works:

1. The administrator creates a **VM storage policy** in vCenter containing **rules**.
2. The policy is **assigned** to a VM, a virtual disk, or set as a datastore default.
3. vSAN reads the rules and **places the object's components** across hosts/fault domains to satisfy them.
4. vCenter continuously checks **compliance** and reports the result.

### 2.1 vSAN objects

Every VM on vSAN is stored as a set of **objects**, each with its own policy applicable:

| Object | Content |
|---|---|
| **VM home namespace** | VMX, logs, config files |
| **Virtual disk (VMDK)** | Disk data |
| **VM swap** | Swap file (created at power-on) |
| **Snapshot delta** | Snapshot data |
| **Memory snapshot** | Optional memory state |

Each object is split into **components** (replicas, stripes, and **witness** components). Witnesses are small metadata components used to establish **quorum** (more than 50% of votes) so vSAN can decide which side is authoritative after a failure.

### 2.2 Why SPBM matters

- **Per-VM and per-disk** granularity: a database VMDK can use RAID-1 while its log or scratch disk uses RAID-5.
- **Policy changes are non-disruptive**: vSAN reconfigures objects in the background (a **resync**).
- **Compliance is continuous**, so a host failure or capacity shortage can flip an object to non-compliant.

## 3. Failures to Tolerate (FTT) and Failure Tolerance Method

The **Failures to Tolerate (FTT)** rule defines how many host/device failures an object can survive and remain accessible. Together with the **Failure Tolerance Method (FTM)**, it decides *how* redundancy is built.

### 3.1 FTT levels

| FTT | Meaning |
|---|---|
| **0** | No redundancy: one copy. Any failure of the hosting component loses data access. Use only for workloads that provide their own protection (or disposable data), and note that vSAN will flag it as having no protection |
| **1** | Survive one failure |
| **2** | Survive two simultaneous failures |
| **3** | Survive three failures (RAID-1 only) |

### 3.2 Failure Tolerance Method (FTM)

| FTM | How it protects | Optimized for |
|---|---|---|
| **RAID-1 (Mirroring)** | Full copies of the data on different hosts plus witnesses | **Performance** (simple I/O path, fast rebuild); higher capacity cost |
| **RAID-5 (Erasure coding)** | Data plus **single parity** striped across hosts | **Capacity efficiency** with FTT=1 |
| **RAID-6 (Erasure coding)** | Data plus **double parity** striped across hosts | **Capacity efficiency** with FTT=2 |

→ **Key relationship:** **RAID-5 = FTT 1**, **RAID-6 = FTT 2**. You cannot select RAID-5 for FTT=2 or RAID-6 for FTT=1. FTT=3 is available only with RAID-1 mirroring.

### 3.3 Minimum hosts and capacity overhead

#### RAID-1 (Mirroring), both OSA and ESA

| FTT | Copies | Min. hosts (fault domains) | Capacity overhead |
|---|---|---|---|
| 1 | 2 replicas + 1 witness | **3** | **2x** (100% extra) |
| 2 | 3 replicas + 2 witnesses | **5** | **3x** |
| 3 | 4 replicas + 3 witnesses | **7** | **4x** |

Formula: **hosts needed = 2 x FTT + 1**.

#### Erasure coding

| Method | FTT | OSA minimum hosts | ESA minimum hosts | Capacity overhead |
|---|---|---|---|---|
| **RAID-5** | 1 | **4** (3 data + 1 parity) | **3** (2 data + 1 parity, adaptive) | OSA **1.33x**; ESA **1.5x** at 3-5 hosts, **1.25x** at 6+ hosts (4+1) |
| **RAID-6** | 2 | **6** (4 data + 2 parity) | **6** (4 data + 2 parity) | **1.5x** |

Key points:

- **OSA erasure coding requires an all-flash cluster.** It is not available on hybrid (flash cache + magnetic capacity) configurations.
- **ESA** erasure coding is built for performance parity with mirroring, so the traditional "performance vs capacity" trade-off is much smaller. ESA also adapts the RAID-5 layout to cluster size (the 2+1 layout on small clusters, 4+1 on larger).
- In OSA, parity writes add I/O amplification, so write-heavy, latency-sensitive workloads historically stayed on RAID-1.
- **Exam habit:** compute **raw capacity needed = usable VM data x overhead factor**, and always keep **slack space** for rebuilds and policy changes.

### 3.4 Quick example

A 500 GB VMDK with:

- **RAID-1, FTT=1** consumes about **1,000 GB** raw.
- **RAID-5, FTT=1 (OSA)** consumes about **667 GB** raw.
- **RAID-6, FTT=2** consumes about **750 GB** raw.
- **RAID-1, FTT=2** consumes about **1,500 GB** raw.

(With thin provisioning, consumption grows only as data is written.)

### 3.5 Why host count matters beyond the minimum

- Minimum hosts let you **create** the object compliantly, but failures can remove a host and leave no place to **rebuild** components.
- To **self-heal** after a failure, you need **extra hosts beyond the minimum** (one more host than the minimum is the common design rule), plus **free capacity**.
- **Maintenance mode** with *Ensure accessibility* may leave objects temporarily non-redundant; with FTT=1 on exactly 3 hosts, there is nowhere to re-protect during maintenance.
- This is why VCF designs start with **4 hosts** for the management domain: it supports FTT=1 mirroring and still allows evacuation and rebuild.

## 4. Other Important vSAN Policy Rules

| Rule | Purpose | Notes |
|---|---|---|
| **Site disaster tolerance** | For **stretched clusters**: *None*, *Dual site mirroring*, *None - keep data on Preferred/Secondary*, etc. | Combined with FTT for protection **within** each site |
| **Stripe width** (number of disk stripes per object) | Spreads an object across more capacity devices to improve performance | Default **1**; raising it rarely helps and increases component count |
| **Object space reservation** | **Thin** (0%, default) up to **thick** (100%) | Reserves capacity up front |
| **Flash read cache reservation** | Reserves cache for reads | **OSA hybrid only** |
| **IOPS limit** | Caps IOPS per object (normalized to 32 KB) | Noisy-neighbor control |
| **Checksum disable** | Turns off end-to-end checksum | Checksums are **on** by default; disable only with justification |
| **Encryption** | Data-at-rest encryption options (via KMS/key provider), or data-in-transit | Configured at cluster level; policy can include encryption rules |
| **Force provisioning** | Allows creation even if the policy cannot be met | Object is created **non-compliant**; avoid in production |
| **Space efficiency (compression/dedup)** | OSA: **cluster-level** dedup and compression (all-flash). **ESA: compression is policy-driven (per object)** | Know the OSA/ESA difference |

**Component limits to remember:** maximum component size is **255 GB**, so large VMDKs are split into multiple components automatically.

## 5. Policy Assignment

### 5.1 Where a policy can be applied

| Level | How |
|---|---|
| **Per VM (VM home)** | Edit VM Storage Policy or set during deployment |
| **Per virtual disk** | Different policy per VMDK |
| **Datastore default** | A **default storage policy** set on the vSAN datastore applies to new VMs that don't specify one |
| **Templates, content library, and automation** | Policies can be selected in clone/deploy workflows and by automation tools |

### 5.2 The default policy

- vSAN provides a **vSAN Default Storage Policy** (typically **FTT=1, RAID-1, stripe width 1, thin provisioned**).
- On ESA, newer versions can also surface **ESA-specific default policies** (for example, RAID-5/RAID-6 based) and, in some releases, an **auto-policy** that is selected based on cluster size. Treat this as release-specific and verify.
- **Do not edit the default policy** casually; create custom policies instead so the default stays predictable.

### 5.3 Compliance states

| State | Meaning |
|---|---|
| **Compliant** | Object satisfies the policy |
| **Noncompliant** | Cannot meet policy (insufficient hosts/capacity, failed component) |
| **Out of date / Reapply required** | Policy was edited; objects must be reapplied to pick up changes |
| **Unknown** | vCenter cannot determine the state |

### 5.4 Changing a policy: resync and capacity

- Changing a policy (for example, RAID-1 to RAID-5) creates **new component layouts** and **resyncs** data; **temporary extra capacity** is required while both layouts exist.
- Ensure adequate free space (commonly recommended **25-30% slack**) before large policy changes.
- vSAN throttles resync traffic to protect VM performance; large resyncs can take hours.
- Monitor in **vSAN → Monitor → Resyncing Objects**.

### 5.5 Policy compatibility check

- When you choose a policy, vCenter shows **compatible** and **incompatible** datastores.
- A vSAN datastore appears **incompatible** if the cluster **doesn't have enough hosts/fault domains** for the rules (for example, RAID-5 on OSA with only 3 hosts).

## 6. SPBM in VCF Workload Domains

### 6.1 Scope and ownership

- A **VM storage policy is a vCenter construct.** Each VCF domain (management domain and each VI workload domain) has its **own vCenter**, so policies are **created and managed per domain**. They are **not shared automatically** across domains.
- VCF **builds the cluster and vSAN datastore** and applies the **default vSAN policy**; you then define **custom policies in the domain's vCenter** for workload needs.
- Structural changes (adding hosts/clusters, lifecycle, domain creation) go through VCF tooling (SDDC Manager in VCF 5.x; VCF Operations / VCF Installer in VCF 9). **Day-2 workload policy design (RAID level, FTT, IOPS limits)** is done in **vCenter**.
- Because workload domains frequently use **different cluster sizes and hardware**, the **same policy name may need different settings** in each domain, so keep naming consistent but validate the host-count fit.

### 6.2 Design guidance by domain type

| Domain / cluster | Typical guidance |
|---|---|
| **Management domain** (4+ hosts) | Keep the **default FTT=1 RAID-1** (or the ESA equivalent). Don't change policies on VCF-managed management VMs (vCenter, NSX Manager, SDDC Manager) without supported guidance |
| **VI workload domain, 4-5 hosts** | RAID-1 FTT=1 for latency-sensitive; RAID-5 FTT=1 for capacity (OSA all-flash needs 4; ESA needs 3) |
| **VI workload domain, 6+ hosts** | RAID-6 FTT=2 for critical data; ESA gets better RAID-5 efficiency |
| **Stretched cluster** | Site disaster tolerance (dual-site mirroring) plus secondary FTT within sites; requires a **witness host** |
| **Remote/edge or ROBO** | Smaller clusters (2-node with witness) rely on RAID-1 |

### 6.3 Sample policy catalog

| Policy name | FTT / FTM | Other rules | Use case |
|---|---|---|---|
| `VCF-Gold-R6` | FTT=2, RAID-6 | Checksum on, thin | Tier-1 databases, 6+ hosts |
| `VCF-Silver-R5` | FTT=1, RAID-5 | Thin | General-purpose capacity-efficient workloads |
| `VCF-Perf-R1` | FTT=1, RAID-1 | Thin | Latency-sensitive OLTP (OSA) |
| `VCF-Scratch-R0` | FTT=0 | Thin | Disposable/test data protected at app layer |
| `VCF-Stretched` | Dual-site mirroring + FTT=1 | Witness required | Site-resilient workloads |
| `VCF-NoisyLimit` | FTT=1 | IOPS limit | Cap noisy neighbors |

### 6.4 Operational workflow

1. **Assess** workload requirements (RPO/availability, performance, capacity).
2. **Verify** the cluster size and architecture (OSA or ESA) against the policy's host minimums.
3. **Create** the policy in the domain's vCenter (*Policies and Profiles → VM Storage Policies*).
4. **Check compatibility** (the datastore must be listed as compatible).
5. **Assign** to VM/disks (or set as datastore default).
6. **Verify compliance** and monitor any resync.
7. **Document** policies per domain and standardize naming.
8. **Review capacity** before bulk policy changes or after host loss.

## 7. Exam Tips

1. **Memorize the host-count rules.** RAID-1: **2n+1** hosts. **RAID-5 = 4 hosts (OSA) / 3 hosts (ESA)**. **RAID-6 = 6 hosts** (both).
2. **RAID-5 pairs with FTT=1, RAID-6 with FTT=2.** FTT=3 is only RAID-1.
3. **Capacity overhead:** RAID-1 FTT=1 = **2x**; RAID-1 FTT=2 = **3x**; RAID-5 (OSA) = **1.33x**; RAID-6 = **1.5x**.
4. **OSA erasure coding requires all-flash.** Hybrid clusters can only use mirroring.
5. **ESA is the performance-friendly erasure coding architecture**; if the question mentions ESA, expect RAID-5/6 to be a sound default.
6. **Policy changes cause resync and need temporary free space.** If a question mentions capacity exhaustion during a policy change, think slack space.
7. **Force provisioning creates non-compliant objects.** It is a workaround, not a design.
8. **Policies belong to vCenter, so they are per-domain in VCF.** Don't assume a policy in one workload domain exists in another.
9. **Compliance vs availability:** a non-compliant object can still be *accessible*; read the scenario carefully.
10. **Default policy = FTT=1, RAID-1, stripe 1, thin.** Don't confuse stripe width with FTT.
11. **Witness components** provide quorum; stretched clusters add a **witness host/appliance** at a third site.
12. **Self-healing needs extra hosts and capacity** beyond the minimum; "minimum hosts" means *can create*, not *can rebuild*.
13. **Don't change policies on VCF-managed management VMs** unless supported documentation says so.

## 8. Practice Questions

### Question 1

A VCF VI workload domain has a **5-host vSAN OSA all-flash cluster**. An administrator wants a policy that tolerates **one host failure** while minimizing raw capacity consumption. Which configuration should they choose?

- **A.** FTT=1, RAID-1 (Mirroring)
- **B.** FTT=1, RAID-5 (Erasure Coding)
- **C.** FTT=2, RAID-6 (Erasure Coding)
- **D.** FTT=0, RAID-1

<details>
<summary>Answer and explanation</summary>

**Correct: B.**
RAID-5 with FTT=1 tolerates one failure and uses about **1.33x** capacity (versus 2x for RAID-1). It needs **4 hosts on OSA**, and all-flash is satisfied, so 5 hosts is sufficient (with one spare host for rebuilds).
- **A** works but uses about 2x capacity.
- **C** requires **6 hosts** on vSAN, which this cluster does not have.
- **D** provides no redundancy.

</details>

### Question 2

An administrator creates a policy with **FTT=2 using RAID-1 (Mirroring)** and applies it to a VM in a **4-host cluster**. The vSAN datastore is shown as **incompatible**. What explains this?

- **A.** FTT=2 with RAID-1 requires 5 hosts, but only 4 are available
- **B.** RAID-1 can only be used with FTT=1
- **C.** Stripe width must be raised to 2 for FTT=2
- **D.** Encryption is not enabled on the cluster

<details>
<summary>Answer and explanation</summary>

**Correct: A.**
RAID-1 requires **2 x FTT + 1** hosts. For FTT=2 that is **5 hosts**; a 4-host cluster cannot satisfy it, so the datastore is flagged incompatible.
- **B** is wrong: RAID-1 supports FTT=1, 2, and 3.
- **C** is wrong: stripe width is a performance setting, not an availability setting.
- **D** is irrelevant to host-count compatibility.

</details>

### Question 3

A team applies a new, more space-efficient policy (RAID-1 to RAID-5) to hundreds of VMs in a nearly full workload-domain cluster. Several objects show resync activity and some operations fail for lack of space. What is the **best explanation and prevention**?

- **A.** Policy changes are instant and need no space, so the failure is a vCenter bug
- **B.** Applying a new layout creates new components while the old ones still exist, requiring temporary extra capacity; keep adequate slack space and apply changes in batches
- **C.** The default policy is locked, so it must be deleted first
- **D.** Policies defined in the management domain are overriding the workload domain's policy

<details>
<summary>Answer and explanation</summary>

**Correct: B.**
Reapplying a policy rebuilds objects in the new layout and **resyncs** data. During the transition both the old and new layouts exist, so temporary extra capacity is needed. Maintain **slack space** (commonly 25-30%) and apply large changes in manageable batches.
- **A** is incorrect: policy changes trigger resync and consume space.
- **C** is incorrect: the default policy is not the issue here.
- **D** is incorrect: policies are scoped to each domain's vCenter and do not override each other across domains.

</details>
