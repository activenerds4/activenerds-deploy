## NSX Distributed Firewall (DFW) and Private Cloud Security Rules



<Callout variant="info" title="VCF 9.0 Release Note">

</Callout>


- Describe the **policy categories** and the order in which rules are evaluated.
- Build **groups** using static and **dynamic (tag-based)** membership.
- Use **Applied To** to scope rules to the right workloads and avoid common mistakes.
- Create and apply **security tags** to drive membership.
- Design an **allow-list (zero trust)** security model without breaking VCF management traffic.
- Troubleshoot rule hits, logging, and traffic flows.

## 2. DFW Fundamentals

### 2.1 What the DFW is

- A **stateful Layer 2 to Layer 7 firewall** enforced **in the hypervisor kernel** at the **virtual NIC (vNIC)** of each workload.
- Policy is created centrally in **NSX Manager** and pushed to the **transport nodes** (ESXi hosts) where the workloads run.
- Traffic is inspected **before it leaves the vNIC** (outbound) and **as it arrives at the vNIC** (inbound), including traffic between two VMs on the **same host and same segment**, which a traditional perimeter firewall never sees.
- Works for **overlay-backed** and **VLAN-backed** workloads attached to NSX-prepared hosts, and supports workloads beyond vSphere VMs (bare metal and containers via agents/integrations).

### 2.2 DFW vs Gateway Firewall

| Feature | **Distributed Firewall** | **Gateway Firewall** |
|---|---|---|
| Enforcement point | vNIC of each workload (east-west) | Tier-0 / Tier-1 gateway uplinks and services interfaces (north-south) |
| Runs on | ESXi host kernel | NSX Edge nodes |
| Primary use | **Micro-segmentation**, east-west control | Perimeter, tenant boundary, north-south control |
| Scale model | Scales with number of hosts | Bounded by Edge capacity |

**Rule of thumb:** use the **DFW for east-west** and the **Gateway Firewall for north-south** (and for tenant/edge boundaries).

### 2.3 Why micro-segmentation

Traditional security sits at the network perimeter; once an attacker is inside, lateral movement is easy. Micro-segmentation applies policy **at each workload**, independent of IP subnet or VLAN design.

Benefits:

- **Reduces lateral movement** (limits blast radius).
- **Policy follows the workload** during vMotion because enforcement is at the vNIC.
- **No re-IP or re-architecture** is needed to isolate applications.
- **Zero-trust posture**: explicitly allow required flows, deny everything else.
- Policies are **identity- and context-driven** (tags, names, AD groups, applications) rather than IP-driven.

## 3. Firewall Policy Structure

### 3.1 Hierarchy

```
Category  (evaluation stage)
 └── Policy  (a section: a named, ordered collection of rules, with its own Applied To)
      └── Rule  (source, destination, service, profile, applied to, action)
```

→ In older **Manager mode** terminology, a policy is called a **section**. In **Policy mode**, you work with **categories → policies → rules**. The exam may use "section" and "policy" loosely; know they map to the same grouping concept.

### 3.2 Categories and evaluation order

Categories are evaluated **left to right**, and rules within a policy **top to bottom**. The **first matching rule wins**.

| Order | Category | Intended use |
|---|---|---|
| 1 | **Ethernet** | Layer 2 (MAC-based) rules |
| 2 | **Emergency** | Quarantine and **emergency block/allow** rules; highest priority for incident response |
| 3 | **Infrastructure** | Shared services: DNS, NTP, AD, DHCP, backup, monitoring, management access |
| 4 | **Environment** | Zone-to-zone isolation: Prod vs Dev vs Test, DMZ vs internal, tenant separation |
| 5 | **Application** | App-specific rules: tier-to-tier flows (web to app to database), including the **Default Layer 3 policy** |

Why this matters: placing **broad rules in earlier categories** (for example, "block Dev from Prod" in Environment) means they apply **before** the more specific application rules.

### 3.3 Rule fields

| Field | Description |
|---|---|
| **Name** | Descriptive label |
| **Source / Destination** | Groups, IP addresses, or **Any** |
| **Services** | Protocol/port definitions (predefined or custom) |
| **Context Profiles** | Layer 7 **App ID**, **FQDN/URL** attributes for application-aware rules |
| **Applied To** | The set of **workloads on which the rule is enforced** (see Section 5) |
| **Action** | **Allow**, **Drop** (silent discard), **Reject** (discard and send RST/ICMP unreachable), or **Jump to Application** |
| **Direction** | In, Out, or In-Out (relative to the workload's vNIC) |
| **IP Protocol** | IPv4, IPv6, or both |
| **Logging** | Optional per-rule logging for audit and troubleshooting |
| **Stateful / Stateless** | Stateful by default; stateless is available when required |

**Action notes:**

- **Drop** silently discards; the sender sees timeouts.
- **Reject** responds, so clients fail fast.
- **Jump to Application** skips the remaining rules in the **Environment** category and continues evaluation in **Application**. It is used to let application owners govern flows without hitting broader environment rules.

### 3.4 Allow-list vs block-list

| Model | How it works | Comment |
|---|---|---|
| **Block-list (default allow)** | Everything is allowed; specific bad flows are blocked | Easy to start; weak security posture |
| **Allow-list (default deny)** | Only explicitly allowed flows pass; the default rule is set to **Drop/Reject** | **Zero trust target**; requires flow knowledge first |

- The **Default Layer 3 rule** ships as **Allow** so a fresh deployment does not break traffic.
- **Best practice:** build and validate **allow rules first**, observe flows, **then** change the default rule to **Drop/Reject** (with logging).
- Changing the default to deny **before** the required allow rules exist is a classic outage cause.

### 3.5 Recommended policy layout (example)

| Category | Policy | Purpose |
|---|---|---|
| Emergency | `EMG-Quarantine` | Block anything tagged `Quarantine` in and out |
| Infrastructure | `INF-Shared-Services` | Allow DNS, NTP, AD, backup, monitoring |
| Infrastructure | `INF-Mgmt-Access` | Allow admin jump hosts to management ports |
| Environment | `ENV-Isolation` | Drop Prod to/from Dev/Test; allow within each zone |
| Application | `APP-Payments` | Web to App on 8443, App to DB on 1433, deny rest |
| Application | `Default Layer 3` | Final **Drop** with logging (after validation) |

## 4. Groups and Security Tags

### 4.1 Groups

A **group** is a dynamic or static collection used as a **source, destination, or Applied To** target.

| Membership method | Examples |
|---|---|
| **Dynamic criteria** (up to a limited number of criteria per group) | VM **tag**, VM **name** (contains/starts with), **OS name**, **computer name**, **segment**, **segment port** |
| **Static members** | Specific **VMs**, **segments**, **IP addresses/ranges**, other **groups** |
| **Identity (AD) members** | **Active Directory groups** for Identity Firewall |

- **Nesting** is supported: a group can contain other groups.
- Dynamic membership is **evaluated continuously**; when a VM gains or loses a matching attribute, it **joins or leaves the group automatically** and policy follows within seconds.

### 4.2 Security tags

- A **tag** is metadata with a **value** and an optional **scope** (for example, scope `env`, tag `prod`).
- Tags are **assigned to VMs** (or other objects such as segments/ports) in NSX and used in group criteria.
- Typical tag taxonomy:

| Scope | Example tags |
|---|---|
| `env` | `prod`, `dev`, `test` |
| `app` | `payments`, `hr`, `crm` |
| `tier` | `web`, `app`, `db` |
| `compliance` | `pci`, `hipaa` |
| `state` | `Quarantine`, `Remediate` |

- **Limits exist** on the number of tags per object and the length of tag/scope strings; check the current **configuration maximums** rather than assuming.
- Tags can be applied **manually, via API/automation (for example, a provisioning workflow), or by third-party/security integrations**.

### 4.3 Tag-driven automation examples

1. A provisioning workflow tags a new VM `env=prod`, `tier=db`, `app=payments`.
2. Group `Prod-Payments-DB` has criteria: tag `prod` AND tag `payments` AND tag `db`.
3. The rule "App tier to DB on 1433" already references that group, so the **new VM is protected immediately**, with no firewall edit required.
4. If antivirus detects a threat, a **`Quarantine`** tag is applied; the Emergency policy matches the `Quarantine` group and **isolates the VM** instantly.

### 4.4 Group design tips

- Build **groups by role** (web, app, db), then **combine** into app-level groups.
- Prefer **tags over IPs** so policy survives IP changes.
- Keep **naming consistent** (`GRP-<env>-<app>-<tier>`).
- Avoid very large, deeply nested groups that are hard to troubleshoot.

## 5. Applied To

### 5.1 What it does

**Applied To** defines **where the rule is pushed and enforced**. It selects which workloads' vNICs receive the rule.

- Default is **DFW** (the rule is pushed to **all** DFW-enabled workloads).
- You can restrict to specific **groups** (and, depending on the object type, segments or ports).
- **Applied To can be set at the policy level** (inherited by rules) **or at the rule level** (more granular).

### 5.2 Why scope matters

| Benefit | Explanation |
|---|---|
| **Performance and scale** | Fewer rules per vNIC (less to evaluate and store) |
| **Operational clarity** | Rules only appear where relevant |
| **Safety** | Reduces accidental impact on unrelated workloads |

### 5.3 Critical concept: the rule must be realized where the traffic is enforced

A rule only takes effect on workloads in its **Applied To**. If the **source** or **destination** is a workload that is *not* in Applied To, the rule will **not** be enforced at that workload's vNIC.

Example mistake:

- Rule: **Source** `Web-Group` to **Destination** `DB-Group`, TCP 1433, **Allow**, **Applied To** = `Web-Group` only.
- Result: the rule is enforced only at the web VMs' vNICs; **the DB VMs do not get this allow rule**. If a default **drop** exists for DB inbound traffic, the connection can still be blocked at the DB side.

**Correct approach:** apply to **both** `Web-Group` and `DB-Group` (or leave at **DFW** if scoping is not important), so enforcement occurs at **both ends**.

### 5.3.1 Applied To and "Any"

- A rule with **Source = Any, Destination = Any, Applied To = DFW** touches every workload; use sparingly and mostly for deliberate default policies.
- Use **Applied To** to limit blanket rules (for example, "drop all except allowed" for a single application).

### 5.4 Exclusion list

- The **DFW exclusion list** removes selected objects from DFW enforcement.
- **NSX Manager and NSX Edge nodes are automatically excluded**; add other critical infrastructure (for example, **vCenter Server** and other management components) to prevent accidental lockout when building a deny-by-default policy.
- Excluded workloads have **no DFW protection**, so keep the list short and reviewed.

## 6. NSX DFW in VCF Workload Domains

### 6.1 Placement and ownership

- **NSX Manager** (a 3-node cluster in standard designs) is deployed by VCF into the **management domain**, with the **vCenter of each domain registered as a compute manager**. Each **VI workload domain** can use a **dedicated NSX Manager cluster** or **share** one with other workload domains, depending on design.
- Host preparation (installing NSX VIBs/components, creating transport nodes, assigning TEP IP pools) is handled by **VCF workflows**; the DFW then **activates on prepared hosts** automatically.
- DFW policy is configured in **NSX Manager** (UI or API), not in vSphere Client firewall settings.

### 6.2 VCF-specific guidance

| Topic | Guidance |
|---|---|
| **Protect VCF management traffic** | Before moving to default-deny, ensure rules allow **vCenter, NSX Manager, SDDC Manager / VCF Operations, ESXi management, DNS, NTP, backup, identity**, and cross-component flows. Add **critical management VMs to the exclusion list** if appropriate |
| **Tenant / workload segmentation** | Use **Environment** policies to separate tenants, business units, or Prod/Dev/Test; **Application** policies for tiers |
| **Change control** | Use **Emergency** category sparingly; document all rules and owners |
| **Automation** | VCF Automation / blueprints/templates can **apply tags at provisioning**, so firewall policy is applied from day one |
| **Visibility** | Use **rule hit counts, logging, Traceflow, and flow-analysis tools** (for example, VCF Operations network visibility or NSX security add-ons, depending on licensing and release) to discover flows and recommend rules |
| **Do not edit VCF-managed objects ad hoc** | Avoid manual changes to VCF-created NSX objects (transport zones, management segments) outside supported workflows |
| **VPC consumption (newer NSX/VCF releases)** | In VPC-based networking, **security policies are scoped to the VPC**; confirm the model in your release documentation |

### 6.3 Typical implementation path

1. **Discover** current flows (flow monitoring, logs, application owners).
2. **Define tag taxonomy** and **groups**.
3. Create **Infrastructure** rules for shared services.
4. Create **Environment** isolation rules.
5. Create **Application** policies per workload, scoped with **Applied To**.
6. Enable **logging** on key rules; validate with **hit counts** and Traceflow.
7. Change **Default Layer 3** to **Drop/Reject** only after validation.
8. **Monitor and review** regularly; retire unused rules.

## 7. Operations and Troubleshooting

| Tool / Feature | Use |
|---|---|
| **Rule hit count** | Shows how often a rule matched; find unused or shadowed rules |
| **Rule logging** | Sends rule-match logs for audit and troubleshooting |
| **Traceflow** | Injects a synthetic packet to see if and where it is dropped, and which rule applied |
| **Realized state / Applied To check** | Confirm which workloads received the rule |
| **Effective members** of a group | Verify tag/criteria matches resolved as expected |
| **Packet capture / host logs** | Deep troubleshooting at the host level |
| **Drafts / publish** | Stage firewall changes as drafts and publish together (when used) |

**Common problems:**

| Symptom | Likely cause |
|---|---|
| New VM not covered by policy | Missing tag, group criteria mismatch, or **Applied To** excludes it |
| Allow rule has no effect | **Applied To** doesn't include both ends; a broader earlier rule matches first |
| Everything breaks after enabling default deny | Required allow rules (infrastructure/management) missing |
| Management access lost | vCenter/management components not allowed or not excluded |
| Rule never hits | Shadowed by a rule higher in order or an earlier category |
| Cross-VM traffic still blocked | Stateful return path is fine, but **inbound rule at destination** is missing |

## 8. Exam Tips

1. **Evaluation order:** categories **Ethernet, Emergency, Infrastructure, Environment, Application**; within a policy, **top to bottom**; **first match wins**.
2. **DFW is enforced at the vNIC**, east-west, in the **hypervisor kernel**; **Gateway Firewall** is for north-south on Edge.
3. **Default rule is Allow** on a new deployment; move to **Drop/Reject only after** building allow rules.
4. **Applied To controls where a rule is enforced.** If it excludes a workload, that workload never receives the rule. Know the "Web to DB applied to Web only" trap.
5. **Tags drive dynamic groups**; security tags enable **automation and quarantine** workflows.
6. **Emergency category** is for **quarantine/incident response**; it is evaluated early.
7. **Jump to Application** skips remaining **Environment** rules and continues in **Application**.
8. **Drop = silent; Reject = sends a response.**
9. **Exclusion list** removes objects from DFW; **NSX Manager and Edge nodes are automatically excluded**. Add vCenter and other critical management components as needed.
10. **Micro-segmentation does not require IP or VLAN changes**; policy follows the VM through vMotion.
11. **In VCF, NSX Manager lives in the management domain**; workload domains register their vCenter as a compute manager and may use dedicated or shared NSX Managers.
12. **Prefer tags and groups over IPs** in answers about scalable policy design.
13. **Read the scenario for the clue:** "stop lateral movement inside a subnet" means **DFW**; "control traffic leaving the data center" means **Gateway Firewall**; "quarantine an infected VM instantly" means **tag + Emergency policy**.

## 9. Practice Questions

### Question 1

A security team wants to prevent lateral movement between application tiers that share the **same subnet and segment** in a VCF workload domain, without re-IPing the workloads. Which NSX capability should they use?

- **A.** Gateway Firewall rules on the Tier-0 gateway
- **B.** Distributed Firewall rules enforced at each VM's vNIC
- **C.** A new VLAN for each tier with ACLs on the physical switch
- **D.** Exclusion of all VMs from the Distributed Firewall

<details>
<summary>Answer and explanation</summary>

**Correct: B.**
The DFW enforces policy at the **vNIC**, so it can control traffic between workloads even on the **same segment and subnet**, with no network redesign. This is the essence of **micro-segmentation**.
- **A** inspects north-south traffic at the Edge; intra-segment traffic never reaches it.
- **C** requires re-architecture and re-IPing, which the requirement rules out.
- **D** would remove protection entirely.

</details>

### Question 2

An administrator creates an Application-category rule: **Source** `Web-Group`, **Destination** `DB-Group`, **Service** TCP 1433, **Action** Allow, **Applied To** `Web-Group`. A final **Default Layer 3** rule is set to **Drop**. Web servers still cannot connect to the databases. What is the **most likely cause**?

- **A.** TCP 1433 is not a valid service for the DFW
- **B.** The rule is not applied to `DB-Group`, so the databases' vNICs do not have the allow rule and the default drop blocks the traffic
- **C.** Security tags cannot be used in group membership
- **D.** The rule must be placed in the Ethernet category

<details>
<summary>Answer and explanation</summary>

**Correct: B.**
A rule is enforced only on the workloads in its **Applied To**. With Applied To set to `Web-Group` alone, the database VMs never receive the allow rule, and their **inbound** traffic hits the default **Drop**. Add `DB-Group` to Applied To (or use the default DFW scope).
- **A** is incorrect; TCP 1433 is a standard SQL Server port and can be defined as a service.
- **C** is incorrect; tag-based membership is a core feature.
- **D** is incorrect; Ethernet rules are Layer 2 (MAC-based) and not appropriate for this requirement.

</details>

### Question 3

An endpoint security tool detects malware on a VM. The security team wants to **isolate the VM immediately**, overriding all normal application rules, and without editing individual firewall rules. Which approach is best?

- **A.** Add the VM's IP address to a new rule in the Application category, below the Default Layer 3 rule
- **B.** Apply a `Quarantine` security tag that is matched by a group used in an **Emergency** category policy with Drop rules
- **C.** Place the VM on the DFW exclusion list
- **D.** Change the Default Layer 3 rule to Allow

<details>
<summary>Answer and explanation</summary>

**Correct: B.**
The **Emergency** category is evaluated **before** Infrastructure, Environment, and Application rules, so a **tag-driven quarantine** policy overrides normal rules. Applying the tag adds the VM to the quarantine group automatically, and the rule takes effect without further edits.
- **A** places the rule too late (and below the default rule it would never be reached); IP-based rules are also brittle.
- **C** removes the VM from DFW enforcement, so it would be *less* protected.
- **D** weakens security.

</details>
