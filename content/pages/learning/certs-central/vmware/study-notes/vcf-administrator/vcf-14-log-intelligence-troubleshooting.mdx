> **Instructor note on naming:** Product names changed across releases. What was **vRealize Log Insight (vRLI)**, then **Aria Operations for Logs**, is **VCF Operations for logs** in VCF 9.x. **vRealize/Aria Operations** is **VCF Operations**. In VCF 4.x/5.x these were deployed and lifecycle-managed through vRealize/Aria Suite Lifecycle; in 9.x they are integrated into the VCF management stack. The concepts below (syslog ingestion, queries, alerts, content packs) carry across, but **UI paths and deployment methods differ by release**. Confirm against the current exam guide and documentation.

---

## 1. Learning Objectives

After this module you should be able to:

- Explain how logs and metrics are collected and aggregated in VCF.
- Configure log forwarding from ESXi, vCenter, NSX, and SDDC Manager to VCF Operations for logs.
- Query logs using Interactive Analytics, filters, field extraction, and saved queries.
- Locate key log files on SDDC Manager, vCenter, ESXi, and NSX.
- Configure alerts and notifications in VCF Operations and VCF Operations for logs.
- Apply a structured troubleshooting workflow and collect support bundles.

## 2. Observability Building Blocks

| Component | Role |
|---|---|
| **VCF Operations** (formerly Aria Operations / vROps) | Metrics, capacity, health, alerts, symptoms, dashboards, compliance. |
| **VCF Operations for logs** (formerly Aria Operations for Logs / vRLI) | Centralized log collection, indexing, search, dashboards, log-based alerts. |
| **Content packs / integrations** | Prebuilt dashboards, extracted fields, and alerts for vSphere, NSX, vSAN, VCF, and others. |
| **SDDC Manager** | Source of workflow, LCM, and inventory logs; also drives log-forwarding configuration for the management domain in many releases. |
| **Syslog / agents** | Transport mechanisms for sending logs to the log platform. |

**Logs vs. metrics vs. events**

| Data type | Example | Where you analyze it |
|---|---|---|
| **Logs** | `vpxd.log` entry about a failed login | VCF Operations for logs |
| **Metrics** | CPU ready %, datastore latency | VCF Operations |
| **Events / alerts** | "Host connection lost" | vCenter events; VCF Operations alerts |

Effective troubleshooting **combines all three**: an alert (VCF Operations) points to an object, metrics show when it degraded, and logs show why.

## 3. Log Aggregation

### 3.1 Architecture

```
ESXi hosts ──┐
vCenter ─────┤
NSX Managers ┼──(syslog / cfapi)──► VCF Operations for logs ──► Search, dashboards, alerts
NSX Edges ───┤                          (single node or cluster)        │
SDDC Manager ┘                                                          ▼
                                                  Forward to VCF Operations / SIEM / email / webhook
```

### 3.2 Ingestion methods and ports

| Method | Protocol / Port | Notes |
|---|---|---|
| **Syslog UDP** | 514 | Unreliable; no encryption. |
| **Syslog TCP** | 514 | Reliable; unencrypted. |
| **Syslog TLS** | 6514 (RFC 5425) | Encrypted. Common for ESXi/NSX is 1514 for SSL in ESXi syslog config. Confirm the port your destination listens on. |
| **Ingestion API (cfapi)** | 9000 (HTTP) / 9543 (HTTPS) | Used by Log Insight agents and some integrations. |
| **Log Insight agent** | cfapi | Installed on Windows or Linux guest OSes for file-based collection. |
| **Web UI / API** | 443 | Administration and query access. |

→ **Exam tip:** When an exam question mentions "reliable and encrypted" log delivery, the answer is **syslog over TLS** (or the agent using SSL).

### 3.3 Sizing and clustering
- Deploy as a **single node** for small environments or a **cluster** (master + workers) with an **Integrated Load Balancer (ILB)** virtual IP for scale and HA.
- Point log sources at the **ILB VIP/FQDN**, not at an individual node, so sources survive node failure.
- Plan **retention**, **storage**, and **archiving** (often to NFS). Retention is bounded by index capacity, so long-term retention requires archive or forwarding.
- Ingestion rate is measured in events per second (EPS). Oversized EPS leads to dropped events or high indexing latency.

### 3.4 Configuring sources

**ESXi**
- Advanced setting: `Syslog.global.logHost`, e.g. `tcp://logs.corp.local:514` or `ssl://logs.corp.local:1514`.
- Can be set per host, via host profile, or by SDDC Manager/vCenter configuration in VCF workflows.
- Open the ESXi firewall `syslog` rule outbound if required.
- ESXi logs live on a ramdisk by default unless a persistent scratch location is configured. **Remote syslog protects log data across reboots.**

**vCenter Server**
- VAMI (`https://vcenter:5480`) → **Syslog** → add the log destination (up to three forwarding targets).
- Choose protocol (UDP/TCP/TLS) and port.

**NSX Manager / Edge**
- NSX CLI example: `set logging-server <ip-or-fqdn>:<port> proto <tcp\|udp\|tls> level info`
- Verify with `get logging-servers`.
- Must be configured on **each NSX Manager node and each Edge node**. ESXi transport nodes use the ESXi syslog configuration.

**SDDC Manager**
- Appliance syslog is configured at the OS level, and in many releases the VCF log-forwarding workflow configures it automatically when the log platform is integrated.
- In VCF 4.x/5.x, deploying Aria Operations for Logs through the Aria Suite Lifecycle workflow and integrating it with the management domain configures log forwarding for ESXi, vCenter, NSX, and SDDC Manager.

**VCF Operations integration**
- VCF Operations for logs can integrate with VCF Operations for **launch-in-context** (jump from an alert to related logs) and to forward log-based alerts into VCF Operations.

### 3.5 Content packs and integrations
- Provide **extracted fields**, dashboards, and alert definitions for products such as **vSphere**, **NSX**, **vSAN**, and **VCF**.
- Without the right content pack/integration, logs still arrive but appear as raw text without parsed fields, which makes queries harder.

## 4. Querying Logs

### 4.1 Interactive Analytics workflow
1. Open **Explore Logs / Interactive Analytics**.
2. Set the **time range** (the first thing to narrow).
3. Enter **text search** terms (keywords, phrases in quotes, wildcards).
4. Add **field filters** (e.g., `hostname`, `appname`, `vmw_esxi_message`, `vc_event_type`, source IP). Operators typically include *contains, does not contain, matches, starts with, ends with*, and numeric comparisons.
5. Use **Group By** to aggregate and **chart** results (count over time, top N sources).
6. **Save** useful queries, **add to a dashboard**, or **create an alert** from the query.

### 4.2 Practical query patterns

| Goal | Approach |
|---|---|
| Find all errors from one host in the last hour | Time range = last hour; filter `hostname` contains the host; text `error` OR filter by severity field. |
| Trace one failed login | Search the username; narrow to `appname` = vCenter/SSO components. |
| Count events by type | Filter by source/product; **Group by** event type; chart count. |
| Compare "before vs. after" a change | Use two time ranges; look for new or spiking message patterns. |
| Identify noisy sources | Group by `hostname`; chart event count; investigate top talkers. |

### 4.3 Field extraction
- You can define **custom extracted fields** from a log line (pattern + named capture). Useful for custom apps or fields not covered by content packs.
- Extracted fields can then be filtered, grouped, and charted like built-in fields.

### 4.4 Event correlation techniques
- Use a **shared identifier**: task ID, correlation ID, VM name, UUID, IP address, or user name.
- Align on **time**. All components must be NTP-synchronized, or timestamps will not line up. Remember **time zone** (most appliances log in UTC).
- Look for the **first error**, not the loudest one. Downstream failures often spam more entries than the root cause.

## 5. Key Log Locations by Component

### 5.1 SDDC Manager (appliance)

| Path / file | Contents |
|---|---|
| `/var/log/vmware/vcf/domainmanager/domainmanager.log` | Workload domain and cluster workflows (create, add host, expand, delete). |
| `/var/log/vmware/vcf/operationsmanager/operationsmanager.log` | Inventory, password management, certificate and configuration operations. |
| `/var/log/vmware/vcf/lcm/lcm.log` | Lifecycle management: bundle download, precheck, upgrade. |
| `/var/log/vmware/vcf/commonsvcs/vcf-commonsvcs.log` | Shared services such as credentials and authentication. |
| `/var/log/vmware/vcf/sddc-manager-ui-app/` | UI service logs. |
| `/var/log/vmware/vcf/vcf-services/` (and similar) | Other services. File names vary by release. |

**Tools**
- **SoS utility:** `/opt/vmware/sddc-support/sos` is the VCF support tool for **health checks** and **log/support bundle collection**. Run as `root` (log in as `vcf`, then `su -`). Typical capabilities: health checks across domains, collecting SDDC Manager, vCenter, NSX, and ESXi logs for a given domain, and writing output to a log directory. Check `sos --help` for options in your release.
- **UI:** SDDC Manager → **Tasks** panel shows workflow progress, subtasks, and errors; failed tasks usually offer **Retry** after the cause is fixed.
- **Task correlation:** Find the **task ID** or **correlation ID** in the UI/API, then search for it in `domainmanager.log` or `lcm.log` to see the exact subtask failure.

### 5.2 vCenter Server

| Path / file | Contents |
|---|---|
| `/var/log/vmware/vpxd/vpxd.log` | Core vCenter service: inventory, tasks, host connectivity, DRS/HA operations. |
| `/var/log/vmware/vpxd-svcs/` | vCenter services (tagging, permissions, etc.). |
| `/var/log/vmware/vsphere-ui/logs/` | vSphere Client issues. |
| `/var/log/vmware/sso/` and `/var/log/vmware/vmdird/` | SSO and directory authentication. |
| `/var/log/vmware/applmgmt/` | Appliance management and patching. |
| `/var/log/vmware/vmware-vmon/` | Service lifecycle (service start/stop failures). |
| `/var/log/vmware/eam/` | ESX Agent Manager (agent VMs, vSAN/NSX VIB deployment issues). |

**Tools:** `service-control --status --all` to check service state; `vc-support.sh` or **Export System Logs** in the UI for support bundles.

### 5.3 ESXi

| File | Contents |
|---|---|
| `/var/log/vmkernel.log` | Kernel, storage, networking, driver events. |
| `/var/log/hostd.log` | Host management agent, VM operations. |
| `/var/log/vpxa.log` | vCenter agent on the host; vCenter-to-host communication. |
| `/var/log/vobd.log` | VMkernel Observation events. |
| `/var/log/fdm.log` | vSphere HA agent. |
| `/var/log/syslog.log`, `/var/log/shell.log` | General and shell activity. |
| `/var/log/dfwpktlogs.log` | NSX distributed firewall packet logs (when rule logging is enabled). |

### 5.4 NSX

| Location | Contents |
|---|---|
| `/var/log/syslog` (Manager and Edge) | General NSX appliance log; includes audit and API activity. |
| `/var/log/proton/nsxapi.log` | NSX Manager API and management plane. |
| `/var/log/policy/` | Policy engine logs. |
| `/var/log/corfu/` | Corfu datastore (clustering/datastore health). |
| `/var/log/cloudnet/` | Control-plane/central control related logs. |
| Edge `/var/log/syslog` and datapath logs | Edge node, T0/T1 services. |

**NSX CLI helpers:** `get cluster status` (manager cluster health), `get managers`, `get logging-servers`, `get log-file <name>` (view a log from CLI). NSX also offers **support bundle** generation from the UI (System → Support Bundle).

NSX logs are tagged by component (`NSX`, `MP`, `CCP`, etc.), and with the NSX content pack you can filter by component, severity, and message ID.

## 6. Alerts and Notifications

### 6.1 Two alerting layers

| Layer | Source | Example |
|---|---|---|
| **Metric / object-based** | **VCF Operations** (symptoms and alert definitions) | Host CPU ready above threshold; datastore capacity low; vSAN health warning. |
| **Log-based** | **VCF Operations for logs** (query-based alerts) | More than N "storage path down" messages in 5 minutes. |
| **Native product alarms** | vCenter / NSX / SDDC Manager | vCenter alarms; NSX alarms; SDDC Manager notifications. |

### 6.2 VCF Operations: alert anatomy
- **Symptom:** A condition (metric threshold, property, event, message) on an object.
- **Alert definition:** One or more symptoms + criticality + recommendations + the object type it applies to.
- **Alert:** A triggered instance on a specific object, with a status, criticality (Info, Warning, Immediate, Critical), and recommended actions.
- **Notification rule:** Sends matching alerts to an **outbound method**.
- **Outbound methods:** Email (SMTP), SNMP trap, REST/webhook, and other integrations such as Slack or ServiceNow depending on release/plugin.
- Use **policies** to control which alert definitions are enabled for which groups of objects. Disable noisy definitions in non-production.

### 6.3 VCF Operations for logs: query-based alerts
1. Build and **validate** the query in Interactive Analytics.
2. Click **Create Alert from Query**.
3. Define:
   - **Trigger condition** (e.g., count of events above a threshold over a time window).
   - **Evaluation interval** (how often the query runs).
   - **Severity.**
   - **Notification:** email recipients, **webhook**, and/or **forward to VCF Operations**.
4. Test and tune to prevent alert storms.

### 6.4 Prerequisites for notifications
- **SMTP settings** configured and tested (server, port, authentication, TLS, "from" address).
- DNS/firewall allow outbound connectivity to SMTP/webhook endpoints.
- For forwarding to VCF Operations, the **integration** must be configured and the alert type mapped.

### 6.5 SDDC Manager notifications
- SDDC Manager shows **in-product notifications** and tasks (e.g., failed workflows, expiring certificates, bundle availability).
- Pair these with **VCF Operations** and **log-based alerts** so failures are not discovered only by someone looking at the UI.

### 6.6 Alert design best practices
- Alert on **symptoms that need action**, not on every warning.
- Use **thresholds with duration** (e.g., sustained for 5 minutes) to avoid flapping.
- Route by **severity** (Critical to on-call/webhook; Warning to email digest).
- Include **context** (object name, time, recommended action) in notifications.
- Review and tune after every incident.

## 7. Troubleshooting Workflows

### 7.1 General methodology (use this to eliminate wrong answers)

1. **Define the problem.** What exactly failed? Who is affected? Since when?
2. **Scope it.** One VM, one host, one cluster, one domain, or everything?
3. **Check for recent changes.** Upgrades, certificate changes, password rotation, network or DNS changes, new firewall rules.
4. **Check health and alerts.** VCF Operations alerts and object health; SDDC Manager tasks; vCenter/NSX alarms.
5. **Gather evidence.** Metrics for timeline; logs for root cause. Align timestamps.
6. **Isolate the layer.** Physical, ESXi, vCenter, NSX overlay/underlay, SDDC Manager, identity, DNS/NTP.
7. **Fix the root cause**, not just the symptom.
8. **Validate.** Re-run the workflow/health check; confirm alerts clear.
9. **Document and prevent.** Update runbooks and alert thresholds.

### 7.2 Workflow A: Failed SDDC Manager task (e.g., add host, create domain, upgrade)

1. Open **SDDC Manager → Tasks**; expand the failed task to find the **failing subtask** and message.
2. Note the **task ID / correlation ID**.
3. Review the relevant log:
   - Domain/cluster/host workflows: `domainmanager.log`
   - Upgrades/bundles/precheck: `lcm.log`
   - Passwords/certs/inventory: `operationsmanager.log`
4. Check **dependencies**: DNS forward/reverse, NTP drift, credentials (use **Password Management** to remediate mismatches), host connectivity, vCenter/NSX status.
5. **Fix the cause outside SDDC Manager** (e.g., correct DNS, restore NSX connectivity). Avoid changing the environment in ways that conflict with SDDC Manager's inventory.
6. **Retry** the failed task from the UI so the workflow resumes in a supported way.
7. If unresolved, run **SoS** to collect logs and open a support case with the bundle.

### 7.3 Workflow B: Host disconnected from vCenter
1. VCF Operations: confirm the alert and the time it began; check host metrics before the event.
2. Search logs for the host in VCF Operations for logs: `vpxa.log`, `hostd.log`, `vpxd.log` entries around the time.
3. Check: management network, DNS resolution, NTP, certificate validity, `vpxa`/`hostd` service state.
4. Attempt reconnect after the fix; verify in vCenter and vSAN/NSX health.

### 7.4 Workflow C: NSX connectivity or overlay issue
1. NSX UI: check **alarms**, **transport node status**, **Tunnel status**, and **Manager cluster** health.
2. CLI: `get cluster status`, edge/host tunnel status, and **MTU** (overlay requires adequate MTU, typically 1600+ end-to-end for Geneve).
3. Search logs by component and time in the log platform; check `nsxapi.log`, edge syslog, and ESXi `vmkernel.log` for TEP/driver issues.
4. Use **Traceflow** and **Port Mirroring/Packet Capture** to localize drops.
5. Review distributed firewall logs (`dfwpktlogs.log`) if traffic is blocked by policy.

### 7.5 Workflow D: Login or SSO failures
1. Verify identity source status in vCenter; test LDAPS connectivity.
2. Check **NTP/time skew** and **DNS**.
3. Review `/var/log/vmware/sso/` and `vmdird` logs (or search the log platform for the username).
4. Fall back to **local break-glass accounts** (`administrator@vsphere.local`, `admin@local`) to repair the configuration.

### 7.6 Workflow E: Log data is missing in the log platform
1. Confirm the **destination, protocol, and port** on the source (ESXi `Syslog.global.logHost`, vCenter VAMI syslog, NSX `get logging-servers`).
2. Check **firewall rules** and the ESXi **syslog firewall rule**.
3. Verify the log platform is **receiving** (ingestion status/administration page) and is not **out of disk or hitting ingest limits**.
4. Confirm **TLS trust** (the CA certificate) if using TLS.
5. Make sure sources point to the **ILB VIP** if clustered.

### 7.7 Support bundles: which to use

| Need | Tool |
|---|---|
| VCF-wide health and logs | **SoS utility** on SDDC Manager |
| vCenter logs | vCenter **Export System Logs** / `vc-support.sh` |
| ESXi logs | vSphere Client **Export System Logs** or `vm-support` |
| NSX logs | NSX **Support Bundle** |

## 8. Best Practices Summary

- Send **all** infrastructure logs to a **central** platform; do not rely on local logs.
- Use **TLS** transport and the cluster **ILB VIP**.
- Keep **NTP and DNS** correct everywhere. They are the cause of a surprising share of incidents.
- Install and update the relevant **content packs/integrations**.
- Create **dashboards** for each domain (vSphere, NSX, vSAN, SDDC Manager).
- Tune alerts to reduce noise; route by severity.
- Define **retention and archive** policy up front.
- Collect a **support bundle immediately** when a problem occurs (logs roll over).
- **Do not modify** SDDC Manager-managed service accounts, or reconfigure managed components outside of SDDC Manager workflows, unless documented.

## 9. Exam Tips

1. **Combine tools:** VCF Operations = metrics/alerts; VCF Operations for logs = log search and log-based alerts. Questions often hinge on picking the right one.
2. **Syslog TLS** = reliable/encrypted answer; UDP = lightweight but lossy.
3. **Point sources to the ILB VIP**, not a single node.
4. SDDC Manager workflow failures: look at **Tasks**, then `domainmanager.log` (domain workflows) or `lcm.log` (upgrades), then **Retry** after fixing the root cause.
5. **SoS utility** (`/opt/vmware/sddc-support/sos`) is the VCF-native tool for health checks and log collection.
6. **vpxd.log** = vCenter core; **vpxa.log** = host-side agent; **hostd.log** = ESXi management; **vmkernel.log** = storage/network/driver.
7. NSX logging must be configured **per node** (every Manager and Edge).
8. Without a **content pack**, logs are indexed but fields are not parsed.
9. Log-based alerts use a **query + threshold + time window**. Test the query first.
10. **SMTP must be configured** before email notifications work.
11. **Time sync** is critical for log correlation, so check NTP when timelines disagree.
12. Look for the **first error** in the chain, not the last.
13. Remote syslog preserves logs across **ESXi reboots** (ramdisk logs are lost otherwise).
14. Use **Retry** in SDDC Manager rather than starting a new conflicting workflow after fixing a failure.

## 10. Practice Questions

### Question 1
An administrator wants ESXi hosts in a management domain to send logs to a clustered VCF Operations for logs deployment. The requirement is that log delivery is **reliable, encrypted, and survives the loss of a single log node**. Which configuration meets all requirements?

- **A.** Configure each ESXi host with `udp://<node1-fqdn>:514`.
- **B.** Configure each ESXi host with `tcp://<node1-fqdn>:514`.
- **C.** Configure each ESXi host with an `ssl://` target pointing to the cluster's Integrated Load Balancer FQDN.
- **D.** Install a Log Insight agent on every ESXi host and point it to the master node.

<details>
<summary>Answer and Explanation</summary>

**Correct answer: C.**

- **Encrypted** requires TLS/SSL transport.
- **Reliable** requires a connection-oriented protocol (TCP-based, including TLS), not UDP.
- **Survives the loss of a single node** requires targeting the **ILB VIP/FQDN** instead of one node.

A uses UDP (unreliable, unencrypted) and one node. B is reliable but unencrypted and still targets a single node. D is incorrect because agents are not installed on ESXi; ESXi uses native syslog forwarding, and pointing at the master node would still create a single point of failure.
</details>

---

### Question 2
In SDDC Manager, a "Add Host to Cluster" workflow fails at a subtask. The administrator found that the new host's forward DNS record was missing and has now created it. What is the **best next step**?

- **A.** Delete the task and run a new "Add Host" workflow with the same host.
- **B.** Reboot SDDC Manager to clear the failed task.
- **C.** Verify the failure reason in `domainmanager.log`, confirm DNS now resolves forward and reverse, then use **Retry** on the failed task.
- **D.** Manually add the host to the cluster in the vSphere Client to bypass SDDC Manager.

<details>
<summary>Answer and Explanation</summary>

**Correct answer: C.**

The supported recovery path is to **fix the root cause** (DNS), confirm it from both forward and reverse lookups, and **Retry** the failed task so the workflow resumes with consistent state. Host and cluster workflows are logged in `domainmanager.log`, which is the right place to confirm the cause.

A can create inconsistent state or leftovers. B does not address the cause. D bypasses SDDC Manager and leaves its inventory out of sync with vCenter, which causes later workflow and lifecycle failures.
</details>

---

### Question 3
An administrator needs to be notified when an ESXi host logs **more than 20 "storage path down" messages within 5 minutes**. The notification must go to an on-call webhook. Which approach is correct?

- **A.** Create a symptom in VCF Operations on the host's CPU ready metric and attach an SNMP notification rule.
- **B.** Build and validate the query in VCF Operations for logs, create an alert from the query with a count threshold over a 5-minute window, and configure a webhook notification.
- **C.** Enable a vCenter alarm for "Host connection lost" and send email.
- **D.** Increase the ESXi syslog log level to debug and review logs daily.

<details>
<summary>Answer and Explanation</summary>

**Correct answer: B.**

The condition is based on **log message content and frequency over time**, which is exactly what a **log-based (query) alert** in VCF Operations for logs provides: a validated query, a trigger threshold and time window, and a notification method such as a **webhook**.

A uses a CPU metric unrelated to storage paths and the wrong notification type. C monitors a different condition (host connectivity). D is a manual process with no automated notification and adds log noise.
</details>
