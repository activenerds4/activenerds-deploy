> **Instructor note:** VCF Automation is the successor to what many of you know as Aria Automation / vRealize Automation. The product was re-architected for VCF 9.0, and some names changed (for example, *Cloud Templates* are called *Blueprints* in newer releases, and tenancy is built on *Organizations*). The exam may use either vocabulary depending on the objective wording. Always cross-check specifics against the current **official VCP-VCF Administrator exam guide** and the **VCF Automation documentation** for your exact version. Where I'm describing version-specific behavior, I flag it.

---

## 1. Learning Objectives

By the end of this module you should be able to:

- Explain where VCF Automation fits in the VCF private cloud stack and how it integrates with the management domain, workload domains, and VCF Operations.
- Describe the tenancy model (provider vs. tenant, organizations, projects) and how isolation is enforced.
- Author and deploy infrastructure-as-code **Cloud Templates / Blueprints** using YAML.
- Configure **projects**, membership, roles, quotas, and resource constraints.
- Extend templates with **custom resources** and extensibility (Orchestrator, ABX).
- Publish content to a **service catalog** and manage Day-2 actions.
- Troubleshoot common cloud-consumption failures.

## 2. Big Picture: Where VCF Automation Fits

VCF gives you the infrastructure layer (compute, storage, networking, lifecycle). **VCF Automation** is the **self-service consumption layer** on top of it.

| Layer | Component | Role |
|---|---|---|
| Infrastructure | vSphere, vSAN, NSX | Compute, storage, networking |
| Lifecycle / Fleet | SDDC Manager / VCF fleet management | Deploy, patch, upgrade, certificate and credential management |
| Operations | VCF Operations (formerly Aria Operations) | Monitoring, capacity, cost visibility |
| **Consumption** | **VCF Automation** | **Tenants, projects, templates, catalog, governance, extensibility** |

**Key idea:** Admins publish *approved, policy-governed building blocks*; consumers request them on demand without needing vCenter or NSX access.

### Integration points to remember

- **Infrastructure sources:** Workload domain vCenter/NSX are registered as cloud accounts/regions that Automation can provision into.
- **Identity:** Integrates with VCF identity sources (SSO/identity broker, AD/LDAP, SAML/OIDC). Users and groups are assigned to organizations and projects.
- **Operations:** Deployments and resources can be monitored and costed through VCF Operations.
- **Kubernetes:** In VCF, vSphere Supervisor and namespaces provide a path to consume Kubernetes and VM services declaratively.
- **Extensibility:** Orchestrator workflows, ABX (Action Based Extensibility), event subscriptions, and external integrations (ITSM, IPAM, CMDB, Git).

## 3. Multi-Tenancy Model

### 3.1 Provider vs. Tenant

| Persona | Scope | Typical tasks |
|---|---|---|
| **Provider (Cloud/Service Provider Admin)** | Whole platform | Add infrastructure (regions), create organizations, allocate capacity, manage provider-level identity and branding, monitor health |
| **Organization (Tenant) Admin** | One organization | Manage org users/groups, projects, catalog, policies, org networking |
| **Project Admin / Member / Viewer** | One project | Author templates, request deployments, manage deployed resources |
| **Consumer / End user** | Catalog items they're entitled to | Request and manage their own deployments |

### 3.2 Organizations (Tenants)

An **organization** is the top-level tenant boundary. Each org has:

- Its own users, groups, and role assignments
- Its own projects, catalog, content, and policies
- Its own allocation of regions/capacity and networking
- Its own branding and login URL (depending on version)



<Callout variant="info" title="VCF 9.0 Release Note">
In VCF 9.0, organizations come in types aligned to the workload they serve (for example, a model for traditional VM-centric apps that preserves blueprint/template-style authoring, and a model for modern, namespace/Supervisor-centric consumption). Check the release documentation for the exact org types and feature differences in your version.
</Callout>



### 3.3 Projects

A **project** is the working unit inside an organization. It links *people* to *resources*.

A project defines:

- **Members and roles** (Administrator, Member, Viewer, and in some versions Supervisor)
- **Cloud zones / region and resource assignments** (where deployments may land)
- **Constraints** (tag-based placement rules, e.g., `env:prod`)
- **Custom properties** (default values injected into deployments)
- **Quotas / limits** (instances, CPU, memory, storage)
- **Naming** (custom naming templates for deployed resources)

```
Provider
 └── Organization A (Tenant)
 │     ├── Project: Finance-Dev
 │     ├── Project: Finance-Prod
 │     └── Catalog / Policies / Users
 └── Organization B (Tenant)
       └── Project: HR-Apps
```

### 3.4 Tenant Isolation in VCF

Isolation operates at several layers. Exam questions often ask *which layer* provides the isolation.

| Layer | How isolation is achieved |
|---|---|
| **Identity & RBAC** | Users and roles are scoped to an organization and project; one org cannot see another org's objects |
| **Management plane** | Separate catalog, templates, deployments, policies, and content per org |
| **Capacity** | Regions / zones and quotas allocated per org or project |
| **Network** | NSX constructs: separate **VPCs** (or tier-1 gateways / segments in networking-profile models), per-tenant DFW rules, optional dedicated edge/gateway; overlay segments isolate east-west traffic |
| **Compute / Kubernetes** | vSphere/Supervisor **namespaces** with resource limits, permissions, and storage policies |
| **Storage** | Storage policies (SPBM) tied to namespaces/projects; datastores can be dedicated |
| **Operations visibility** | Role-scoped dashboards and reports; tenants see only their own objects |

**Design guidance:**

- Use **separate organizations** for hard tenant boundaries (different business units, customers, or compliance domains).
- Use **separate projects** for team or environment separation within one tenant (dev/test/prod).
- Pair management-plane isolation with **network** isolation. RBAC alone does not stop traffic between workloads.
- For strict compliance, consider dedicated workload domains, clusters, or edge clusters per tenant.

## 4. Cloud Templates (Blueprints)

### 4.1 What they are

A **Cloud Template** (called a **Blueprint** in newer releases) is a **declarative YAML** definition of the resources a deployment should contain: machines, networks, storage, load balancers, security groups, and custom resources, along with their relationships.

You can author them in a **canvas (drag-and-drop)** designer or edit **YAML** directly. Both views stay in sync.

### 4.2 Anatomy

```yaml
formatVersion: 1
inputs:
  size:
    type: string
    title: T-shirt size
    enum:
      - small
      - medium
    default: small
  env:
    type: string
    enum: [dev, prod]
resources:
  Web_Net:
    type: Cloud.Network
    properties:
      networkType: existing
      constraints:
        - tag: 'net:web'
  Web_VM:
    type: Cloud.Machine
    properties:
      image: ubuntu-22
      flavor: '${input.size}'
      constraints:
        - tag: 'env:${input.env}'
      networks:
        - network: '${resource.Web_Net.id}'
          assignment: static
      cloudConfig: |
        #cloud-config
        packages: [nginx]
```

### 4.3 Key concepts

| Concept | Meaning |
|---|---|
| **Inputs** | User-supplied values at request time (dropdowns, text, numbers) |
| **Resources** | Objects to provision (`Cloud.Machine`, `Cloud.Network`, `Cloud.Volume`, `Cloud.SecurityGroup`, `Cloud.LoadBalancer`, and more) |
| **Bindings / expressions** | ``{resource.X.property}` and ``{input.Y}` create dependencies and ordering |
| **Constraints** | Tag-based placement rules (`hard` or `soft`) that match infrastructure tags |
| **Flavor mappings** | Map abstract sizes (small/medium) to CPU/memory per region |
| **Image mappings** | Map abstract image names to real templates/images per region |
| **Network profiles** | Define networks, IP ranges, isolation and security settings, load balancers |
| **Storage profiles** | Define datastore/policy, disk type, and tag-based selection |
| **Versioning** | Save versions and release them to the catalog |
| **Day-2 actions** | Power, resize, snapshot, add disk, and custom actions after deployment |

### 4.4 Lifecycle

1. **Author** the template in a project.
2. **Test** with a deployment from the design canvas.
3. **Version** and **release** a version.
4. **Publish** to the catalog (via content sources / sharing) and **entitle** projects or users.
5. **Request** from the catalog, then **approve** (if an approval policy applies).
6. **Provision** (placement, naming, extensibility hooks).
7. **Operate** with Day-2 actions, leases, and lifecycle policies.
8. **Destroy / reclaim** at lease end.

### 4.5 Governance policies

- **Lease policies** (automatic expiry and reclamation)
- **Approval policies** (require approval by user or role)
- **Day-2 action policies** (which users can run which actions)
- **Resource quota policies** (limit consumption)
- **Deployment limit policies**
- **Naming policies**

## 5. Custom Resources and Extensibility

### 5.1 Why custom resources

Built-in resource types cover infrastructure. **Custom resources** let you model *anything else* as a first-class object in a template, such as a DNS record, an IPAM reservation, a ticket, a database in an external system, or a certificate.

### 5.2 How a custom resource is built

1. **Define the resource type**, including its schema (properties, types, required fields).
2. **Attach lifecycle actions** (Create, Read, Update, Delete) backed by:
   - **Orchestrator (vRO) workflows**, or
   - **ABX actions** (serverless scripts in Python, Node.js, PowerShell)
3. **Use the resource** in a template like any other (it can be bound to other resources via expressions).
4. **Add Day-2 resource actions** if needed (e.g., "Renew certificate").

Example usage in a template:

```yaml
resources:
  DNS_Record:
    type: Custom.DNSRecord
    properties:
      hostname: '${resource.Web_VM.resourceName}'
      address: '${resource.Web_VM.address}'
```

### 5.3 Extensibility options compared

| Mechanism | Best for | Notes |
|---|---|---|
| **Orchestrator workflows** | Complex, multi-step, reusable enterprise logic | Rich plug-in library; uses its own runtime |
| **ABX actions** | Lightweight scripts, API calls | Serverless-style; faster to author |
| **Event subscriptions (Event Broker)** | Hook into lifecycle phases (e.g., pre-compute allocation, post-provision) | Blocking vs. non-blocking matters |
| **Custom forms** | Tailor the request UI | Dynamic visibility, value pickers, external value sources |
| **Terraform / Ansible integrations** | Reuse existing IaC and config management | Terraform integration runs through configured runners/integrations |

### 5.4 Blocking vs. non-blocking subscriptions

- **Blocking:** the deployment waits for the action to finish; it can change the outcome or fail the request.
- **Non-blocking:** fire-and-forget (notifications, logging).

## 6. Cloud Consumption: The Service Catalog

- **Content sources** (templates, Orchestrator workflows, marketplace items, Git-based content) feed the catalog.
- **Content sharing** and **entitlements** control which projects/users see which items.
- **Custom forms** present a user-friendly request experience.
- Consumers request an item, optionally pass through approval, and monitor in **Deployments**.
- **Day-2 operations** are available per resource type and governed by policy.

**Admin workflow summary:**

```
Infrastructure ready → Region/Zones & profiles → Project → Template (version/release)
→ Content source → Share/entitle → Policies → Consumer requests → Deployment
```

## 7. Operational Considerations

| Area | What to know |
|---|---|
| **Capacity planning** | Quotas and zone allocations prevent one tenant from starving another; monitor with VCF Operations |
| **Cost transparency** | Pricing cards and showback/chargeback reporting at project/org level (via Operations) |
| **Backup/DR** | Back up VCF Automation and its dependencies as part of the fleet; follow documented procedures for your version |
| **Lifecycle** | Upgrade through the VCF-supported lifecycle process; keep Automation compatible with the VCF release |
| **Certificates & identity** | Plan certificate renewal and identity source health; expired certs break integrations |
| **Logging** | Use VCF Operations for Logs (or your syslog target) for troubleshooting provisioning |

### Common troubleshooting scenarios

| Symptom | Likely cause | Check |
|---|---|---|
| Deployment fails at placement | No zone/profile matches constraints | Tags on compute, network and storage vs. template constraints; project zone assignment |
| Image/flavor not found | Missing image/flavor mapping for that region | Mappings per region |
| Request exceeds limit | Quota or deployment limit policy | Policies scoped to the project/org |
| User cannot see a catalog item | Not entitled, or wrong project role | Content sharing/entitlements and membership |
| Custom resource stuck | Failing workflow/ABX action | Execution logs for the action or workflow run |
| Tenant sees another tenant's network | Misconfigured shared network profile | Network isolation settings, VPC/tier-1 design |

## 8. Exam Tips

1. **Know the hierarchy cold:** Provider → Organization → Project → Deployment. Org is the *hard* boundary; project is the *working* boundary.
2. **Tags drive placement.** If a question mentions a deployment failing to place, think *constraint tag vs. capability tag mismatch* first.
3. **Mappings are per region.** Flavor and image mappings abstract the infrastructure; missing mappings are a classic failure cause.
4. **Templates are declarative YAML.** Be able to read a short snippet and identify inputs, resources, and bindings.
5. **Custom resource vs. custom property vs. custom form:** a resource is an object with lifecycle; a property is a key/value; a form is UI.
6. **Blocking subscriptions can fail or delay a request;** non-blocking cannot.
7. **RBAC alone ≠ network isolation.** Pair identity scoping with NSX segmentation/VPCs.
8. **Terminology drift:** Cloud Template = Blueprint (newer name); Aria Automation = VCF Automation; Aria Operations = VCF Operations. Don't get tripped up by either name.
9. **Read for scope words:** "provider," "organization," "project," "deployment" each point to a different answer.
10. **Eliminate extremes.** Answers that grant tenants infrastructure-level access (e.g., direct vCenter admin) usually contradict the self-service model.

## 10. Practice Questions

### Question 1

A VCF administrator manages a platform used by two business units that must have **completely separate users, catalogs, policies, and capacity allocations**. Within each business unit, development and production teams need separate access to resources. Which design BEST meets these requirements?

- **A.** One organization with one project and tag-based constraints for each team
- **B.** One organization per business unit, with separate projects for development and production within each
- **C.** One organization per team (four total), sharing a single catalog
- **D.** One project per business unit, with environments separated by custom properties

<details>
<summary>Answer and Explanation</summary>

**Correct answer: B**

The organization is the hard tenant boundary: separate users, catalog, policies, and capacity. Each business unit therefore gets its own organization. Inside each org, **projects** separate dev and prod teams (different members, quotas, zones, and constraints).

- **A** fails: a single org cannot provide separate catalogs, users, and policies per business unit.
- **C** over-segments and a shared catalog contradicts the requirement for separate catalogs.
- **D** places both business units without an org boundary (or relies on custom properties, which are not an isolation mechanism).

**Exam takeaway:** Org = hard boundary between tenants. Project = team/environment boundary within a tenant.
</details>

### Question 2

A user requests a catalog item from a project. The deployment fails during placement with a message indicating that **no matching resources were found**. The Cloud Template contains the following snippet:

```yaml
Web_VM:
  type: Cloud.Machine
  properties:
    image: ubuntu-22
    flavor: medium
    constraints:
      - tag: 'env:prod'
```

The project is assigned to a zone, and other templates without the constraint deploy successfully. What is the MOST likely cause?

- **A.** The user does not have the Viewer role in the project
- **B.** No compute resources in the project's assigned zone carry a matching `env:prod` capability tag
- **C.** The lease policy for the project has expired
- **D.** The custom form is missing a value picker

<details>
<summary>Answer and Explanation</summary>

**Correct answer: B**

Constraints in a template are matched against **capability tags** on the infrastructure (compute, network, storage via zones and profiles). Other templates deploy fine, so the project, zone, and mappings work. The only difference is the `env:prod` hard constraint, so the likely issue is that nothing in the zone/profile carries that tag.

- **A** would block requesting entirely rather than fail at placement. A Viewer typically could not request at all.
- **C**: lease policies affect deployment expiry, not initial placement.
- **D**: a form issue would affect input, not placement.

**Troubleshooting path:** check tags on the cloud zone compute, network profile, and storage profile, and confirm the hard/soft setting of the constraint.
</details>

---

### Question 3

An administrator wants a Cloud Template to automatically create a **DNS record in an external system** after a VM is provisioned, make the record destroyable when the deployment is deleted, and expose a Day-2 action named "Update Address." Which approach is MOST appropriate?

- **A.** Add a custom property named `dns` to the VM and rely on guest scripts
- **B.** Create a custom resource type with Create/Delete lifecycle actions (Orchestrator workflow or ABX) and a Day-2 resource action, then reference it in the template
- **C.** Create a non-blocking event subscription that sends an email to the DNS team
- **D.** Add a second Cloud.Machine to the template to run DNS commands

<details>
<summary>Answer and Explanation</summary>

**Correct answer: B**

The requirement is an externally managed object with a **full lifecycle** (create on deploy, delete on destroy) plus a **Day-2 action**. That is exactly what a **custom resource** provides. It is bound to the VM through expressions (such as `${resource.Web_VM.address}`), is tracked in the deployment, and is cleaned up when the deployment is deleted.

- **A**: a custom property is only a key/value; it has no lifecycle or external integration.
- **C**: a non-blocking subscription is fire-and-forget; it neither tracks the object nor deletes it.
- **D**: an extra VM is wasteful and does not provide lifecycle tracking in the deployment.

**Exam takeaway:** If the object needs create/read/update/delete behavior and Day-2 actions, think custom resource.
</details>
