> **Instructor note:** LCM is one of the most heavily scenario-driven areas on the exam. You are rarely asked "what is a bundle?" You are asked *"what do you do first, what order, and why did it fail?"* Learn the **sequence** and the **pre-check logic**, not just the vocabulary.
→
> **Version caveat:** VCF's LCM tooling has evolved (SDDC Manager-centric in 4.x/5.x; VCF Operations-based fleet management and the VCF Installer/Download tooling arrive in 9.0). Concepts below are stable across releases, but **menu names, tool names, and exact flags change**. Always cross-check against the exam guide and the Broadcom TechDocs for the release your exam targets.

## 1. Learning Objectives


<AccordionGroup type="single">
<AccordionItem title="Deep-Dive: Strict SDDC Manager Upgrade Sequencing Order">

When applying a full-stack VCF upgrade, SDDC Manager enforces a strict dependency pipeline to prevent management disconnects:

1. **SDDC Manager Appliance** (Upgraded first)
2. **NSX Manager Cluster & Edge Nodes**
3. **vCenter Server Appliance** (Management Domain)
4. **ESXi Hypervisor Hosts** (Rolling maintenance mode)
5. **vSAN Disk On-Disk Format Upgrade**

**Why this order matters:**

* Upgraded NSX Managers remain backwards compatible with older vCenters and older ESXi vibs.
* Upgrading ESXi before vCenter would leave vCenter unable to communicate with hosts running a newer hypervisor build.
* Disk format upgrades happen only after all hosts in the vSAN cluster are running the newer ESXi version.

</AccordionItem>

</AccordionGroup>

4. Run and interpret **pre-checks** before an upgrade.
5. Explain the purpose and workflow of the **Async Patch Tool**.
6. State the correct **upgrade sequence** for SDDC Manager, NSX, vCenter, and ESXi, and the management-vs-workload-domain ordering.
7. Troubleshoot common LCM failures.

## 2. Core Concepts

### 2.1 The Bill of Materials (BOM)

Every VCF release is a **validated, interoperable set of component versions**: ESXi, vCenter, NSX, vSAN, SDDC Manager, and (depending on release) the operations/automation/logging stack.

- The BOM is the "known-good combination" VMware/Broadcom has tested.
- LCM's job is to move a domain from one BOM to the next in a **supported, ordered, automated** way.
- **Do not upgrade components individually through their native UIs** (e.g., upgrading vCenter by hand from the VAMI). SDDC Manager's inventory and compatibility logic will become out of sync, and you risk an unsupported state.

### 2.2 Who does the work?

| Function | Component |
|---|---|
| Downloads and stores bundles, orchestrates upgrades | **SDDC Manager** (LCM service) |
| Per-cluster ESXi image/baseline orchestration | **vSphere Lifecycle Manager (vLCM)**, driven by SDDC Manager |
| Tracks what is deployed and what is compatible | SDDC Manager inventory + compatibility data |

---

## 3. Update Bundles

A **bundle** is a signed package SDDC Manager uses to update one or more components.

### 3.1 Bundle types

| Type | What it is | Typical use |
|---|---|---|
| **Install bundle** | Contains software to *deploy* a new component (e.g., add a new product or workload domain component) | New deployments |
| **Upgrade bundle** | Moves a component to a **new BOM version** (release-level upgrade) | Planned release upgrades |
| **Patch / async patch bundle** | Fixes (often security) for a **single component** released *between* VCF releases | Out-of-cycle fixes without a full BOM upgrade |

### 3.2 How bundles arrive

1. **Online depot (connected):** SDDC Manager is registered with the Broadcom depot using the account/download token and pulls bundle metadata and downloads automatically or on demand.
2. **Offline / dark-site:** Use the supported offline download utility (Offline Bundle Transfer Utility in 4.x/5.x; the VCF Download Tool in newer releases) on an internet-connected host, then move bundles to SDDC Manager.
3. **Manual upload:** Upload a bundle file directly to SDDC Manager.

### 3.3 Bundle lifecycle in the UI (conceptual)

```
Available  ->  Downloading  ->  Downloaded  ->  Schedule/Apply update  ->  Applied
```

- A bundle must be **downloaded** before it can be applied.
- SDDC Manager shows only bundles **applicable** to your current BOM and what it detects as the next valid hop.
- **Skip-level / multi-hop:** Some releases support skipping intermediate versions; others require stepping through each. Check release notes. If a hop is required, SDDC Manager will only offer the next valid bundle.

## 4. Pre-Checks

**Rule of thumb: never click "Update Now" without a clean pre-check.**

### 4.1 What a pre-check validates

| Area | Examples |
|---|---|
| **Compatibility** | Target version supported by current BOM, hardware on the HCL, firmware/driver compatibility |
| **Component health** | vCenter services, NSX Manager cluster status, Edge nodes, transport nodes |
| **Hosts / clusters** | Connectivity, can enter maintenance mode, **DRS enabled and set so VMs can evacuate**, no stuck vMotion blockers (e.g., attached ISOs, passthrough devices) |
| **vSAN** | Cluster health, no resyncing objects, enough capacity for a rolling evacuation |
| **Credentials** | Expired or out-of-sync passwords managed by SDDC Manager, broken SSH/API access |
| **Backups/state** | Recent successful backups, adequate free disk space on appliances |
| **Time/DNS/certs** | NTP drift, forward/reverse DNS, expired certificates |

### 4.2 How to run

- In SDDC Manager: **Workload Domains → (domain) → Updates/Patches tab → Run Precheck** (choose the target version/components).
- Also available via **API** (useful for automation and CI-style readiness checks).
- Results: **Pass / Warning / Fail**. Resolve failures; evaluate warnings; **re-run** until clean.

### 4.3 Manual prep checklist (instructor's "flight checklist")

- [ ] Verify the **target BOM** and read the release notes (known issues!).
- [ ] Confirm **interoperability** with add-ons (backup tools, monitoring, third-party plugins, HCX, etc.).
- [ ] **Back up** SDDC Manager, NSX Manager, and vCenter (and confirm backup success).
- [ ] Take **snapshots/restore points** where supported (SDDC Manager also snapshots some appliances during upgrade).
- [ ] Verify DRS and HA are healthy; no hosts in maintenance mode or with unresolved alarms.
- [ ] Clear vSAN resyncs; verify capacity for one host failure *during* the upgrade.
- [ ] Confirm **free space** on appliances and datastores.
- [ ] Confirm **password/credential** status in SDDC Manager.
- [ ] Schedule a **maintenance window**; notify stakeholders.
- [ ] Verify firmware/driver compatibility against the HCL (vendor-specific ISO or cluster image if required).

## 5. The Async Patch Tool

### 5.1 Why it exists

VCF releases are infrequent, but critical fixes for **individual components** (e.g., an ESXi, vCenter, or NSX security patch) can arrive more often. Waiting for the next full VCF BOM could leave you exposed.

The **Async Patch Tool (AP CLI)** lets you obtain and apply those **component-level patches** *through SDDC Manager* while staying in a **supported** state.

### 5.2 Key characteristics

- Delivers **patch** bundles, **not** BOM upgrades.
- Applied through SDDC Manager's normal LCM workflow (so inventory remains accurate).
- Works at **component** granularity: patch vCenter without moving everything else.
- Results in a **patched BOM state** that SDDC Manager understands (it can differ from the published release BOM).
- In newer releases, many async patches are published **directly in the SDDC Manager Updates view** via the depot; the CLI is mainly for cases where the patch is not surfaced there (e.g., restricted/dark-site environments or specific components).

### 5.3 Typical workflow (conceptual)

```
1. Identify the advisory / patch (e.g., a security advisory for vCenter).
2. Download and run the Async Patch Tool (on a host with access to SDDC Manager
   and/or the depot, per the tool's documentation).
3. Tool lists available async patches for the components in your environment.
4. Download the selected patch bundle(s).
5. Upload/make available to SDDC Manager (if not directly downloaded there).
6. Run PRE-CHECK on the target domain.
7. Apply via SDDC Manager (schedule it or run now).
8. Validate: component versions, health, and re-run pre-check/inventory sync.
```

### 5.4 Exam-relevant points

- **When** to use it: urgent component-level fix between releases.
- **Where** it is applied: **SDDC Manager** (not by patching the product manually).
- **Not** a replacement for planned BOM upgrades; plan to converge on the next full release.
- Confirm the **patch is applicable** to your current version (the tool/SDDC Manager filters).

## 6. Upgrade Sequence Order

### 6.1 The golden order (VCF 4.x/5.x model)

```
      Management Domain first
                |
                v
  +----------------------------+
  | 1. SDDC Manager (and its   |
  |    LCM/Domain Manager      |
  |    services)               |
  +-------------+--------------+
                v
  +----------------------------+
  | 2. NSX                     |
  |    a) Edge clusters        |
  |    b) Host (transport node)|
  |       clusters             |
  |    c) NSX Manager cluster  |
  +-------------+--------------+
                v
  +----------------------------+
  | 3. vCenter Server          |
  +-------------+--------------+
                v
  +----------------------------+
  | 4. ESXi (cluster by        |
  |    cluster, rolling, w/    |
  |    vSAN where applicable)  |
  +-------------+--------------+
                v
  +----------------------------+
  | 5. Add-on/other components |
  |    (operations/automation  |
  |    stack, per BOM)         |
  +----------------------------+
                |
                v
      Then VI Workload Domains
      (same order: NSX -> vCenter -> ESXi)
```

**Memory aid:** **S**ome **N**ew **V**CF **E**ngineers: **S**DDC Manager → **N**SX → **v**Center → **E**SXi.

### 6.2 Why this order?

| Step | Reason |
|---|---|
| **SDDC Manager first** | It is the orchestrator. It must understand the *newer* BOM and bundles to drive everything else. |
| **NSX before vCenter** | Newer NSX remains compatible with the existing vCenter/ESXi; the networking control plane is updated before the virtualization management layer. |
| **vCenter before ESXi** | **vCenter must be at the same or higher version than the ESXi hosts it manages.** Never upgrade hosts past their vCenter. |
| **ESXi last** | Hosts are the most disruptive (rolling maintenance mode); do them last once management planes are ready. |

### 6.3 Ordering within NSX

1. **Edge clusters** (data plane for north-south)
2. **Host clusters** (NSX VIBs/transport nodes on ESXi)
3. **NSX Manager cluster** (management/control plane)

→ In SDDC Manager you can usually choose to upgrade the Edge, host, and Manager parts of NSX in stages; the UI enforces the order.

### 6.4 Domain ordering

- **Management domain first**, then **VI workload domains**.
- A workload domain must not run a **higher** version than the management domain's SDDC Manager can manage; respect the compatibility matrix.
- Workload domains can be upgraded **independently of one another** (once management is ready), and ESXi clusters within a domain can be upgraded **one at a time**.

### 6.5 VCF 9.0 note

VCF 9.0 introduces new operational tooling (VCF Operations, fleet-level lifecycle for the operations/automation stack, new installer and download tooling, and mandatory image-based lifecycle for clusters). The **core ordering principle is unchanged**: the orchestration/management layers move first, then NSX, then vCenter, then ESXi, and management domain before workload domains. Verify the exact fleet-level order (which VCF Operations components go first) in the official 9.0 upgrade documentation.

### 6.6 ESXi upgrade behavior

- **Rolling:** Hosts enter maintenance mode one (or a configured number) at a time; DRS migrates VMs.
- **Image-based (vLCM):** Cluster image = base ESXi + vendor add-on + firmware/driver components. Compliance is checked against the desired image.
- **Parallel host upgrades** can be enabled where capacity permits (shortens window, reduces redundancy).
- Optional **Quick Boot** can reduce reboot time on supported hardware.
- If a host fails the upgrade, SDDC Manager stops; fix the cause and **retry**; it resumes from the failed task.

## 7. Execution and Validation Workflow

```
1. Verify BOM/target + release notes
2. Back up (SDDC Manager, NSX, vCenter)
3. Download bundles (online/offline/manual)
4. Run PRE-CHECK -> fix -> re-run until clean
5. Upgrade in order: SDDC Manager -> NSX -> vCenter -> ESXi
6. Post-checks: component versions, alarms, vSAN health, NSX status, backups
7. Re-run pre-check / confirm inventory shows the new BOM
8. Document and re-baseline backups
```

### Scheduling
- You can **schedule** an update for the maintenance window.
- Updates run as **tasks**; you can monitor, **retry**, and view subtasks and logs in SDDC Manager.

## 8. Troubleshooting Cheat Sheet

| Symptom | Likely cause | Action |
|---|---|---|
| Bundle not visible | Not applicable to current BOM, depot credentials/token invalid, or prior hop missing | Check version path, depot connectivity/auth, release notes |
| Download fails | Proxy/firewall, expired token, disk full on SDDC Manager | Fix connectivity/auth, check free space |
| Pre-check fails on host | Cannot enter maintenance mode (DRS off, VM pinned, ISO attached) | Disconnect media, enable DRS, remove blockers |
| vSAN-related failure | Resync in progress or insufficient capacity | Wait for resync, restore health, free capacity |
| Upgrade task stuck/failed | Service/connectivity/credential issue | Read the failed subtask, fix, then **retry** (do not restart from scratch) |
| Credential errors | Rotated or expired passwords out of sync with SDDC Manager | Remediate/update credentials in SDDC Manager |
| Certificate or DNS errors | Expired cert, bad forward/reverse DNS | Correct and re-run pre-check |

**Logs:** SDDC Manager LCM logs (e.g., under `/var/log/vmware/vcf/lcm/`), the task's subtask details in the UI, and the component's own logs (vCenter, NSX, ESXi `vmkernel`/`esxupdate`). Confirm the current log paths for your release.

## 9. Exam Tips

1. **Order, order, order.** "SDDC Manager → NSX → vCenter → ESXi." Management domain before workload domains.
2. **vCenter must be ≥ ESXi version.** If a question describes upgrading ESXi before vCenter, it is wrong.
3. **Use SDDC Manager for upgrades.** Answers involving manual in-product upgrades (VAMI, standalone installers, direct NSX upgrade coordinator) are traps in VCF context.
4. **Pre-check first.** If a scenario asks for the *first* action before an upgrade, think **verify BOM, backup, and pre-check**.
5. **Async Patch Tool = component patching between releases**, through SDDC Manager. Not for full BOM upgrades.
6. **Bundle types:** Install ≠ Upgrade ≠ Async patch. Know when each applies.
7. **Dark site?** Think offline download tool + manual upload to SDDC Manager.
8. **Failed upgrade?** Fix the root cause, then **retry**. Do not manually "fix" components in ways that desync inventory.
9. **DRS and maintenance mode** are the most common host-upgrade blockers.
10. **NSX internal order:** Edges → Hosts → Manager.
11. **Read the verbs.** "Most efficient," "least disruptive," "supported" each point to different answers; "supported" always implies using SDDC Manager.
12. **Version-specific questions:** If the question mentions a specific VCF version, answer for *that* version's tooling and UI names.

## 10. Practice Questions

### Question 1
An administrator must apply an urgent security fix to vCenter Server in a VCF management domain. The fix was released as a component-level patch between VCF releases, and the organization is not ready to move to the next full VCF release. What is the **best supported approach**?

- A. Download the vCenter patch ISO and apply it manually through the vCenter VAMI.
- B. Obtain the async patch bundle using the Async Patch Tool/depot, run a pre-check, and apply it through SDDC Manager.
- C. Wait for the next full VCF BOM release and upgrade all components together.
- D. Remove vCenter from SDDC Manager inventory, patch it manually, and re-add it.

**Answer: B**

<details>
<summary>Explanation</summary>
**Explanation:** Async patches exist precisely so you can fix individual components between VCF releases while remaining in a supported state. They are applied **through SDDC Manager**, preceded by a pre-check, so inventory and compatibility tracking stay accurate. **A** and **D** bypass SDDC Manager, causing inventory drift and an unsupported configuration. **C** leaves the environment exposed to a known vulnerability when a supported mitigation is available.
</details>
---

### Question 2
A VCF administrator is planning a full BOM upgrade of the management domain. Which sequence is **correct**?

- A. ESXi → vCenter → NSX → SDDC Manager
- B. vCenter → NSX → ESXi → SDDC Manager
- C. SDDC Manager → NSX → vCenter → ESXi
- D. NSX → SDDC Manager → ESXi → vCenter

**Answer: C**

<details>
<summary>Explanation</summary>
**Explanation:** SDDC Manager is upgraded first because it orchestrates the rest of the lifecycle and must understand the new BOM. NSX follows, then vCenter, and ESXi last. The key rule is that **vCenter must run an equal or higher version than the ESXi hosts it manages**, which rules out any option that puts ESXi before vCenter (A, B, D). The management domain is upgraded before VI workload domains.
</details>
---

### Question 3
During a pre-check for a workload domain ESXi upgrade, SDDC Manager reports that several hosts **cannot enter maintenance mode**. The cluster uses vSAN. Which combination of actions is MOST likely to resolve the issue?

- A. Disable vSAN on the cluster and proceed with the upgrade.
- B. Skip the pre-check and start the upgrade, since SDDC Manager will resolve blockers automatically.
- C. Verify DRS is enabled and able to migrate VMs, detach any ISOs/passthrough devices pinning VMs, confirm vSAN health/resyncs are clear, then re-run the pre-check.
- D. Manually put hosts into maintenance mode with "No data migration" and upgrade them one by one using the ESXi command line.

**Answer: C**

<details>
<summary>Explanation</summary>
**Explanation:** Hosts typically fail the maintenance mode check because VMs cannot be evacuated (DRS disabled or misconfigured, attached media, passthrough/pinned VMs) or because vSAN health/capacity does not support evacuating data safely. The correct approach is to remove those blockers and **re-run the pre-check until it is clean**. **A** is destructive and unsupported. **B** ignores the purpose of the pre-check and will likely fail mid-upgrade. **D** bypasses SDDC Manager, risks vSAN data accessibility, and leaves LCM state inconsistent.
</details>

## 11. Quick Review Summary

| Topic | Key Takeaway |
|---|---|
| **BOM** | Validated set of component versions per VCF release |
| **Bundles** | Install (deploy), Upgrade (new BOM), Async patch (component fix) |
| **Delivery** | Online depot, offline tool for dark sites, or manual upload |
| **Pre-checks** | Run before every update; fix and re-run until clean |
| **Async Patch Tool** | Component-level patching between releases, applied via SDDC Manager |
| **Order** | SDDC Manager → NSX (Edge → Host → Manager) → vCenter → ESXi |
| **Domains** | Management domain first, then VI workload domains |
| **Never** | Upgrade VCF-managed components outside SDDC Manager |
| **Failures** | Fix root cause, then retry the task |
