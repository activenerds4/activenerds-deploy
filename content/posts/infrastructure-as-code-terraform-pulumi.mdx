Infrastructure as code is table stakes — you can't run production infrastructure with click-ops and sleep well at night. The real question is which tool to use. [Terraform](/articles/terraform-module-design-patterns) has been the default for a decade, but Pulumi challenges it by letting you write infrastructure in real programming languages. This [comparison](/articles/devops-tools-benchmark-comparison) helps you decide which fits your team.

## IaC Fundamentals

### Declarative vs Imperative

Both Terraform and Pulumi are declarative at the outcome level — you describe the desired state, and the tool reconciles. But Pulumi lets you use imperative logic (loops, conditionals, functions) to generate that declarative state, while Terraform's HCL has limited programming constructs.

### State Management

Both tools track state — a record of what infrastructure exists. State is how the tool knows what to create, update, or destroy. State management is the #1 operational concern:

- **Terraform** — state stored in a backend (S3, GCS, Terraform Cloud). State file is a JSON file.
- **Pulumi** — state stored in Pulumi Service (SaaS) or self-managed backend (S3, Azure, GCS).

### Drift Detection

Both tools can detect drift (infrastructure changed outside the IaC tool). Terraform has `terraform plan` which shows drift. Pulumi has `pulumi preview` which does the same. Neither auto-remediates drift by default — you review and apply.

## Terraform Deep Dive

### HCL Language

HCL (HashiCorp Configuration Language) is Terraform's DSL. It's declarative with limited programming constructs:

```hcl
resource "aws_instance" "web" {
  count         = 3
  ami           = data.aws_ami.ubuntu.id
  instance_type = var.instance_type

  tags = {
    Name = "web-${count.index}"
    Env  = var.environment
  }
}

# Conditional logic is limited
resource "aws_db_instance" "main" {
  count                  = var.create_db ? 1 : 0
  engine                = "postgres"
  instance_class         = var.db_instance_class
  allocated_storage      = 20
}
```

HCL's simplicity is its strength — anyone can read a Terraform file and understand the infrastructure. Its limitation is that complex logic (loops, data transformations, conditional blocks) becomes verbose and hard to follow.

### Provider Ecosystem

Terraform has the largest provider ecosystem — over 3,000 providers covering every cloud, SaaS, and infrastructure component. If a service has an API, there's probably a Terraform provider.

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
    kubernetes = {
      source  = "hashicorp/kubernetes"
      version = "~> 2.23"
    }
  }
}
```

### Module Registry

The Terraform Registry has thousands of community modules. Verified modules are maintained by cloud providers:

```hcl
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.0.0"

  cidr = "10.0.0.0/16"
  azs  = ["us-east-1a", "us-east-1b", "us-east-1c"]
}
```

## Pulumi Deep Dive

### Real Languages

Pulumi lets you write infrastructure in TypeScript, Python, Go, C#, and Java. This means you can use real programming constructs:

```typescript
import * as aws from "@pulumi/aws";

const zones = ["us-east-1a", "us-east-1b", "us-east-1c"];

// Real loops, not count meta-argument
const webServers = zones.map((zone, i) => new aws.ec2.Instance(`web-${i}`, {
  ami: "ami-12345678",
  instanceType: "t3.micro",
  availabilityZone: zone,
  tags: {
    Name: `web-${i}`,
    Env: environment,
  },
}));

// Conditional logic is just an if statement
if (createDb) {
  const db = new aws.rds.Instance("main", {
    engine: "postgres",
    instanceClass: "db.t3.micro",
    allocatedStorage: 20,
  });
}
```

### Programmatic IaC

Because you're in a real language, you can:
- Use functions and abstractions to reduce repetition
- Write unit tests for infrastructure logic
- Pull configuration from APIs at runtime
- Generate infrastructure from data files (JSON, YAML)

```typescript
// Read config from a JSON file
const config = JSON.parse(fs.readFileSync("environments.json", "utf-8"));

const environments = Object.entries(config).map(([name, cfg]) => {
  return new aws.ec2.Vpc(name, {
    cidrBlock: cfg.cidr,
    enableDnsHostnames: true,
    tags: { Name: name, Env: name },
  });
});
```

### Crosswalk for K8s

Pulumi's Crosswalk for Kubernetes provides higher-level abstractions:

```typescript
import * as k8s from "@pulumi/kubernetes";

const app = new k8s.apps.v1.Deployment("app", {
  spec: {
    replicas: 3,
    template: {
      spec: {
        containers: [{
          name: "app",
          image: "myregistry/app:v1",
          ports: [{ containerPort: 8080 }],
        }],
      },
    },
  },
});

// Automatic Service creation and exposure
const service = app.spec.template.spec.containers[0].ports[0].containerPort.apply(port =>
  new k8s.core.v1.Service("app-svc", {
    spec: { type: "LoadBalancer", ports: [{ port: 80, targetPort: port }] },
  })
);
```

## Feature Comparison

| Feature | Terraform | Pulumi |
|---------|-----------|--------|
| Language | HCL (DSL) | TS, Python, Go, C#, Java |
| State backend | S3, GCS, TFC | Pulumi Service, S3, Azure, GCS |
| Provider count | 3,000+ | 150+ (via bridges) |
| Module ecosystem | Large (Registry) | Growing (Package Registry) |
| Testing | Limited (terratest) | Native (unit test IaC code) |
| Policy as code | Sentinel (paid) | CrossGuard (free) |
| CI/CD | Terraform Cloud or custom | Pulumi GitHub App or custom |
| Cost | Free (OSS) or TFC | Free (OSS) or Pulumi Cloud |

<Callout type="info">
Pulumi bridges Terraform providers, so you get access to the same 3,000+ providers. The bridge isn't perfect — some provider features lag — but it means you're not locked out of any cloud service.
</Callout>

## Choosing Your Tool

### Choose Terraform if:

- Your team includes non-developers (ops, sysadmins) who need to read/write IaC
- You want the largest module ecosystem and community knowledge base
- You need verified cloud provider modules
- Your infrastructure logic is straightforward (no complex conditionals)
- You want the most battle-tested tool with the largest hiring pool

### Choose Pulumi if:

- Your team is developer-heavy and prefers real languages
- You have complex infrastructure logic that HCL makes painful
- You want to unit test infrastructure code
- You're managing K8s resources alongside cloud resources
- You need programmatic infrastructure (generating from data, API-driven)

<Callout type="tip">
**Movement break:** Infrastructure code reviews are dense. After reviewing a Terraform plan or Pulumi preview, stand up and walk to the farthest point in your office or home. The physical distance gives your brain a break from the YAML/JSON/HCL parsing and helps you catch issues you'd miss when fatigued.
</Callout>

### Migration Considerations

Migrating between the two is non-trivial. Both use state files, but the formats differ. Tools like `pulumi convert` can translate Terraform to Pulumi, but the output needs manual cleanup. The safest approach is to migrate incrementally — adopt the new tool for new projects and migrate existing infrastructure as you touch it.

## Summary

Terraform is the safe, proven choice with the largest ecosystem. Pulumi is the modern choice for teams who want to bring software engineering practices (testing, abstraction, real languages) to infrastructure. Neither is wrong — the right choice depends on your team's skills and the complexity of your infrastructure logic. Start with the one that matches your team's existing strengths.
