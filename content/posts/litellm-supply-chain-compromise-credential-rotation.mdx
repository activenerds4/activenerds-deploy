<Callout variant="danger" title="Urgent Practitioner Advisory">
If your production stacks, local development machines, or CI/CD pipelines installed **`litellm==1.107.0`** between its release on PyPI and subsequent yank/quarantine, treat all credentials accessible to that environment as **compromised**. Immediate credential rotation and forensic container audits are required.
</Callout>

LiteLLM has become the de facto lightweight unified proxy gateway for routing requests across OpenAI, Anthropic, Bedrock, Vertex AI, and local LLM backends. Its position in modern AI platform architectures makes it an exceptionally high-value target: it typically holds master API keys, cloud IAM credentials, database connection strings, and vector database auth tokens.

A critical supply chain attack targeting **LiteLLM version 1.107.0** demonstrated how adversaries leverage Python startup hooks (`sitecustomize.py` / `.pth` files) to achieve persistence and exfiltrate secrets before security tooling or application logic even boots. Here is a technical breakdown of what occurred, how to audit your environment, and the precise credential rotation workflow you must execute.

---

## 1. What Happened: Timeline and Affected Versions

The compromise stemmed from an attacker gaining unauthorized publish privileges to the LiteLLM PyPI package repository, uploading a trojanized release tagged as `1.107.0`.

| Event Phase | Date / Time (UTC) | Incident Event Detail |
|---|---|---|
| **Unauthorized Publish** | Oct 21, 2026 | Malicious package `litellm==1.107.0` uploaded to PyPI containing an embedded post-install hook. |
| **Active Exfiltration** | Oct 21 – Oct 23, 2026 | Automated AI pipelines, Docker builds without strict hash pinning, and developer laptops pulled the trojanized version. |
| **Detection & Disclosure** | Oct 23, 2026 | Microsoft Security Threat Intelligence published their technical report on credential theft via Python startup hooks. |

| **Hardening Architecture** | Oct 30, 2026 | LiteLLM announced foundational security overhauls: signed PyPI provenance (SLSA Level 3), automated secret scanning, and reduced default container permissions. |

## 2. How the Python Startup-Hook Credential Theft Works

Unlike traditional malware that relies on suspicious network sockets opened during runtime or obfuscated `exec()` calls inside library functions, this payload exploited **Python's native interpreter initialization hooks**:

```
+--------------------------------------------------------------+
|                    Python Interpreter Init                   |
+------------------------------+-------------------------------+
                               |
                               v
                     +--------------------+
                     |  site.py Execution |
                     +---------+----------+
                               | Scans site-packages for *.pth
                               v
                     +--------------------+
                     | Malicious .pth Hook| ---> (Executes arbitrary Python code)
                     +---------+----------+
                               | Reads os.environ & ~/.aws, ~/.azure
                               v
                     +--------------------+
                     | Encrypted Exfil    | ---> C2 Server (Cloudflare worker / webhook)
                     +--------------------+
```

### The `.pth` Mechanism

When Python starts up, the built-in `site` module processes all directories in `sys.path`. If it encounters a `.pth` file, lines starting with `import ` are executed automatically:

```python
# Disguised .pth entry placed in site-packages
import os, sys, base64; exec(base64.b64decode("...malicious_payload..."))
```

Because this runs before your application script (`main.py`, `app.py`, or `uvicorn`) even executes its first line of code:
1. **Application-level guards** (e.g., custom secret masking or telemetry) are completely bypassed.
2. The payload inherits full access to all environment variables (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `AWS_SECRET_ACCESS_KEY`, `DATABASE_URL`).
3. It scans local user directories for cloud CLI credentials (`~/.aws/credentials`, `~/.azure/accessTokens.json`, `~/.config/gcloud/`).

## 3. Am I Affected? Diagnostic Audit Commands

Run the following checks across all Kubernetes nodes, container image registries, CI runners, and developer environments.

### Step 3.1: Check Installed Package Versions

```bash
# Check virtual environment or active container
python3 -m pip list | grep -E "litellm"

# Or check poetry / pipenv lockfiles
poetry show litellm 2>/dev/null || pipenv graph | grep litellm
```

If you discover `litellm==1.107.0`, **mark the machine or container pod as compromised immediately**.

### Step 3.2: Inspect Site-Packages for Rogue `.pth` Files

```bash
python3 -c '
import site, os, glob
site_dirs = site.getsitepackages() + [site.getusersitepackages()]
for d in site_dirs:
    if os.path.exists(d):
        pths = glob.glob(os.path.join(d, "*.pth"))
        for p in pths:
            print(f"[CHECK] {p}")
            with open(p, "r", errors="ignore") as f:
                content = f.read()
                if "import " in content and ("exec(" in content or "base64" in content):
                    print(f"  [ALERT - SUSPICIOUS HOOK DETECTED]: {p}\n  --> {content.strip()}")
'
```

### Step 3.3: Indicators of Compromise (IoCs)

- **Outbound HTTP/DNS requests** to unapproved ephemeral domains, custom Cloudflare worker routes, or paste sites during container startup.
- Unexpected presence of `.pth` or `sitecustomize.py` files in `/usr/local/lib/python3.x/site-packages/` modified between Oct 21 and Oct 24, 2026.
- Sudden spikes in API token usage across your provider billing dashboards (OpenAI, Anthropic, Groq, Cohere) originating from non-gateway IP ranges.

## 4. Credential Rotation Checklist

If version `1.107.0` was present in any tier of your infrastructure, do not merely update the package version—**every secret exposed to that execution context must be revoked and rotated**.

```
[ ] 1. Revoke and rotate all LLM Provider API Keys:
    - OpenAI Organization & Project Keys
    - Anthropic Admin and User API Keys
    - Cohere, Mistral, Groq, Perplexity, Together AI tokens
    - HuggingFace access tokens with write/read privileges

[ ] 2. Rotate Cloud Provider IAM Credentials:
    - AWS IAM Access Keys and Session Credentials exposed via env vars
    - Azure Service Principal client secrets
    - GCP Service Account JSON keys mounted in the pod

[ ] 3. Invalidate Database and Vector Store Tokens:
    - Pinecone, Weaviate, Qdrant, Milvus API keys
    - PostgreSQL / Redis connection URIs (especially if containing raw passwords)

[ ] 4. Invalidate Session Storage & Internal JWT Secrets:
    - LITELLM_MASTER_KEY
    - JWT signing keys used by your LiteLLM proxy auth layer

[ ] 5. Purge Container Base Caches and CI Runners:
    - Clear Docker layer cache on GitHub Actions / GitLab runners
    - Delete and re-pull official base images in private registries
```

## 5. Pinning and Verifying AI Dependencies Going Forward

AI libraries are evolving rapidly, resulting in frequent dependencies and transient releases. To prevent supply chain attacks from breaching your runtime:

### 1. Hash-Pinned Dependency Files

Never rely on unpinned ranges like `litellm>=1.0.0` or bare versions `litellm==1.107.2` without cryptographic hashes. Use `pip-tools` or `uv`:

```bash
# Generate SHA-256 hash-pinned requirements with uv
uv pip compile pyproject.toml --generate-hashes -o requirements.txt
```

Verify that your `requirements.txt` includes strict hashes:

```text
litellm==1.107.2 \
    --hash=sha256:7a4f9104b9015c9d... \
    --hash=sha256:e3b0c44298fc1c14...
```

### 2. Isolate Gateway Network Egress

LiteLLM should only be capable of communicating with known AI provider API endpoints. Restrict pod egress using a Kubernetes `NetworkPolicy` or Cilium egress gateway:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: litellm-restricted-egress
  namespace: ai-gateway
spec:
  podSelector:
    matchLabels:
      app: litellm-proxy
  policyTypes:
    - Egress
  egress:
    # Allow DNS resolution
    - to:
        - namespaceSelector: {}
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - protocol: UDP
          port: 53
    # Restrict external outbound traffic to standard HTTPS on port 443 only
    - ports:
        - protocol: TCP
          port: 443
```

### 3. Run Containers as Non-Root with Read-Only Filesystem

The malicious `.pth` hook required write access to the Python `site-packages` directory. Enforce a read-only root filesystem on your Kubernetes pods:

```yaml
spec:
  containers:
    - name: litellm
      image: ghcr.io/berriai/litellm:main-v1.107.2
      securityContext:
        readOnlyRootFilesystem: true
        runAsNonRoot: true
        runAsUser: 10001
        allowPrivilegeEscalation: false
        capabilities:
          drop:
            - ALL
      volumeMounts:
        - mountPath: /tmp
          name: tmp-volume
  volumes:
    - name: tmp-volume
      emptyDir: {}
```

By enforcing strict cryptographic hash pinning, locking container file systems, and isolating network egress, your AI gateway infrastructure remains protected against malicious upstream releases.
