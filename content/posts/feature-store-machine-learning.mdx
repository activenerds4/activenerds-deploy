One of the most reliable ways to introduce bugs into a production ML system is to compute features one way during training and a slightly different way at serving time. The model was trained on a particular distribution; at inference it sees another. Performance degrades silently, and nobody notices until a metric drops. Feature stores exist to make that class of bug impossible.

## The Training-Serving Skew Problem

Training-serving skew creeps in through innocent-looking differences: a feature computed in a Spark batch job during training, then recomputed in a Python service at serving time, with a subtly different aggregation window or a different handling of nulls. The two implementations look equivalent in code review and produce different numbers in production.

The deeper issue is duplicated logic. When the same feature is defined independently in two places — the training pipeline and the serving application — they drift over time. Someone updates the training version; the serving version stays. Or a timezone assumption differs. The model never sees the data distribution it was trained on.

A feature store solves this by making the feature definition a single, versioned artifact. Both training and serving read from the same definition, computed by the same transformation code. Skew becomes structurally impossible rather than something you have to police.

## Online vs Offline Stores

A feature store is really two stores with a shared definition layer.

The **offline store** serves batch training. It holds large historical feature data and supports point-in-time correctness — when generating training data, each row reflects only the feature values that were known *at that timestamp*, preventing future leakage. This is typically backed by a data warehouse or object storage with a query engine.

The **online store** serves inference. It holds only the latest feature values for each entity and answers low-latency lookups (single-digit milliseconds) so a serving path can enrich a request with features before scoring. This is typically backed by Redis, DynamoDB, or a similar KV store.

The same feature definition materializes into both. The offline store gets the full history; the online store gets a continuously updated latest-value view. The model trains on the offline data and serves against the online data, and because both derive from one definition, the distributions match.

## Tools: Feast and Tecton

**Feast** is the leading open-source feature store. You define features in Python, register them, and materialize between offline and online stores. It's vendor-neutral — you bring your own offline store (BigQuery, Snowflake, Spark) and online store (Redis, DynamoDB). Feast gives you the consistency guarantees without locking you into a platform.

**Tecton** is a fully managed platform built by some of the original Feast authors. It handles the infrastructure, transformation orchestration, and monitoring for you, at the cost of being a paid product with less flexibility. For teams that want the pattern without operating it, Tecton removes most of the toil.

The build-vs-buy decision is mostly about team size and operational appetite. Feast requires you to run materialization jobs, manage the online store, and handle monitoring. Tecton handles all of that. A small ML team often gets more value from buying; a platform team with existing infra often prefers Feast's composability.

## Implementation Patterns

Define features as code, with explicit entity keys (the join key, e.g. `user_id`) and event timestamps. Materialize on a cadence that matches how stale your features can get — real-time features may need streaming ingestion; daily aggregates can materialize once a day.

<Callout type="tip">
Start with the features that are most prone to skew — anything involving time windows, aggregations, or third-party data. Those are where training-serving inconsistency hurts most and where a feature store pays off fastest.
</Callout>

Finally, monitor feature health in production: freshness (is the online store up to date?), null rates, and distribution drift. A feature store makes consistency automatic, but it doesn't make features correct — a broken upstream pipeline still produces broken features, just consistently.
