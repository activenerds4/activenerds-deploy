Most Kubernetes workloads are stateless, and the Deployment controller handles them well: it doesn't care which pod is which, it just wants a certain number of identical replicas running. The moment a workload needs stable identity, ordered startup, or per-pod persistent storage, the Deployment model breaks down — pods get random names, they start in arbitrary order, and they share or fight over storage. That's the gap StatefulSet fills. A StatefulSet gives each pod a stable name, a stable network identity, and its own persistent volume, with ordered rollout and scaling. It's the controller for databases, distributed queues, and any system where the pods are not interchangeable.

This is the practical guide to StatefulSets: why they exist, how identity and storage work, how rollout and scaling behave, and the patterns that use them well.

## Why StatefulSets Exist

The Deployment controller treats pods as a fungible pool. If a pod dies, a new one replaces it with a new name and no memory of the old one. For a stateless web server, this is correct — any pod can serve any request, and identity doesn't matter. For a stateful workload, this is wrong.

**Stateless vs stateful workloads.** A stateful workload has one or more of these properties: each replica has a unique identity that matters (a database primary vs replicas), replicas must start or stop in a specific order (a cluster that elects a leader), each replica needs its own persistent storage that follows it across restarts, or replicas are addressed individually by peers (a peer-to-peer cluster where nodes know each other by name). A Deployment gives you none of these reliably; a StatefulSet gives you all of them.

**The identity problem.** Consider a three-node database cluster where nodes replicate to each other and each node is known by a stable hostname. With a Deployment, pods are named like `db-xyz12`, `db-abc34` — random, changing on every restart. Peers can't reliably address each other, and a pod that restarts gets a new name and loses its place in the cluster's topology. With a StatefulSet, pods are named `db-0`, `db-1`, `db-2` — stable across restarts, with stable DNS names (`db-0.db.default.svc.cluster.local`). Peers address each other by these stable names; a restarted pod comes back with the same identity and the same storage.

**When a Deployment is wrong.** The rule of thumb: if your pods are interchangeable and any can replace any other, use a Deployment. If your pods have individual identity, order dependencies, or per-pod storage, use a StatefulSet. The common mistake is using a Deployment with a shared PVC for a database — it "works" until two pods write to the same volume and corrupt it, or until a pod restarts and loses the data it had because the volume was shared and got overwritten. StatefulSet's per-pod PVCs exist precisely to prevent this.

## Stable Identity and Storage

The two features that define a StatefulSet are stable identity and stable storage, and they work together.

**Stable network names.** Each pod gets a predictable name: `{statefulset-name}-{ordinal}`, starting at 0. A StatefulSet named `db` produces `db-0`, `db-1`, `db-2`. These names are stable for the life of the StatefulSet — if `db-1` is deleted, the controller recreates a pod named `db-1`, not a new random name. Combined with a headless Service (a Service with `clusterIP: None`), each pod gets a stable DNS A record, so peers and clients can address `db-0.db.default.svc.cluster.local` and always reach the same logical pod. This is what makes peer-to-peer clustering possible — nodes know each other by stable address.

**Ordered pod names.** The ordinal naming isn't cosmetic; it encodes creation order. `db-0` is created first, then `db-1`, then `db-2`. On scale-down, the reverse: `db-2` is deleted before `db-1`. This ordering matters for workloads that need a primary to exist before replicas join, or that need ordered shutdown to avoid split-brain. You can relax the ordering with `podManagementPolicy: Parallel` if your workload doesn't need it, which speeds up scale operations for clusters where all pods are equal.

** This is the storage feature. A StatefulSet uses a `volumeClaimTemplates` field to create a separate PersistentVolumeClaim for each pod, bound to that pod's ordinal. `db-0` gets its own PVC, `db-1` gets its own, and so on. When `db-1` restarts, it reattaches to its original PVC — its data persists across restarts because the volume follows the identity, not the pod instance.

This is the fundamental difference from a Deployment with a shared PVC: each pod has its own durable storage, and there's no risk of two pods writing to the same volume. The PVCs are not deleted when the StatefulSet is deleted (by default) — they persist, so you can recreate the StatefulSet and get the data back. This is deliberate: storage outlives the workload definition, because deleting a StatefulSet shouldn't delete your database.

## Rollout and Scaling

StatefulSets have specific rollout and scaling behavior that differs from Deployments and matters for stateful workloads.

**Ordered vs parallel pod management.** The default `podManagementPolicy: OrderedReady` creates pods one at a time, waiting for each to be ready before starting the next. This is the safe default for workloads that need ordered startup (a primary before replicas). `Parallel` creates all pods simultaneously, which is faster but assumes pods don't depend on each other's startup order. For a database cluster that needs a primary elected first, use Ordered; for a cache cluster where all nodes are equal, Parallel is fine and faster.

**Rolling updates.** A StatefulSet rolling update replaces pods in reverse ordinal order, one at a time, waiting for each to be ready before proceeding to the next. So `db-2` is updated first, then `db-1`, then `db-0`. This ordered, one-at-a-time rollout is critical for stateful workloads: it ensures that at most one pod is unavailable at a time, and for a database, it lets you update replicas before the primary, so you can promote an updated replica and update the primary last. The `partition` field lets you pause a rollout partway (only pods with ordinal >= partition are updated), which is useful for canarying a stateful workload update — update one replica, verify, then lower the partition to continue.

** Scale-up adds the next ordinal (if you have 3, scaling to 4 creates `db-3`), and scale-down removes the highest ordinal first. The ordering means scale operations are predictable. The caveat: scale-down does not delete the PVC for the removed pod, by default.

If you scale from 4 to 3, `db-3`'s pod is deleted but its PVC remains — so if you scale back up to 4, the new `db-3` reattaches to the original data. If you want PVCs deleted on scale-down, you must set a retention policy explicitly. This is a deliberate safety choice: Kubernetes assumes you'd rather keep data you might need than delete data you can't recover.

## Common Patterns

StatefulSets are the right tool for a specific set of workloads, and misusing them is a common source of pain.

**Databases on StatefulSets.** This is the canonical use case — PostgreSQL, MySQL, MongoDB, Cassandra, Elasticsearch, etc. Each instance needs its own data, stable identity for replication, and often ordered startup. The pattern: a StatefulSet with per-pod PVCs, a headless Service for stable DNS, and an init pattern where `db-0` initializes as primary and `db-1+` join as replicas. The [operator pattern](/articles/k8s-operators-explained) (see our [Kubernetes operators guide](/blog/k8s-operators-explained)) often wraps this, automating the primary election and failover that a raw StatefulSet doesn't handle — a StatefulSet gives you the identity and storage, but the application logic for leader election and replication is still yours (or an operator's).

**Leader election.** Many stateful clusters need a single primary that the others follow. The StatefulSet's ordered naming makes a simple leader election possible: `db-0` is the primary by convention, and `db-1+` are replicas. If `db-0` fails, the cluster promotes the next available pod. This convention-based approach works but isn't true leader election — for robust failover, use a proper election mechanism (Raft via an operator, a lease in a ConfigMap, or the application's built-in election). The StatefulSet gives you the stable identity that makes election meaningful; it doesn't do the election for you.

**Anti-patterns to avoid.** Don't use a StatefulSet for stateless workloads — the ordered rollout and per-pod PVCs add overhead and complexity you don't need; a Deployment is simpler and faster. Don't use a StatefulSet with a shared PVC — if the storage is shared, the pods are effectively stateless relative to each other and a Deployment is the right tool. Don't assume StatefulSets handle failover — they give you stable identity and storage, but application-level failover (promoting a replica, reconfiguring clients) is your responsibility or an operator's. And don't scale a StatefulSet down expecting data cleanup — PVCs persist by default, so scale-down leaves orphaned PVCs that cost money and clutter the cluster unless you configure a retention policy.

The honest framing: StatefulSets are the controller for workloads where pods have identity and own data, and they're the right tool for databases and distributed systems on Kubernetes. The cost is operational complexity — ordered rollout is slower, per-pod PVCs are more to manage, and failover logic is often application-specific. For stateless workloads, a Deployment is simpler and you should use it. The decision is about whether your pods are interchangeable: if yes, Deployment; if no, StatefulSet. Pair this with [resource quotas and limits](/blog/kubernetes-resource-quotas-limits) to govern the resources stateful workloads consume, and [node affinity and taints](/blog/kubernetes-node-affinity-taints) when stateful pods need to land on specific nodes for storage or performance reasons.
