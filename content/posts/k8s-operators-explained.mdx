If you've been in the Kubernetes ecosystem for any time, you've heard about operators. The Prometheus Operator, the Cert-Manager Operator, the Elasticsearch Operator — they're everywhere. But what exactly is an operator, and when do you actually need one?

## The Operator Pattern

At its core, an operator is just a Kubernetes controller with extra domain knowledge. To understand operators, you first need to understand controllers.

**Controllers in K8s**: Every Kubernetes controller follows a simple pattern — a reconciliation loop:

1. **Observe**: Watch the current state of the cluster
2. **Diff**: Compare current state to desired state
3. **Act**: Make changes to bring current state closer to desired state

The Deployment controller does this for pods. The Service controller does it for network endpoints. An operator does the same thing, but for your custom application.

**Custom Resource Definitions (CRDs)**: Operators extend Kubernetes with new resource types. Instead of just Deployments and Services, you get `PostgresClusters`, `Prometheus` instances, or whatever domain object your operator manages.

```yaml
# A custom resource managed by an operator
apiVersion: postgres-operator.crunchydata.com/v1beta1
kind: PostgresCluster
metadata:
  name: my-database
spec:
  instances: 3
  version: "16"
  backups:
    pgbackrest:
      repos:
        - name: repo1
          schedules:
            full: "0 2 * * *"
```

The operator watches for `PostgresCluster` resources and creates/configures the actual PostgreSQL instances, replicas, backups, and failover logic.

## When You Need an Operator

Not everything needs an operator. Here's a simple decision framework:

**Use Helm or plain manifests when**:
- Your application is stateless
- Configuration changes are infrequent
- You don't need automated failover or scaling logic

**Consider an operator when**:
- Your application is stateful (databases, message queues)
- You need automated lifecycle management (backup, restore, upgrade, failover)
- Day-2 operations are complex and error-prone
- You want to encode operational expertise into code

<Callout type="tip">
A good rule of thumb: if you're writing runbooks for operating your application on K8s, you might benefit from an operator that encodes those runbooks as code.
</Callout>

## Building Your First Operator

The Operator SDK provides scaffolding for building operators in Go, Helm, or Ansible.

### Choosing Your Approach

| Approach | Best For | Learning Curve |
|----------|----------|----------------|
| Go (controller-runtime) | Complex operators, full control | Steep |
| Helm Operator | Simple lifecycle, existing Helm charts | Easy |
| Ansible Operator | Infrastructure automation teams | Medium |
| Kubebuilder | Go operators (alternative to Operator SDK) | Steep |

### Basic CRD Structure

```go
// A simple operator's CRD in Go
type MyAppSpec struct {
    Replicas int32  `json:"replicas"`
    Image    string `json:"image"`
    Config   string `json:"config,omitempty"`
}

type MyApp struct {
    metav1.TypeMeta   `json:",inline"`
    metav1.ObjectMeta `json:"metadata,omitempty"`
    Spec   MyAppSpec   `json:"spec,omitempty"`
    Status MyAppStatus `json:"status,omitempty"`
}
```

## Real-World Examples

**Prometheus Operator**: Manages Prometheus and Alertmanager deployments. When you create a `Prometheus` CR, the operator provisions the pods, configures scraping, and manages configuration updates.

**Cert-Manager**: Manages TLS certificates. When you create a `Certificate` CR, it handles issuance, renewal, and secret management automatically.

**Database Operators** (Crunchy Postgres, Zalando Postgres): Handle replication, failover, backup, point-in-time recovery, and version upgrades for database clusters.

<Note>
Don't build an operator just because you can. The maintenance burden is real — operators need testing, upgrades, and documentation. Start with Helm, and only build an operator when you've identified specific lifecycle automation that Helm can't handle.
</Note>
