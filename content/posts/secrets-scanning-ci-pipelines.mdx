Leaked secrets in git are one of the most common and most damaging security incidents, and they happen because developers do the convenient thing — paste a key into code to test quickly, commit, and forget. Once a secret is in git history it's effectively public: public repos expose it immediately, private repos expose it to everyone with access and to anyone who later gains access, and scraping bots index leaked keys within minutes. Secrets scanning is the control that catches these before they do damage, and modern tooling makes it cheap enough that there's no excuse not to run it. This is a practical guide to the tools, the policy, and the response when something slips through.

## Why Secrets Leak

The root cause is almost always the speed-vs-safety tradeoff in its most mundane form. A developer needs to test something against a real API, the fastest path is to hardcode the key, and the key ends up in a commit. Env files (`.env`) get committed because they're not gitignored, or because someone copies a config template that still has real values. Service account JSON files, cloud credentials, and database URLs with embedded passwords all leak the same way — they're convenient to drop in and easy to forget.

The damage is amplified by git's design. History is append-only and replicated, so a secret committed five years ago in a private repo is still there when the repo is shared, made public, or accessed by an attacker who grabbed a token. `git rm` removes it from the current tree but not from history; truly purging a secret requires history rewriting, which is disruptive and often skipped, leaving the secret recoverable. Prevention — catching it before it's committed — is dramatically cheaper than remediation.

The scale is real: studies of public GitHub find millions of leaked secrets at any given time, and the time-to-exploitation for a leaked cloud key is often measured in minutes, thanks to automated scrapers. This is not a theoretical risk.

## Scanning Tools

Two tools cover most needs. **Gitleaks** is fast, repo-focused, and easy to run as a pre-commit hook or CI step. It uses a library of regex patterns for known secret formats (AWS keys, GitHub tokens, private keys, database URLs) plus entropy detection for high-randomness strings that look like secrets. It's open-source, lightweight, and the default choice for "scan this repo."

**TruffleHog** adds **verification** — the ability to actually test a detected secret against the service it's for, to confirm it's live and not a placeholder or a rotated key. This matters because raw regex scanning produces false positives (test fixtures, documentation examples, dummy values), and a scanner that screams about every high-entropy string gets ignored. TruffleHog's verified findings are far more actionable, and it scans more sources (git history, cloud storage, Slack). For CI, a common setup is Gitleaks as the fast pre-commit gate and TruffleHog for deeper periodic scans with verification.

**Pre-commit vs CI gates** is the key architectural choice. Pre-commit hooks (run via the pre-commit framework or husky) catch secrets before they're committed, which is the ideal — the secret never enters history. The limitation is that hooks can be bypassed (`--no-verify`) and only run for developers who have them installed. CI gates catch what bypassed pre-commit or came from contributors without hooks, and they can't be bypassed by the developer — but they run after the commit is pushed, so the secret is in the remote history even if the build fails. The mature pattern is both: pre-commit for the fast local catch, CI as the non-bypassable gate.

## Fail-Closed Policy

A secrets scanner is only useful if it blocks. The policy that works is **fail-closed**: a detected secret fails the CI build and blocks the merge, every time. The temptation is to start in warn-only mode to avoid disruption, but warn-only scanners get ignored within weeks — developers see the warnings, confirm the build passes, and move on. Fail-closed from the start, with a clear process for handling the block, is less painful in the long run than trying to tighten a warn-only policy later.

**Allowlist and baselines** handle the legitimate cases. Some "secrets" are test fixtures, documentation examples, or dummy values that are safe. A allowlist (in Gitleaks config or TruffleHog's allowlist) suppresses these with a documented reason. A baseline file records existing findings so you only fail on *new* secrets, which makes adoption in a legacy codebase feasible — you acknowledge the existing exposure separately and prevent new leaks going forward.

**Handling false positives** is the operational tax. Entropy-based detection over-triggers on hashes, UUIDs, and random IDs. The response is to tune the config (narrow entropy thresholds, disable noisy rules for specific paths) and to use verified scanning (TruffleHog) where possible. A scanner that produces a high signal-to-noise ratio gets respected; one that cries wolf gets bypassed, and the moment your team learns to `--no-verify` past it, you've lost the control.

## When a Secret Escapes

Despite prevention, secrets will leak — a bypassed hook, a new contributor, a key format the scanner doesn't know. The response matters as much as prevention, and it has a strict order.

**Revocation first.** The instant a real secret is detected in history, rotate and revoke it. Do not try to clean the history first — the secret is already out, the only meaningful action is to make it useless. Rotate the key, update the consuming services, and confirm the old key no longer works. Everything else is secondary.

**Rotation automation** is what makes this survivable at scale. If rotating a secret means updating a dozen services by hand, the response time stretches into hours and the damage compounds. Secrets managed through a vault or cloud secret manager, with consumers that pull dynamically, can be rotated in minutes. Design for rotation from the start — it's the control that turns a leak from an incident into a non-event.

**Post-incident hardening** is the learning loop. After a leak, ask: why did the scanner miss it (new format? ), and close the gap. Add the format to the scanner config, enforce the CI gate, maybe require pre-commit for the team.

Each leak is a free pen test of your detection — use it. The end state is a pipeline where secrets are caught before they ship, where the rare escape is rotated in minutes, and where the process improves with each incident rather than repeating it. That's what "secrets scanning in CI" means when it's actually working.
