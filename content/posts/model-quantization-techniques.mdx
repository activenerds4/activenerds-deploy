- **For production LLM inference**: AWQ or GPTQ at INT4.

Quantization is the single most effective technique for running large models on limited hardware. A 70B parameter model in FP16 needs ~140GB of VRAM — out of reach for most single-GPU setups. With INT4 quantization, that same model fits in ~35GB, runnable on a single A100. The question isn't whether to quantize, but which method to use and how much accuracy you're willing to trade.

This guide compares the main quantization approaches so you can choose based on your constraints, not hype.

## Why Quantize Models

Three forces drive quantization adoption:

**Memory reduction** is the most obvious benefit. Going from FP16 (16-bit) to INT4 (4-bit) reduces model memory by 4x. This is the difference between needing 4× A100s and fitting on 1× A100 for a 70B model.

**Inference speedup** comes from reduced memory bandwidth requirements. Modern GPUs are often memory-bandwidth-bound, not compute-bound. Smaller weights mean less data to move, which means faster inference — often 2-3x for INT8 vs FP16.

**Deployment flexibility** — quantized models can run on consumer GPUs, edge devices, and cheaper cloud instances. This democratizes access to large models.

<Note>
Quantization primarily helps inference, not training. During training, you need gradient precision that quantization sacrifices. Use quantization for serving; use mixed precision (AMP) for training.
</Note>

## Post-Training Quantization

Post-training quantization (PTQ) converts a pre-trained model to lower precision without retraining. It's the fastest path to a quantized model but can suffer accuracy loss.

**Dynamic quantization** converts weights to INT8 but keeps activations in FP32 during computation. This is the simplest approach and works well for models where activation ranges are unpredictable. PyTorch supports it natively:

```python
import torch

model = torch.load("model.pt")
model = torch.quantization.quantize_dynamic(
    model,
    {torch.nn.Linear},
    dtype=torch.qint8
)
```

**Static quantization** converts both weights and activations, but requires a calibration dataset to determine activation ranges. This gives better performance (no FP32 fallback) but needs representative data:

```python
model = torch.quantization.quantize_static(
    model,
    calibrate_fn,
    [torch.quantization.default_qconfig],
    dtype=torch.qint8
)
```

For LLMs, standard PTQ methods struggle because the activation distributions in transformer layers are more complex. This is where GPTQ and AWQ come in.

## GPTQ and AWQ

**GPTQ** is a post-training quantization method specifically designed for LLMs. It uses a layer-wise quantization approach based on approximate second-order information, minimizing the error introduced by quantizing each weight. The result: INT4 quantization with minimal accuracy loss.

```python
from auto_gptq import AutoGPTQForCausalLM, BaseQuantizeConfig

quantize_config = BaseQuantizeConfig(
    bits=4,
    group_size=128,
    desc_act=False,
)

model = AutoGPTQForCausalLM.from_pretrained(
    "model_name",
    quantize_config,
)
```

GPTQ is well-supported in Hugging Face Transformers via the `auto-gptq` library and works with popular serving frameworks like vLLM and Text Generation Inference.

**AWQ** (Activation-aware Weight Quantization) takes a different approach: instead of treating all weights equally, it identifies the most important weights (those that produce large activations) and protects them from quantization error. This "salient weight" approach often preserves accuracy better than GPTQ.

```python
from awq import AutoAWQForCausalLM

model = AutoAWQForCausalLM.from_quantized(
    "model_name-awq",
    fuse_layers=True,
)
```

### Benchmark Comparison

| Method | Bits | Memory (70B) | Accuracy Loss | Speed vs FP16 |
|--------|------|-------------|---------------|---------------|
| FP16 (baseline) | 16 | ~140GB | 0% | 1.0x |
| GPTQ | 4 | ~35GB | 1-3% | 2-3x |
| AWQ | 4 | ~35GB | 0.5-2% | 2-3x |
| bitsandbytes NF4 | 4 | ~38GB | 2-4% | 1.5-2x |
| INT8 (PTQ) | 8 | ~70GB | &lt;1% | 1.5-2x |

AWQ generally edges out GPTQ on accuracy, while GPTQ has broader ecosystem support. Both are excellent choices for INT4 LLM quantization.

## bitsandbytes and NF4

**bitsandbytes** popularized 4-bit quantization for LLMs through its integration with Hugging Face Transformers. Its **NF4 (NormalFloat 4-bit)** format is designed specifically for normally-distributed weights, which is the case for most trained neural networks.

NF4 is the quantization method behind QLoRA, which enables fine-tuning of 65B+ models on a single 48GB GPU. It's not the fastest for inference, but it's the easiest to use:

```python
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.float16,
    bnb_4bit_use_double_quant=True,
)

model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-2-70b-hf",
    quantization_config=bnb_config,
)
```

<Callout type="tip">
Use bitsandbytes for quick prototyping and fine-tuning (QLoRA). Use GPTQ or AWQ for production inference — they're faster and better supported by serving frameworks.
</Callout>

## Choosing the Right Method

**For production LLM inference**: AWQ or GPTQ at INT4. Both are well-supported by vLLM and TGI, and the accuracy loss is negligible for most use cases.

**For fine-tuning on consumer GPUs**: bitsandbytes NF4 (QLoRA). It's the only method designed for training, not just inference.

**For non-LLM models (CNNs, smaller transformers)**: Standard PyTorch INT8 dynamic or static quantization. These models are simpler and don't need the LLM-specific methods.

**For maximum accuracy**: INT8 over INT4. The 2x memory savings (vs 4x for INT4) is worth it if you can fit the model and accuracy is critical.

**For edge/mobile deployment**: INT8 or even INT4 with framework-specific tools (ONNX Runtime quantization, Core ML optimization). The ecosystem here is different from server-side quantization.

The quantization landscape is evolving rapidly. The methods described here are current as of 2025, but new techniques (like SpinQuant and QuaRot) are pushing accuracy boundaries further. The key principle remains: always benchmark your specific model and use case — general benchmarks don't predict your accuracy loss.
