Policy as code brings the benefits of version control, testing, and automation to infrastructure governance. In the Kubernetes ecosystem, two tools dominate: Open Policy Agent (OPA) with Gatekeeper, and Kyverno. Both enforce policies on your cluster, but they take fundamentally different approaches.

## What Is Policy as Code?

Policy as code means defining your governance rules as declarative, version-controlled code rather than manual configurations or tribal knowledge. The benefits:

- **Version control**: Every policy change is tracked, reviewable, and reversible
- **Testing**: Test policies against scenarios before applying them
- **Audit trail**: Know exactly what policies were in effect at any time
- **Automation**: Policies apply consistently across all environments

## OPA/Rego Approach

Open Policy Agent uses Rego, a purpose-built policy language. Gatekeeper is the Kubernetes integration that runs OPA policies as an [admission controller](/articles/kubernetes-admission-controllers-guide).

### Rego Example

```rego
package k8srequiredlabels

deny[msg] {
  resource := input.review.object
  not resource.metadata.labels["app"]
  msg := sprintf("missing required label 'app' on %s/%s", [resource.kind, resource.metadata.name])
}
```

### Strengths

- **Expressiveness**: Rego is a full policy language. It can express complex logic that YAML can't.
- **Ecosystem**: OPA runs beyond Kubernetes — you can use the same policies for API gateways, CI/CD, and microservices.
- **Maturity**: Large community, extensive documentation, battle-tested at scale.

### Weaknesses

- **Learning curve**: Rego is a unique language. Your team needs to learn it.
- **YAML gap**: Rego policies don't look like Kubernetes manifests, which creates a mental context switch.
- **Debugging**: Rego's evaluation model can be hard to debug for complex policies.

## Kyverno Approach

Kyverno uses YAML-native policies. If you know Kubernetes, you know Kyverno — policies are just Kubernetes resources.

### Kyverno Example

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-labels
spec:
  validationFailureAction: enforce
  rules:
    - name: require-app-label
      match:
        resources:
          kinds: [Pod]
      validate:
        message: "The label 'app' is required"
        pattern:
          metadata:
            labels:
              app: "?*"
```

### Strengths

- **Native K8s experience**: Policies are YAML. No new language to learn.
- **Mutation**: Kyverno can modify resources (inject labels, add defaults) in addition to validating.
- **Image verification**: Built-in support for Cosign image signature verification.
- **Simpler onboarding**: Teams that know K8s can be productive immediately.

### Weaknesses

- **Expressiveness**: Complex policies can become verbose YAML. Some logic that's trivial in Rego requires workarounds in Kyverno.
- **K8s-only**: Kyverno policies only work in Kubernetes. No cross-platform reuse.
- **Newer**: Smaller community and ecosystem compared to OPA.

## Feature Comparison

| Feature | OPA/Gatekeeper | Kyverno |
|---------|---------------|---------|
| Policy language | Rego | YAML |
| Learning curve | Steep | Gentle |
| Mutation | Via external tools | Built-in |
| Image verification | Custom Rego | Built-in (Cosign) |
| Cross-platform | Yes (API, CI/CD) | No (K8s only) |
| Community size | Larger | Growing fast |
| Policy expressiveness | High | Medium-High |
| K8s native feel | No | Yes |

## Decision Framework

### Choose OPA when:
- You need policies beyond Kubernetes (API gateway, CI/CD, microservices)
- Your team has strong programming skills and can learn Rego
- You need complex policy logic that YAML can't express cleanly
- You're in a large organization with a dedicated platform/security team

### Choose Kyverno when:
- Your team is Kubernetes-first and wants to stay in the YAML ecosystem
- You need image verification (Cosign integration is first-class)
- You want mutation capabilities (inject labels, add defaults)
- You want faster team onboarding
- You're in a smaller team or startup

### Hybrid approach:
Some organizations use both — Kyverno for K8s-native policies (labels, image verification) and OPA for cross-platform policies (API authorization, CI/CD gates). This gives you the best of both worlds at the cost of maintaining two systems.

<Note>
Don't overthink the choice. Both tools are production-ready and widely used. Pick the one that fits your team's skills and current needs. The worst choice is no policy enforcement at all.
</Note>
