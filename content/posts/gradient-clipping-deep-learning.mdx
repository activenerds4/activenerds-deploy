You're 40 minutes into a training run. Loss is dropping nicely, the learning rate schedule is doing its thing, and then — without warning — the loss jumps to `NaN`. The model hasn't learned a thing since. This is the classic signature of exploding gradients, and gradient clipping is the first line of defense.

Clipping isn't a fix for a fundamentally broken training setup, but it's a cheap, reliable stabilizer that buys you headroom on architectures and learning rates that would otherwise be unusable. This guide covers when to reach for it, the two [strategies](/articles/hyperparameter-tuning-strategies) that matter, and how to wire it into a PyTorch loop without hiding deeper bugs.

## The Exploding Gradient Problem

Gradients explode when the product of weight matrices in a deep network amplifies a small input perturbation into a huge gradient signal. Recurrent networks were the historical poster child for this, but it shows up in transformers too — particularly with long sequences, large learning rates, or uninitialized embeddings. The symptom is unmistakable: loss is fine for a stretch, then spikes to `inf` or `NaN`, and every subsequent step is dead.

The reason it's sudden rather than gradual is that the explosion compounds over layers. A gradient norm that creeps up by 10% per step looks benign until it crosses a threshold where floating-point overflow turns it into garbage in a single update. By the time you notice, the weights are already corrupted.

This bites hardest in three situations: training from scratch with aggressive learning rates, mixed-precision training where the fp16 dynamic range is narrow, and distributed training where gradient averaging across ranks can interact badly with large local gradients. In all three, clipping is a pragmatic guardrail — it doesn't solve the root cause, but it keeps the run alive long enough for you to find it.

## Clipping Strategies

There are two clipping strategies, and they do different things. Choosing the wrong one is a common mistake.

**Value clipping** caps each individual gradient element to a range `[-c, c]`. It's a hard per-element ceiling: any gradient component above `c` becomes `c`, anything below `-c` becomes `-c`. This is rarely what you want for stability, because it distorts the gradient direction — clipping some elements and not others changes which way the update points. It's useful in narrow cases (e.g., bounding a known misbehaving parameter), but as a general stabilizer it's the wrong tool.

**Norm clipping** rescales the entire gradient vector so its global norm doesn't exceed a threshold. If the current gradient norm is below the threshold, nothing happens. If it's above, the whole vector is scaled down proportionally. This preserves the gradient *direction* while capping its magnitude, which is almost always what you want for training stability. In PyTorch this is `clip_grad_norm_`.

Choosing a threshold is empirical, not theoretical. A common starting point is a value around the typical gradient norm you observe during stable training — set the clip just above that, so it only kicks in during excursions. Too low and you artificially slow learning; too high and it never fires. Log your gradient norms for the first few hundred steps and pick a threshold at roughly the 90th–95th percentile of what you see.

A subtlety: `clip_grad_norm_` computes the norm over *all* parameters together by default. For models with very different parameter scales (e.g., embeddings vs. attention matrices), a single global norm can let one group dominate. Per-parameter-group clipping is an option, but it adds complexity; start with the global norm and only refine if you see one parameter group's gradients consistently getting crushed while others explode.

## PyTorch Implementation

The implementation is one line, but its placement matters. Clipping happens *after* `loss.backward()` computes the gradients and *before* `optimizer.step()` applies them:

```python
optimizer.zero_grad()
loss = model(batch)
loss.backward()

# Clip before stepping
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)

optimizer.step()
scheduler.step()
```

The most common bug is calling it before `backward()` (no gradients exist yet) or after `step()` (too late — the explosion already corrupted the weights). Put it between the two, every time.

Logging the gradient norm alongside the clip is what turns clipping from a bandage into a diagnostic. Capture the norm *before* clipping so you can see the raw excursions:

```python
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
# log pre-clip norm separately if you want to observe excursions
total_norm = torch.norm(torch.stack([
    p.grad.norm(2) for p in model.parameters() if p.grad is not None
]), 2)
```

If you see the pre-clip norm sitting at the threshold constantly, your clipping is doing real work every step — that's a sign the learning rate is too high or there's a deeper issue, not a sign the clip is "working." A clip that fires occasionally during a schedule warmup and then goes quiet is healthy; a clip that fires every step is masking a problem.

## Beyond Clipping

Clipping is a stabilizer, not a cure. If you find yourself ratcheting the threshold down to keep training alive, step back and look at the actual cause.

The learning rate is the usual suspect. A rate that's too high for the architecture or the current training phase produces large gradients that clipping then suppresses — you're training with a clipped, distorted gradient and wondering why convergence is poor. Lowering the learning rate often removes the need to clip at all. This is why clipping pairs with a [warmup schedule](/blog/optimize-pytorch-training-speed): warmup keeps gradients small early when the model is most fragile, and clipping catches the occasional excursion.

Normalization layers change the gradient landscape substantially. Models with LayerNorm or RMSNorm are far less prone to exploding gradients than their unnormalized counterparts because normalization keeps activations (and thus gradients) in a bounded range. If you're fighting explosions on an older architecture, consider whether a normalization change would help more than clipping.

The deepest trap: clipping can mask a real bug. A NaN in your data, a division by zero in a custom loss, or an embedding row that never gets updated and stays at its (large) initialization will all produce large gradients that clipping quietly absorbs. You'll see "stable" training that's actually broken, just slower to reveal itself. When you add clipping, also log the raw gradient norm and the loss — if the loss looks flat or weirdly noisy while the clip fires constantly, suspect that clipping is hiding something rather than fixing it.

Used well, gradient clipping is a five-line safety net that lets you train more aggressively with confidence. Used as a crutch, it lets broken runs limp along while you debug the wrong thing. The difference is whether you treat it as a guardrail you monitor or a switch you flip and forget.
