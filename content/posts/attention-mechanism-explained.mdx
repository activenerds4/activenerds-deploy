Attention is the single idea that turned sequence models from slow, forgetful chains into the parallel, context-aware engines behind modern LLMs. Yet most explanations either drown you in linear algebra or hand-wave so hard you learn nothing usable. This guide explains attention the way I wish someone had explained it to me: concretely, with the intuition first and the math only where it earns its place.

If you train or fine-tune models, you don't need to derive attention from scratch to use it. But you do need to understand it well enough to reason about memory, sequence length, and why your training run blew up at 8k tokens.

## Why Attention Matters

Before attention, the dominant [architecture](/articles/transformer-architecture-explained) for sequences was the recurrent neural network (RNN). RNNs process tokens one at a time, carrying a hidden state forward. That design has two painful consequences: training is sequential (you can't parallelize across the time dimension easily), and information from early tokens degrades as it passes through many hidden-state transitions. Long-range dependencies get lost.

Attention solves both problems by letting every token look directly at every other token in a single step. There's no hidden-state relay race — each position computes its output as a weighted mixture of all positions, and those weights are learned. Because the operation is a batch of matrix multiplications over the full sequence, GPUs parallelize it efficiently. That parallelism is a big part of why transformers scaled where RNNs stalled.

The practical payoff: you can train on much longer contexts, model richer dependencies, and throw hardware at the problem in a way that actually translates to better models. When you're deciding whether a fine-tuning run can afford a 16k context window, the thing you're weighing is attention's memory cost — so understanding the mechanism is understanding your budget.

## Queries, Keys, and Values

The cleanest mental model for attention is a retrieval system. Imagine a database lookup, but soft: instead of returning one exact match, you return a weighted blend of all records based on how relevant each is.

Three vectors drive this:

- **Query (Q)** — what the current token is "looking for."
- **Key (K)** — what each token "offers" or advertises.
- **Value (V)** — the actual content each token contributes if selected.

For a given query, you compute similarity scores against every key. High similarity means "this key is relevant to my query." Those raw scores get passed through a softmax, which turns them into weights that sum to one. The output is then a weighted sum of the values — tokens with relevant keys contribute more of their value to the result.

The similarity is almost always a dot product, because dot products are cheap and capture alignment between vectors. The softmax ensures the weighting is differentiable and normalized, so the model learns to assign sharp weight where it matters and near-zero weight elsewhere.

<Callout type="tip">
If you remember only one thing: attention is "soft lookup." The query asks, the keys answer, and the values are what actually gets mixed in. Everything else is engineering.
</Callout>

## Self-Attention in Practice

In self-attention — the form used inside transformers — the queries, keys, and values all come from the same input sequence, each produced by its own learned linear projection. So every token can attend to every other token (and itself), and the model learns what to pay attention to through those projection weights.

The core computation is scaled dot-product attention:

```
Attention(Q, K, V) = softmax(Q · Kᵀ / √dₖ) · V
```

The `√dₖ` scaling matters more than it looks. Dot products grow with the dimensionality of the key vectors, and as they grow, softmax gets pushed into regions where gradients vanish — a few tokens dominate and learning stalls. Dividing by the square root of the key dimension keeps the variance stable. Omit that scaling and you'll see training instability on longer sequences, which is exactly the kind of bug that's invisible in toy tests and brutal in production.

Multi-head attention runs this whole operation several times in parallel with different learned projections, then concatenates the results. Each head can specialize: one might track syntactic relationships, another coreference, another long-range topic continuity. More heads give the model more independent "attention channels" without proportionally more compute, which is why head count is a knob worth tuning rather than maxing out.

One subtlety: attention itself is permutation-invariant. It doesn't know about token order — position 3 and position 30 look identical to the mechanism. That's why transformers add positional encodings to the input embeddings. Without them, "the cat sat on the mat" and "mat the on sat cat the" would be indistinguishable. Positional encodings are how attention learns sequence structure despite being fundamentally order-agnostic.

## Implementing Attention

A minimal self-attention block in PyTorch is short, and writing it once demystifies the whole thing:

```python
import torch
import torch.nn.functional as F
import math

class SelfAttention(torch.nn.Module):
    def __init__(self, embed_dim, num_heads):
        super().__init__()
        assert embed_dim % num_heads == 0
        self.num_heads = num_heads
        self.head_dim = embed_dim // num_heads
        self.qkv = torch.nn.Linear(embed_dim, embed_dim * 3)
        self.out = torch.nn.Linear(embed_dim, embed_dim)

    def forward(self, x):
        B, T, C = x.shape
        qkv = self.qkv(x).reshape(B, T, 3, self.num_heads, self.head_dim)
        q, k, v = qkv.unbind(dim=2)  # each (B, T, heads, head_dim)
        q, k, v = [t.transpose(1, 2) for t in (q, k, v)]  # (B, heads, T, head_dim)

        scores = (q @ k.transpose(-2, -1)) / math.sqrt(self.head_dim)
        weights = F.softmax(scores, dim=-1)
        out = weights @ v  # (B, heads, T, head_dim)

        out = out.transpose(1, 2).reshape(B, T, C)
        return self.out(out)
```

The memory consideration is the part that bites in practice. The attention weight matrix is `(sequence_length × sequence_length)` per head per batch. At 2k tokens that's 4M floats per head — fine.

At 32k tokens it's over a billion floats per head, and you're suddenly shopping for techniques like FlashAttention, sliding-window attention, or sparse patterns. When your training run OOMs after you doubled the context length, this quadratic is almost always why. We cover the broader debugging playbook in our [PyTorch OOM debugging guide](/blog/debugging-oom-pytorch).

A few common pitfalls when implementing from scratch: forgetting the scaling (unstable training), transposing the wrong dimension (silently wrong attention that still trains but learns nothing useful), and applying dropout to the weights but not the output (regularization imbalance). The implementation above is intentionally bare — real transformers add causal masking for decoder layers, cross-attention for encoder-decoder setups, and careful initialization. But the core is exactly this, and once it's concrete, the rest of the architecture reads as variations on a theme.

Understanding attention at this level pays off every time you tune a hyperparameter, debug a memory spike, or decide whether a longer context window is worth the cost. It's the load-bearing idea of modern ML — worth the hour to actually understand.
