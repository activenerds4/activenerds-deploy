A slow CI/CD pipeline doesn't just waste time — it kills developer productivity. When a build takes 20 minutes, developers context-switch, lose flow state, and batch changes to avoid the wait. Fast pipelines (under 5 minutes) enable true continuous integration and rapid iteration.

This guide covers the highest-impact optimizations for CI/CD speed, applicable to GitHub Actions, GitLab CI, CircleCI, and similar platforms.

## Why Pipeline Speed Matters

The feedback loop cost is real: every minute between pushing code and seeing results is a minute where the developer's context is at risk. Research shows that context switching costs 15-25 minutes of productivity per switch. A 15-minute pipeline that causes a context switch effectively costs 30-40 minutes.

The goal: get feedback to developers in under 5 minutes for the critical path (lint, typecheck, unit tests). Everything else (integration tests, e2e, security scans) can run in parallel or post-merge.

## Caching Strategies

### Layer Caching for Docker

Docker layer caching is the single biggest win for container-based pipelines. The key is ordering your Dockerfile correctly:

```dockerfile
# Bad: Dependencies change every time code changes
COPY . /app
RUN npm install

# Good: Dependencies only reinstall when package.json changes
COPY package.json package-lock.json /app/
RUN npm install
COPY . /app
```

### Dependency Caching

Cache your package manager's cache directory between runs:

```yaml
# GitHub Actions example
- name: Cache npm
  uses: actions/cache@v3
  with:
    path: ~/.npm
    key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-node-
```

### Build Artifact Caching

Cache intermediate build artifacts (compiled objects, test results) to skip redundant work. Tools like `ccache` (C/C++), `tsbuildinfo` (TypeScript), and `pytest-cache` (Python) can dramatically reduce build times.

<Callout type="tip">
Cache the most expensive, most frequently-used layers. Don't cache everything — cache misses on rarely-used layers waste more time than they save.
</Callout>

## Parallel and Matrix Builds

### Job Splitting

Split long-running test suites into parallel jobs:

```yaml
# GitHub Actions: split tests across 4 runners
jobs:
  test:
    strategy:
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - run: npm test -- --shard=${{ matrix.shard }}/4
```

### Test Parallelization

Tools for automatic test splitting:
- **Jest**: `--shard` flag for built-in sharding
- **pytest**: `pytest-xdist` for parallel execution
- **Jest Circus**: `--maxWorkers` for multi-process runs

### Conditional Execution

Skip jobs that aren't needed:

```yaml
jobs:
  test:
    if: |
      !contains(github.event.head_commit.message, '[skip ci]')
  docs:
    if: contains(github.event.head_commit.message, '[docs]')
  security:
    if: github.ref == 'refs/heads/main'
```

## Build Optimization

### Multi-Stage Docker Builds

Multi-stage builds reduce final image size and build time by separating the build environment from the runtime:

```dockerfile
# Build stage
FROM node:20 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Runtime stage (much smaller, faster to pull)
FROM node:20-slim
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
CMD ["node", "dist/index.js"]
```

### BuildKit Features

Enable BuildKit for advanced caching:

```bash
# Enable BuildKit
DOCKER_BUILDKIT=1 docker build --cache-from=type=registry,ref=myimage:cache \
  --cache-to=type=registry,ref=myimage:cache,mode=max .
```

### Selective Builds

Only build what changed:

```yaml
# Only build the affected service
- name: Detect changes
  uses: dorny/paths-filter@v2
  id: changes
  with:
    filters: |
      api:
        - 'services/api/**'
      web:
        - 'services/web/**'

- name: Build API
  if: steps.changes.outputs.api == 'true'
  run: docker build -t api ./services/api
```

## Measuring and Iterating

### Pipeline Metrics

Track these metrics over time:
- **Total pipeline duration**: End-to-end time from push to completion
- **Per-stage duration**: Identify which stages are slowest
- **Cache hit rate**: Are your caches actually working?
- **Queue time**: Time waiting for runners (infra problem, not code problem)

### Bottleneck Identification

Use the profiling tools in your CI platform:
- GitHub Actions: "Timing" tab in workflow runs
- GitLab CI: Pipeline visualization shows per-job duration
- CircleCI: Insights dashboard

### Continuous Improvement

Set a pipeline speed budget:
- **Target**: 5 minutes for PR feedback (lint + typecheck + unit tests)
- **Target**: 15 minutes for full pipeline (integration + e2e + security)
- **Review**: Monthly pipeline speed review — identify the slowest job and optimize it

<Note>
The fastest pipeline is the one that doesn't run. Use path-based filtering to skip pipelines for changes that don't need them (docs-only changes shouldn't trigger full test suites). Conditional execution is free performance.
</Note>

Pipeline optimization is iterative. Start with caching (biggest bang for the buck), then parallelization, then selective builds. Measure after each change — some optimizations help, some don't, and the only way to know is to measure.
