Certificates are the unglamorous infrastructure that everything else depends on. In Kubernetes, you need TLS for Ingress, you need mTLS for service-to-service communication in any serious setup, and you need certificates for the API server's webhook endpoints. Doing this by hand — generating CSRs, copying certs into Secrets, remembering to renew them — is exactly the kind of toil that fails at 3am when a cert expires and takes the ingress down with it. cert-manager is the standard answer: a controller that issues, rotates, and renews certificates inside the cluster so you don't have to.

This is a practical guide to cert-manager: the concepts, getting Let's Encrypt working, using private CAs for internal mTLS, and the operational realities that determine whether your certificates renew silently or expire loudly.

## The Certificate Problem in K8s

**Manual renewal pain.** The failure mode of manual certificates is that they work fine for 89 days and ruin your day on the 90th. A certificate that someone generated by hand, stored in a Secret, and forgot about will expire, and the first sign is usually a user reporting that the site is broken or a [service mesh](/articles/mtls-microservices-implementation) refusing connections. The fix is automation: certificates should be objects the cluster manages, with renewal that happens well before expiry and without human intervention.

**mTLS and Ingress TLS.** Two distinct use cases. Ingress TLS is the public-facing certificate for your domain, terminating TLS at the ingress so browsers trust the connection — this is where Let's Encrypt fits. mTLS is internal: services authenticate to each other with certificates, which requires a private CA and a way to distribute it. cert-manager handles both, but with different issuers and different operational concerns. See our [mTLS implementation guide](/blog/mtls-microservices-implementation) for the service-mesh side of this.

**Why cert-manager.** cert-manager is a CustomResource-driven controller: you define an `Issuer` (or `ClusterIssuer`) that knows how to sign certificates, and a `Certificate` resource that requests one. The controller sees the `Certificate`, asks the issuer to sign it, stores the resulting cert and key in a Secret, and schedules a renewal before it expires. The renewal is automatic and the Secret is updated in place, so consumers that mount or watch the Secret pick up the new cert without a manual step.

## Core Concepts

**Issuer vs ClusterIssuer.** An `Issuer` is namespace-scoped — it can only issue certificates in its own namespace. A `ClusterIssuer` is cluster-scoped and can issue to any namespace. For Let's Encrypt on a public ingress, you want a `ClusterIssuer` so all namespaces can use it. For a private CA that should only serve specific namespaces, an `Issuer` gives you the scope restriction. Most setups use one `ClusterIssuer` for Let's Encrypt and namespace `Issuer`s for private CAs where isolation matters.

**Certificate resources.** A `Certificate` resource specifies the DNS names, the issuer to use, and the Secret name to write the result to. cert-manager creates the certificate, writes the cert, chain, and key to the named Secret, and sets a renewal condition based on the certificate's `notAfter`. The Secret is a standard `kubernetes.io/tls` Secret that Ingress and other consumers read directly.

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: app-tls
  namespace: default
spec:
  secretName: app-tls
  dnsNames:
    - app.example.com
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
  duration: 2160h
  renewBefore: 360h
```

**ACME and DNS challenges.** For Let's Encrypt, cert-manager uses the ACME protocol, which requires proving you control the domain before a certificate is issued. cert-manager supports HTTP-01 (serving a token on the domain) and DNS-01 (creating a TXT record on the domain). The choice matters: HTTP-01 is simpler but requires the domain to be reachable; DNS-01 works for wildcard certificates and for domains not yet pointed at the cluster, but requires giving cert-manager credentials to your DNS provider.

## Let's Encrypt in Practice

**HTTP-01 vs DNS-01.** HTTP-01 is the easy start: cert-manager spins up a solver pod or Ingress that serves the ACME challenge token, Let's Encrypt fetches it, and the cert is issued. It works as long as your ingress is reachable on port 80 for the domain. DNS-01 is necessary for wildcard certificates (`*.example.com`), which HTTP-01 can't prove, and for setups where you don't want port 80 exposed. DNS-01 needs a solver configured with your DNS provider's API credentials (Cloudflare, Route53, etc.), which is more setup but more flexible.

**Rate limits.** Let's Encrypt has rate limits that bite if you're not careful: a cert is limited to 5 duplicate certificates per week, and there are limits on failed validations. A common mistake is setting `renewBefore` too aggressively or deleting and recreating `Certificate` resources, which triggers re-issuance and can hit the duplicate limit. Use the Let's Encrypt staging environment for testing — it has the same API but no rate limits and issues certs with an untrusted CA, so you can iterate without burning your production quota.

**Wildcard certificates.** A wildcard cert (`*.example.com`) covers all subdomains with one certificate, which is operationally simpler than per-subdomain certs. It requires DNS-01. The tradeoff is that a compromised wildcard cert exposes every subdomain, so for high-value setups, per-subdomain certs with a narrower blast radius are safer. For most internal and staging use, a wildcard is the right balance of simple and secure.

## Operations

**Renewal failures.** cert-manager renews certificates automatically, but renewal can fail — the ACME challenge can't complete (DNS credentials expired, the ingress isn't reachable), or the private CA is down. The failure is silent unless you monitor it. The operational practice that matters is alerting on `Certificate` resources whose `Ready` condition is False or whose renewal is overdue — cert-manager emits these conditions, and a Prometheus rule that watches them is what turns a 3am outage into a ticket you see on Monday.

**Private CAs for internal mTLS.** For internal mTLS, you run a private CA — either a self-signed CA issuer that cert-manager bootstraps, or an external CA (Vault, a corporate PKI) via the CA issuer. The self-signed path is easy to start with: cert-manager generates a root CA, stores it, and signs leaf certs from it. The operational concern is the root CA's private key — it needs to be stored somewhere it can't be exfiltrated, which is why teams that take this seriously move to Vault or a managed CA for the root. See our guide to [secrets management in Kubernetes with Vault](/blog/secrets-management-kubernetes-vault) for the storage side.

**Monitoring certificate health.** The minimum viable monitoring is: alert when any `Certificate` is not Ready, alert when any certificate expires within 7 days and hasn't renewed, and track issuance failures by issuer. cert-manager exposes metrics for these. The teams that get woken up by expired certificates are the ones without this monitoring; the teams that don't are the ones whose renewal failures become a dashboard they check proactively. Automation handles the 99% that renew cleanly; monitoring catches the 1% that don't, which is the whole point of running cert-manager instead of doing it by hand.
