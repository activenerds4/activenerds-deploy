Kubernetes Secrets are just base64-encoded strings. That's not encryption — it's obfuscation. Anyone with `kubectl get secrets` access can decode them in seconds. For production workloads, you need real secrets management: encryption at rest, rotation, audit logging, and centralized control. HashiCorp Vault with the External Secrets Operator is the industry standard for Kubernetes.

## The Secrets Problem in K8s

### Base64 Is Not Encryption

```bash
# "Encrypt" a secret
echo -n 'super-secret-password' | base64
# c3VwZXItc2VjcmV0LXBhc3N3b3Jk

# "Decrypt" it
echo 'c3VwZXItc2VjcmV0LXBhc3N3b3Jk' | base64 -d
# super-secret-password
```

That's it. That's the "encryption" Kubernetes provides by default. The base64 encoding exists for transport, not security.

### Native Secret Limitations

- **No encryption at rest** by default (requires enabling etcd encryption, which many clusters don't)
- **No automatic rotation** — secrets are static until manually updated
- **No audit trail** — no record of who accessed which secret when
- **No centralized management** — secrets are per-namespace, per-cluster
- **No dynamic credentials** — can't generate short-lived database passwords or cloud credentials

### Rotation Challenges

When a database password needs rotation, the typical K8s workflow is:

1. Generate new password
2. Update the Secret in every namespace that uses it
3. Restart all pods that mount it
4. Hope you didn't miss any

With Vault, rotation is a single API call that generates new credentials, updates the consuming applications, and revokes the old ones — automatically.

## Vault Architecture for K8s

### Vault Helm Deployment

The recommended way to deploy Vault on Kubernetes is via the official Helm chart:

```bash
helm repo add hashicorp https://helm.releases.hashicorp.com/
helm install vault hashicorp/vault \
  --namespace vault \
  --create-namespace \
  --set server.ha.enabled=true \
  --set server.ha.replicas=3 \
  --set injector.enabled=true
```

For production, use the HA mode with Raft storage (no external dependency):

```yaml
# values.yaml
server:
  ha:
    enabled: true
    replicas: 3
    raft:
      enabled: true
      config: |
        ui = true
        listener "tcp" {
          address = "0.0.0.0:8200"
          tls_cert_file = "/vault/tls/tls.crt"
          tls_key_file = "/vault/tls/tls.key"
        }
        storage "raft" {
          path = "/vault/data"
        }
```

### Kubernetes Auth Method

Vault's Kubernetes auth method lets pods authenticate using their service account token — no need to distribute Vault tokens manually.

```bash
# Enable Kubernetes auth method
vault auth enable kubernetes

# Configure with K8s API
vault write auth/kubernetes/config \
  kubernetes_host="https://kubernetes.default.svc"

# Create a role for the payment service
vault write auth/kubernetes/role/payment-service \
  bound_service_account_names=payment-api \
  bound_service_account_namespaces=payment-service \
  policies=payment-service \
  ttl=1h
```

### Dynamic Secrets

Vault can generate short-lived credentials on demand. For a database:

```bash
# Configure database connection
vault write database/config/payment-db \
  plugin_name=postgresql-database-plugin \
  connection_url="postgresql://{{username}}:{{password}}@db.internal:5432/payment" \
  allowed_roles="payment-readonly"

# Create a role that generates readonly credentials
vault write database/roles/payment-readonly \
  db_name=payment-db \
  creation_statements="CREATE ROLE \"{{name}}\" WITH PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; \
    GRANT SELECT ON ALL TABLES IN SCHEMA public TO \"{{name}}\";" \
  default_ttl=1h \
  max_ttl=4h
```

Now any pod with the right policy can get a database credential that expires in 1 hour:

```bash
vault read database/creds/payment-readonly
# Key                Value
# lease_id           database/creds/payment-readonly/abc123
# lease_duration     1h
# username           v-token-payment-readonly-xyz
# password           random-generated-password
```

## External Secrets Operator

### How ESO Works

The External Secrets Operator (ESO) bridges Vault and Kubernetes. Instead of pods querying Vault directly, ESO syncs secrets from Vault into native Kubernetes Secrets — which your pods mount as usual.

The flow:
1. You create an `ExternalSecret` CRD pointing to a Vault path
2. ESO reads the secret from Vault using its own service account
3. ESO creates a native K8s Secret with the value
4. ESO keeps the K8s Secret in sync — if the Vault secret changes, the K8s Secret updates automatically

### ExternalSecret and SecretStore CRDs

```yaml
apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  namespace: payment-service
  name: vault-backend
spec:
  provider:
    vault:
      server: "https://vault.vault.svc:8200"
      path: "kv"
      version: "v2"
      auth:
        kubernetes:
          mountPath: "kubernetes"
          role: "external-secrets"
          serviceAccountRef:
            name: external-secrets
            namespace: external-secrets
---
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  namespace: payment-service
  name: payment-db-credentials
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: SecretStore
  target:
    name: payment-db-credentials
    creationPolicy: Owner
  data:
  - secretKey: username
    remoteRef:
      key: payment-service/db
      property: username
  - secretKey: password
    remoteRef:
      key: payment-service/db
      property: password
```

### Sync Patterns

**Static secrets**: Sync a static secret from Vault's KV store. Updates when the Vault secret changes.

**Dynamic secrets**: ESO can request dynamic credentials from Vault and create time-limited K8s Secrets. When the lease expires, ESO automatically requests new credentials.

```yaml
# Dynamic database credentials via ESO
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: payment-db-dynamic
spec:
  refreshInterval: 55m  # Refresh before the 1h TTL
  secretStoreRef:
    name: vault-backend
    kind: SecretStore
  target:
    name: payment-db-dynamic
  dataFrom:
  - source:
      generator:
        vaultDynamicSecret:
          path: database/creds/payment-readonly
          source:
            v1Alpha1:
              controller: vault
```

## Security Best Practices

### Short-Lived Credentials

The core principle: credentials should live only as long as needed. Configure Vault roles with short TTLs (1-4 hours) and let ESO handle renewal. If a credential is compromised, the blast radius is limited to its TTL.

### Audit Logging

Enable Vault audit logging to track every secret access:

```bash
# Enable file audit
vault audit enable file file_path=/vault/audit/audit.log

# Enable syslog audit (for centralized logging)
vault audit enable syslog tag=vault facility=AUTH
```

Audit logs record every request — who accessed what, when, and whether it succeeded. Ship these to your SIEM for real-time alerting.

### Namespace Isolation

Use Vault namespaces and policies to enforce isolation:

```bash
# Policy that only allows access to payment-service secrets
cat <<EOF > payment-service-policy.hcl
path "kv/data/payment-service/*" {
  capabilities = ["read"]
}

path "database/creds/payment-readonly" {
  capabilities = ["read"]
}
EOF

vault policy write payment-service payment-service-policy.hcl
```

<Warning>
Never use a single Vault policy that grants access to all secrets. Each application should have its own policy scoped to only the secrets it needs. This is the least-privilege principle applied to secrets management.
</Warning>

## Alternatives and Comparison

| Tool | Best For | K8s Integration | Complexity |
|------|----------|-----------------|------------|
| Vault + ESO | Enterprise, dynamic secrets | Excellent (ESO) | High |
| Sealed Secrets | Simple, GitOps-friendly | Native controller | Low |
| SOPS | Git-based, encrypted files | Manual/CI | Medium |
| AWS Secrets Manager | AWS-native workloads | ESO or CSI driver | Low |
| GCP Secret Manager | GCP-native workloads | ESO or CSI driver | Low |
| Azure Key Vault | Azure-native workloads | ESO or CSI driver | Low |

**Sealed Secrets** is the simplest option — encrypt secrets in Git, decrypt in-cluster. Good for teams starting with GitOps who don't need dynamic credentials.

**SOPS** (Mozilla SOPS) encrypts secret values within YAML/JSON files using cloud KMS or PGP. Works well with ArgoCD and Flux via Kustomize plugins.

**Cloud-native secret managers** (AWS, GCP, Azure) are good if you're already invested in a cloud provider and don't need the advanced features of Vault.

<Callout type="info">
For most teams, the progression is: Sealed Secrets (simple) → SOPS (GitOps) → Vault + ESO (enterprise). Don't start with Vault unless you genuinely need dynamic secrets, centralized management across clusters, or compliance requirements that demand audit logging.
</Callout>

## Putting It Together

A production secrets management setup with Vault and ESO:

1. **Vault** runs in HA mode with Raft storage
2. **Kubernetes auth method** lets pods authenticate with their service account tokens
3. **ESO** syncs secrets from Vault to native K8s Secrets
4. **Dynamic secrets** for databases and cloud credentials — short TTLs, auto-renewal
5. **Audit logging** shipped to your SIEM
6. **RBAC policies** enforce namespace-level isolation

This setup gives you encryption at rest, automatic rotation, audit trails, and centralized management — everything native K8s Secrets lack.
