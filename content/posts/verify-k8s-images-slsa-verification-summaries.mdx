<Callout variant="tip" title="Key Announcement">
As of late 2026, the Kubernetes Release Team publishes **SLSA Verification Summaries (v0.2/v1.0)** for all official container images distributed through `registry.k8s.io` (including `kube-apiserver`, `coredns`, `kube-proxy`, and `pause`). You can now cryptographically attest that an image was built on GitHub Actions by the Kubernetes project itself, without relying on trusted registry hosts alone.
</Callout>

For years, securing the Kubernetes supply chain meant verifying signatures with `cosign` or checking hashes against release notes. While Cosign signatures confirmed *who* signed the blob, they didn't inherently prove *how* the image was built, what source commit produced it, or whether the build pipeline was isolated.

With **SLSA (Supply-chain Levels for Software Artifacts) Verification Summaries**, the Kubernetes project now delivers cryptographic proof of build provenance directly alongside container layers. Here is how SLSA verification works and how to integrate it into your CI/CD pipelines and Kubernetes admission controllers.

---

## 1. What SLSA Verification Summaries Are

A **SLSA Verification Summary (VS)** is an attestation statement generated by a trusted builder (in Kubernetes' case, the Google Cloud Build / GitHub Actions Trusted Builder workflows) that links a binary artifact to its exact source repository, git commit SHA, build configuration, and build parameters.

```
+--------------------------------------------------------------+
|                     Kubernetes Release Team                  |
|          Git Commit: kubernetes/kubernetes@v1.32.0           |
+------------------------------+-------------------------------+
                               |
                               v
                     +--------------------+
                     |  Isolated Builder  | ---> Generates SLSA Provenance
                     +---------+----------+
                               |
                               v
                     +--------------------+
                     |  registry.k8s.io   |
                     |  + Image Manifest  |
                     |  + Cosign Signature|
                     |  + SLSA Summary    |
                     +---------+----------+
                               |
                               v
                     +--------------------+
                     | Verifier (Cosign/  | Checks Subject Digest & Signer OIDC
                     | Policy Controller) |
                     +--------------------+
```

Rather than forcing cluster operators to parse giant, hundred-kilobyte raw SLSA provenance JSON documents during pod admission, a **Verification Summary** provides a compact, signed verdict that can be validated in milliseconds:

- **Subject**: The image digest (SHA-256)
- **Builder Identity**: Cryptographic OIDC identity of the official Kubernetes build pipeline
- **Source URI**: `https://github.com/kubernetes/kubernetes`
- **SLSA Level**: Level 3 verified build isolation

---

## 2. Why Image Provenance Matters for Your Clusters

Why isn't pulling from `registry.k8s.io` over HTTPS sufficient?

1. **Registry Compromise / DNS Poisoning**: If a mirror or cache registry is intercepted, malicious binaries can be served under identical tags (`:v1.32.0`).
2. **Internal Mirror Ingestion**: Regulated enterprises mirror official images into internal Harbor, Artifactory, or AWS ECR registries. Without verifiable build provenance, the internal pipeline cannot guarantee the artifact was unmodified before ingestion.
3. **Audit and Compliance (FedRAMP, PCI-DSS 4.0)**: Modern compliance frameworks require non-repudiable evidence of software origins and automated enforcement at deploy time.

---

## 3. Step-by-Step Verification in CI/CD

To verify an official image before deploying or mirroring it, use `cosign` (v2.4+).

### Step 3.1: Verifying the Image with Cosign

Run `cosign verify-attestation` targeting the official Kubernetes OIDC issuer and repository regex:

```bash
# Verify the kube-apiserver image provenance
cosign verify-attestation \
  --type https://slsa.dev/verification_summary/v0.2 \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  --certificate-identity-regexp "^https://github.com/kubernetes/kubernetes/.*" \
  registry.k8s.io/kube-apiserver:v1.32.0
```

### Expected Output

```json
{
  "_type": "https://in-toto.io/Statement/v0.1",
  "predicateType": "https://slsa.dev/verification_summary/v0.2",
  "subject": [
    {
      "name": "registry.k8s.io/kube-apiserver",
      "digest": {
        "sha256": "4c9d749a21d51f28b7e..."
      }
    }
  ],
  "predicate": {
    "verifier": {
      "id": "https://slsa.dev/provenance-verifier"
    },
    "verifiedLevels": ["SLSA_BUILD_LEVEL_3"]
  }
}
```

## 4. Enforcing Verification with Admission Controllers

To enforce that **only verified Kubernetes images** boot in your cluster, use Kyverno or Sigstore Policy Controller.

### Kyverno ClusterPolicy Example

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-k8s-official-provenance
  annotations:
    pod-policies.kyverno.io/autogen-controllers: none
spec:
  validationFailureAction: Enforce
  webhookTimeoutSeconds: 30
  rules:
    - name: verify-k8s-slsa-attestation
      match:
        any:
          - resources:
              kinds:
                - Pod
              namespaces:
                - kube-system
      verifyImages:
        - imageReferences:
            - "registry.k8s.io/*"
          attestations:
            - type: https://slsa.dev/verification_summary/v0.2
              attestors:
                - entries:
                    - keyless:
                        issuer: "https://token.actions.githubusercontent.com"
                        subjectRegExp: "^https://github.com/kubernetes/kubernetes/.*"
              conditions:
                - all:
                    - key: "{{ @.predicate.verifier.id }}"
                      operator: Equals
                      value: "https://slsa.dev/provenance-verifier"
```

If an unauthorized or altered image with a forged tag attempts to launch inside `kube-system`, the Kyverno admission webhook rejects the admission request before container creation.

## 5. Rolling It Out Across Environments

Implementing image verification across a large enterprise fleet requires a staged rollout to prevent cluster outages:

```
+------------------+       +------------------+       +------------------+
| Phase 1: Audit   | ----> | Phase 2: CI Gate | ----> | Phase 3: Enforce |
| Warning in logs  |       | Block unverified |       | Reject at K8s    |
| No pod blocks    |       | mirror pushes    |       | Admission Plane  |
+------------------+       +------------------+       +------------------+
```

1. **Audit Mode (`validationFailureAction: Audit`)**: Deploy the admission policy in audit mode for 14 days. Inspect metrics and admission webhook audit logs to catch custom auxiliary components running in system namespaces.
2. **CI Ingestion Gate**: Place `cosign verify-attestation` inside your image mirroring workflow (e.g., automated sync scripts pushing from `registry.k8s.io` to your internal AWS ECR / Google Artifact Registry).
3. **Hard Enforcement**: Switch `validationFailureAction: Enforce` in production.

## 6. Common Failure Modes and Troubleshooting

| Failure Symptom | Underlying Cause | Remediation |
|---|---|---|
| `no matching attestations found` | Pulling from a custom private mirror that does not replicate `.att` or `.sig` OCI artifacts. | Configure your mirror script (e.g. `crane` or `skopeo`) with `--all` to copy image signatures and attestation layers. |
| `certificate identity mismatch` | The image was built by a subproject (e.g., `kubernetes-sigs/cri-tools`) rather than core `kubernetes/kubernetes`. | Adjust the `--certificate-identity-regexp` regex to match the appropriate SIG repository. |
| `admission webhook timeout` | Public Sigstore Rekor / Fulcio transparency log lookups timing out in private egress-restricted clusters. | Deploy local Sigstore mirrors or cache root CA certificates inside the admission controller. |

By incorporating SLSA verification summaries into your deployment pipelines, you elevate cluster security from simple checksum matching to cryptographically authenticated provenance.
