When Docker was removed as Kubernetes' default container runtime in v1.24, it didn't remove containers — it removed a layer. What's left is the Container Runtime Interface (CRI), a standard API that kubelet calls to run containers, and a choice of runtimes that implement it. For most clusters that choice comes down to two: containerd and CRI-O. They do the same job, they're both mature, and in a blind test most workloads wouldn't notice the difference. So why does the choice matter, and how do you pick?

This is the practical comparison — what each one is, where they differ in ways that affect operations, and where the choice is genuinely consequential versus where it's a coin flip.

## The Container Runtime Layer

The CRI is the contract. Kubelet needs to do a handful of things — pull images, create and start containers, stop them, attach logs — and rather than bind to one runtime, Kubernetes defined an API for it. Any runtime that implements the CRI can be plugged in, and kubelet talks to it over a Unix socket. The runtime does the actual work: it pulls images from registries, manages the image store, creates the container's filesystem and namespaces, and starts the process via a lower-level OCI runtime (almost always runc).

Where runtimes fit: above the kernel (which provides cgroups and namespaces), below kubelet (which orchestrates pods). Docker, when it was the default, was a full developer toolchain that included this runtime layer plus a CLI and a bunch of other things Kubernetes didn't need; the CRI split let Kubernetes use just the runtime part. containerd is what Docker's runtime part became when extracted; CRI-O was built from scratch by the Kubernetes community to be exactly the CRI and nothing more.

Docker's exit from Kubernetes wasn't a judgment on Docker — it was a judgment on running a developer tool as a production cluster component. The runtime layer that mattered (containerd) stayed; the parts that didn't (the Docker CLI, the developer UX) were never what kubelet needed. Understanding this frames the comparison: both containerd and CRI-O are "just the runtime," and the question is which flavor of "just the runtime" you want.

## containerd

containerd is the de facto default and the one most clusters run. It's a CNCF graduated project, it's what Docker is built on, it's what most managed Kubernetes (GKE, EKS, AKS) uses by default, and it has the largest installed base and the broadest ecosystem support. Its architecture is a single daemon (`containerd`) that handles image management, container lifecycle, and snapshots, with the CRI implemented as a built-in plugin.

The strength is maturity and reach. Because it's everywhere, every tool, every image format, every edge case has been hit by someone before you. The documentation is dense, the issues are well-trodden, and if you have a problem, it's a known problem. The scope is also broader than just Kubernetes — containerd is used outside Kubernetes (Docker, standalone, as a library), which means it gets investment from a wider community than just the Kubernetes world.

The limit is that breadth. containerd does more than the CRI requires, which is mostly a benefit but occasionally means features and config that aren't relevant to Kubernetes. It's a general-purpose container runtime that happens to implement the CRI, rather than a CRI implementation that happens to run containers. For most operators this distinction is invisible; for teams who want the absolute minimum running in their clusters, it's a (small) mark against it.

## CRI-O

CRI-O is the Red Hat / Kubernetes-community answer: a runtime built specifically to be the CRI and nothing else. Its design philosophy is minimalism — it implements the CRI, it runs OCI containers, and it deliberately doesn't do things the CRI doesn't ask for. It's the default in OpenShift and in Red Hat's Kubernetes distributions, and it's tightly aligned with the Kubernetes release process (it's a Kubernetes SIG project, not an independent one).

The minimalism is the point. A smaller surface area means less to secure, less to break, less to configure. CRI-O's config surface is genuinely smaller, and its scope is exactly what kubelet needs. For teams whose operational philosophy is "run the smallest thing that works," CRI-O is the more ideologically pure choice. The OpenShift alignment also means it's deeply tested in large, security-conscious production [environments](/articles/devcontainer-setup-consistent-environments).

The tradeoff is the smaller ecosystem. CRI-O works everywhere the CRI works, but the community and tooling around it are smaller and more Red-Hat-shaped. If you're not on OpenShift, you're a more minority user, and some edge-case tooling assumes containerd. This rarely matters in practice — the CRI is the contract, and anything that works with one works with the other — but it's a real consideration for teams that value a large community over a minimal runtime.

## Choosing Between Them

The performance differences are negligible for almost all workloads. Both use runc underneath, both pull images the same way, both have comparable startup and steady-state overhead. Benchmarks show them within a few percent of each other, and that few percent is dominated by your [image size](/articles/docker-multistage-builds-best-practices) and your pod startup patterns, not the runtime. Don't choose on performance; you can't measure a meaningful difference.

The security posture is where they diverge meaningfully, but in a way that favors CRI-O on paper and is a wash in practice. CRI-O's smaller surface area is genuinely less code to audit and attack, which matters for high-security environments. containerd's larger surface area is more code, but it's also more audited code, more fuzzed code, and more battle-tested code. For most clusters, the practical security difference is dwarfed by how you configure whichever you pick — seccomp profiles, SELinux/AppArmor, read-only root filesystems, [distroless images](/blog/distroless-container-images-security), and [image scanning](/blog/container-image-security-scanning) matter far more than runtime-vs-runtime.

The operational maturity question is the real one. If you're on a managed Kubernetes service, use whatever it defaults to — fighting the platform's default is a tax with no benefit. If you're on OpenShift or a Red Hat distribution, CRI-O is the path of least resistance. If you're building your own cluster and want the largest community and the most familiar tooling, containerd.

If your operational religion is minimalism and you're comfortable being a slightly more minority user, CRI-O. Both are production-grade, both are supported, and neither is a mistake. The choice that actually affects your security and reliability is how you build and scan your images, not which runtime pulls them.
