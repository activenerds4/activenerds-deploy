If you've ever stared at a progress bar crawling through epoch 47 of 100 at 2am — and then hit a [CUDA out of memory error](/articles/debugging-oom-pytorch) — you know that [training](/articles/gradient-clipping-deep-learning) speed isn't just a convenience — it's a productivity multiplier. Faster training means more experiments, better hyperparameter search, and the ability to iterate on model architecture without burning through your GPU budget.

This guide covers the highest-impact [techniques](/articles/data-augmentation-techniques-pytorch) for speeding up PyTorch training, ranked roughly by effort-to-payoff ratio. Most of these are drop-in changes that take minutes to implement but can cut training time by 2-5x.

## Why Training Speed Matters

GPU time is expensive — whether you're paying cloud providers by the hour or sharing a limited on-prem cluster with your team. But the bigger cost is often invisible: slow training means fewer experiments, which means slower model improvement.

The common bottlenecks break down into three categories: data loading (your GPU starves waiting for batches), compute (the actual forward/backward pass), and I/O (checkpointing, logging, and evaluation). Most training runs are bottlenecked by the first two, and the fixes are surprisingly straightforward.

<Callout type="tip">
Before optimizing anything, profile your training loop. Use `torch.profiler` to identify whether you're compute-bound or data-bound. Optimizing the wrong bottleneck wastes effort.
</Callout>

## Mixed Precision Training

[Mixed precision](/articles/mixed-precision-training-pytorch) (AMP — Automatic Mixed Precision) is the single highest-ROI optimization for most training workloads. It uses FP16 for most operations while keeping FP32 for operations that need numerical stability, typically cutting memory usage by ~30-40% and speeding up training by 1.5-2x on modern GPUs.

```python
from torch.cuda.amp import autocast, GradScaler

scaler = GradScaler()

for inputs, targets in dataloader:
    inputs, targets = inputs.cuda(), targets.cuda()
    
    with autocast():
        outputs = model(inputs)
        loss = criterion(outputs, targets)
    
    scaler.scale(loss).backward()
    scaler.step(optimizer)
    scaler.update()
    optimizer.zero_grad()
```

The `GradScaler` handles loss scaling to prevent FP16 underflow in gradients. If you're on Ampere or newer GPUs (A100, RTX 30xx+), also consider BF16 — it has the same speed benefits as FP16 but doesn't need a GradScaler because it has the same exponent range as FP32.

## Optimizing the DataLoader

If your GPU utilization is below 80-90% during training, you're likely data-bound. The DataLoader is often the culprit.

```python
DataLoader(
    dataset,
    batch_size=256,
    num_workers=8,      # typically 2-4x your GPU count
    pin_memory=True,    # speeds up CPU→GPU transfer
    prefetch_factor=4,  # prefetch next batches
    persistent_workers=True,  # avoid worker spin-up cost
)
```

- `num_workers`: Start with 4-8 and tune. Too many workers can cause memory issues and context-switching overhead.
- `pin_memory`: Essential for GPU training — enables faster CUDA transfers.
- `persistent_workers`: Avoids the cost of re-spawning workers each epoch.
- Custom collate functions: If you're doing complex preprocessing in collate, consider moving it to the dataset or using vectorized operations.

## Gradient Accumulation and Checkpointing

When you need larger effective batch sizes but GPU memory is the constraint, gradient accumulation simulates larger batches by accumulating gradients across multiple forward passes before stepping.

```python
accumulation_steps = 4
for i, (inputs, targets) in enumerate(dataloader):
    with autocast():
        outputs = model(inputs)
        loss = criterion(outputs, targets) / accumulation_steps
    
    scaler.scale(loss).backward()
    
    if (i + 1) % accumulation_steps == 0:
        scaler.step(optimizer)
        scaler.update()
        optimizer.zero_grad()
```

Gradient checkpointing (`torch.utils.checkpoint`) trades compute for memory by recomputing intermediate activations during the backward pass instead of storing them. This roughly doubles backward pass time but can reduce memory usage by 60%+, enabling larger batch sizes or models.

## Distributed Training Essentials

When a single GPU isn't enough, distributed training is the next step. The two main options:

- **DDP (DistributedDataParallel)**: The default for multi-GPU training. Replicates the model on each GPU and synchronizes gradients. Simple to set up with `torchrun`.
- **FSDP (Fully Sharded Data Parallel)**: Shards model parameters, gradients, and optimizer state across GPUs. Use when the model doesn't fit on a single GPU.

Common pitfalls: uneven batch sizes across GPUs cause synchronization stalls, and forgetting to set the random seed leads to all GPUs doing identical work.

<Note>
A quick check: if `nvidia-smi` shows all GPUs at similar utilization during DDP training, you're fine. If one GPU is idle while others are at 100%, you have a synchronization issue.
</Note>
