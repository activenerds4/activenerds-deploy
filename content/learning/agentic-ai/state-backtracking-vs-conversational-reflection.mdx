## Question
How does explicit state backtracking (e.g., Tree-of-Thoughts or graph rewind) differ from simple conversational reflection when an agent hits an execution dead-end during a complex multi-file codebase refactor?


## Quick Answer
Conversational reflection keeps the transcript moving forward and just asks the model to critique its own last step before continuing, while explicit backtracking (Tree-of-Thoughts, graph rewind) actually restores execution to an earlier checkpoint and branches from it — for a multi-file refactor, reflection can't undo files that were already edited, but backtracking to a pre-edit checkpoint can.

## Detailed Answer
**Conversational reflection** is cheap: after a failed step, you append a prompt like "that didn't work, review what went wrong and propose a better approach" and let the model reason about the mistake within the same, still-growing transcript. The agent's *understanding* changes, but nothing about the actual execution state is undone — any file that was already written, any API call that already fired, is still exactly as it was. This is fine when the failed step had no side effects worth reverting (a failed search query, a bad guess about which function to inspect), because there's nothing to roll back.

**Explicit state backtracking** is a different operation entirely: it restores the agent's actual state — files, variables, the state-graph's checkpoint — to what it was at an earlier point, then resumes from there down a *different* branch, effectively pretending the dead-end path never happened. Tree-of-Thoughts-style search formalizes this by exploring multiple candidate branches from a checkpoint and pruning the ones that don't pan out; graph-based rewind does the same thing more directly by loading an earlier persisted checkpoint (see how checkpointers enable this) and continuing execution from it with a revised plan.

The distinction matters concretely in a multi-file refactor: if step 4 of a 10-step refactor makes an edit that turns out to conflict with step 7's requirements, conversational reflection can get the model to *notice* and *describe* the conflict, but the file on disk from step 4 is still edited — the model has to manually reason its way through un-doing it via more edits, which is error-prone and burns tokens. Backtracking to the checkpoint saved right before step 4 and branching from there with a corrected plan restores the actual file state cleanly, because the checkpoint captured the real state, not just a description of it.

| Approach | What changes | Undoes side effects? | Best for |
|----------|---------------|----------------------|----------|
| Conversational reflection | The model's reasoning, forward only | No | Failed steps with no side effects (bad query, wrong guess) |
| Explicit state backtracking | Actual execution state, via checkpoint restore | Yes | Steps that already mutated files, data, or external systems |

<Callout variant="tip" title="Key Takeaways">
Reflection fixes what the agent *thinks*; backtracking fixes what the agent already *did* — a refactor with real side effects needs the latter, not just a better prompt.
</Callout>
