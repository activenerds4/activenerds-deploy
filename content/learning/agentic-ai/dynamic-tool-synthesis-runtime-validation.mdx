## Question
How can an agent dynamically generate, compile, and execute new tools at runtime to solve unexpected tasks, and how do you ensure these dynamically created tools are safely validated before execution?


## Quick Answer
An agent generates a new tool as source code, compiles or interprets it in an isolated sandbox, and only registers it for use once it passes both static checks (does it parse, does it avoid disallowed operations) and behavioral checks (does it do what it claims on test inputs) — a dynamically synthesized tool never gets the same trust level as a pre-vetted one without going through that gate first.

## Detailed Answer
Dynamic tool synthesis lets an agent handle a task it has no pre-built tool for by writing one: it generates source code for a function matching some need (parse a novel file format, call an undocumented API pattern), and the runtime compiles or interprets that code and exposes it as a callable tool for the rest of the run, sometimes even for future runs if the tool proves useful. This is powerful precisely because it removes the constraint that an agent can only do what its tool library was pre-built to support — but it also means the agent is now generating code that's about to be *executed*, which is a materially different risk profile than generating code that's merely shown to a human for review.

Safety here has to happen in layers, none of which is the model's own judgment. First, the generated code runs in a **sandbox** with hard resource limits (CPU, memory, execution time) and no ambient access to the filesystem, network, or credentials beyond an explicit allow-list scoped to exactly what the task needs — the same principle as pre-execution guardrails on ordinary tool calls, applied to code that didn't exist a moment ago. Second, **static analysis** runs before anything executes: does the code parse cleanly, does it avoid disallowed imports or syscalls (no arbitrary shell execution, no unrestricted file I/O), does it stay within complexity bounds that suggest it isn't doing something wildly outside its stated purpose. Third, **behavioral validation** runs the new tool against test inputs — ideally including adversarial or edge-case inputs — in the same sandbox, checking that its actual output matches what it claims to do, before it's ever registered as callable with real arguments from the agent's live task.

Only after clearing all three gates should the tool be promoted to something the agent can actually invoke — and even then, it's reasonable to keep dynamically synthesized tools on a stricter runtime leash (tighter resource limits, more logging, shorter validity window before re-validation) than tools that were reviewed and shipped by a human ahead of time.

## Production Implications
- Sandbox execution is non-negotiable — never `exec()` or run generated code with the same permissions as the orchestrator process
- Cap what a dynamically synthesized tool can import or call at the interpreter/runtime level, not just via a prompt instruction the generated code could ignore
- Re-validate a synthesized tool if it's reused across runs — code that was safe against yesterday's test inputs isn't automatically safe forever, especially if its usage context changes
- Log the full generation-to-validation pipeline for every synthesized tool, since this is the highest-risk surface in the whole agent architecture and needs the deepest audit trail

```python
# Illustrative sandboxed validation gate
def register_dynamic_tool(source_code: str, test_cases: list):
    static_check(source_code)                 # disallowed imports/syscalls
    compiled = sandbox_compile(source_code)    # isolated, resource-limited
    for case in test_cases:
        result = sandbox_run(compiled, case.input, timeout=2)
        if not case.matches(result):
            raise ToolValidationError(case)
    return register(compiled, trust_level="synthesized")
```

<Callout variant="tip" title="Key Takeaways">
Generated code that's about to be executed needs the same — or stricter — validation as any other untrusted code path; the fact that an LLM wrote it is not a reason to skip sandboxing and pre-execution checks.
</Callout>
