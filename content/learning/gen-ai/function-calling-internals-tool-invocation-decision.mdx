## Question
Under the hood, how does a model "decide" to emit a function call rather than natural language, and what failure modes emerge in production when the tool schema is ambiguous, overly nested, or when two tools have overlapping semantic purpose?


## Quick Answer
There's no separate decision mechanism — tool schemas are serialized as text into the model's context, and the model has been fine-tuned to emit a structured call format (often a special token boundary plus JSON) when the conversation pattern statistically resembles one it learned to associate with tool use.

## Detailed Answer
When you register tools with an API call, the framework converts each tool's name, description, and JSON schema into a text block that gets injected into the model's context — either as a system-prompt-adjacent section or a dedicated tool-definition segment, depending on the provider's chat template. The model was **fine-tuned on examples** where, given a user request plus a set of available tool definitions, the correct continuation was a structured function call rather than prose. At inference time, it's doing the same thing it always does: predicting the most likely next tokens given everything in context — it just so happens that "everything in context" now includes tool schemas, and the training data taught it what a matching request looks like.

This means **tool selection is pattern matching against schema text**, not semantic reasoning about tool capability. Three concrete failure modes fall out of this:

- **Ambiguous schemas** — two tools whose descriptions overlap (e.g., `search_orders` and `get_order_status`) get confused because the model is matching surface-level textual similarity between the user's request and the tool description, not a deeper understanding of which is more precise.
- **Overly nested parameters** — deeply nested JSON schemas increase the chance the model emits a structurally invalid call (wrong nesting level, missing required field) because it has to track more structural state purely through next-token prediction, with no schema validator in the loop until after generation.
- **Too many tools in context** — every additional tool definition consumes context budget and adds candidate patterns the model must discriminate between, degrading selection accuracy well before you hit any token limit.

<Callout variant="tip" title="Key Takeaways">
Treat tool schemas as prompt engineering, not API configuration — clear, non-overlapping descriptions and flat parameter structures reduce misfires more reliably than model upgrades do.
</Callout>
