## Question
Why do production vector databases rely on approximate nearest neighbor (ANN) algorithms like HNSW or IVF instead of exact k-NN search, and what specific trade-off between recall, latency, and memory footprint are you tuning when you adjust an HNSW graph's `ef_construction` and `M` parameters?


## Quick Answer
Exact k-NN has to compare a query vector against every vector in the index, which is too slow at production scale — ANN algorithms like HNSW and IVF accept a small, tunable amount of missed matches in exchange for query times that don't grow linearly with index size.

## Detailed Answer
Exact nearest-neighbor search is a brute-force comparison: compute distance from the query to all *n* vectors, sort, take the top-k. That's `O(n)` per query, and it doesn't get better with clever data structures the way exact search does for low-dimensional data — in the high-dimensional spaces embeddings live in, there's no exact index structure that reliably beats brute force at scale. Once an index holds millions of vectors, exact search at meaningful query volume becomes prohibitively slow, so production systems trade a small amount of accuracy for sublinear query time using an ANN algorithm.

**HNSW (Hierarchical Navigable Small World)** builds a multi-layer graph over the vectors: the top layer has few nodes and long-range links for fast coarse navigation, and each layer down adds more nodes and shorter, denser links, until the bottom layer contains every vector. A query walks the graph greedily from the top layer down, following whichever neighbor is closest to the query at each step, refining as it descends — this gets query time down to roughly logarithmic in index size instead of linear.

Two parameters set at index-build time control the shape (and therefore the quality) of that graph:

| Parameter | Controls | Trade-off when increased |
|-----------|----------|----------------------------|
| `M` | Max number of edges (neighbors) each node keeps per layer | Higher recall and more robust graph connectivity, at the cost of more memory per vector and slower graph construction |
| `ef_construction` | Size of the candidate list explored while inserting each node during index build | Higher-quality graph (better recall at query time), at the cost of significantly slower index build |
| `ef_search` (query-time) | Size of the candidate list explored while answering a query | Higher recall per query, at the cost of higher query latency |

In practice: `M` and `ef_construction` are a **one-time cost** paid once at build time in exchange for a permanently better-connected graph — worth paying generously if the index doesn't need frequent full rebuilds. `ef_search` is a **per-query knob** and is usually where teams tune the live recall/latency trade-off, since it can be adjusted without rebuilding the index at all.

**IVF (Inverted File Index)** takes a different approach: it clusters the vector space (via k-means) into `nlist` partitions, and a query only searches the `nprobe` clusters nearest to it rather than the whole index — same fundamental trade (recall vs. latency), controlled by `nprobe` instead of `ef_search`, with the additional cost that clustering quality depends on how well the data matches the assumptions of the clustering step.

<Callout variant="tip" title="Key Takeaways">
Every ANN tuning knob is the same trade in different clothing — more graph density or candidate exploration buys recall at the cost of memory and latency, so tune `ef_search`/`nprobe` against your actual recall requirement rather than defaulting to the highest setting.
</Callout>
