## Question
A junior engineer says "a container is just a lightweight VM." Explain precisely why this analogy is wrong, and describe what a container actually *is* at the process level on the host.


## Quick Answer
A container isn't a small virtual machine — it's an ordinary Linux process that the kernel isolates using **namespaces** (controlling what it can see) and **cgroups** (controlling what resources it can use), running directly on the host kernel with no hypervisor or guest OS involved.


## Detailed Answer
A VM virtualizes hardware: a hypervisor boots an entire separate kernel and OS inside an isolated virtual machine, which is why VMs take tens of seconds to boot and carry real memory/disk overhead just for that second OS. A container does none of this — **it is a process (or process tree) on the host, running the exact same host kernel as everything else**, just with a restricted view of the system. Linux namespaces (PID, NET, MNT, UTS, IPC, USER) give that process its own illusion of having its own process tree, network stack, filesystem mounts, and hostname, while cgroups cap how much CPU, memory, and I/O it's allowed to consume. Because there's no second kernel to boot, containers start in milliseconds, not seconds, and because they share the host kernel, a kernel-level vulnerability or a shared kernel resource exhaustion issue can, in principle, affect every container on that host — an isolation boundary a VM's separate kernel doesn't have.


<Callout variant="tip" title="Key Takeaways">
"Lightweight VM" hides the one fact that matters most operationally — containers share your host's kernel, so kernel-level security and resource isolation is a real concern that a true VM boundary wouldn't have.
</Callout>
