## Question
Two engineers build the same application — one from `ubuntu:latest`, another from `alpine`. Beyond image size, what practical engineering trade-offs should inform this base image decision?


## Quick Answer
Alpine's small size comes from **musl libc** and **BusyBox** instead of glibc and GNU coreutils — which can break precompiled binaries, native language modules, and familiar debugging tools that Ubuntu's glibc-based environment handles without a second thought.

## Detailed Answer
Image size is the trade-off everyone notices first, but it's rarely the one that costs the most engineering time. The deeper difference is that Alpine and Ubuntu aren't the same operating system with different sizes — they're built on different core libraries entirely.

Ubuntu uses **glibc**, the GNU C library that almost every prebuilt Linux binary on the internet was compiled and tested against. Alpine uses **musl libc**, a smaller, stricter, spec-conformant reimplementation that is *not* binary-compatible with glibc. This matters the moment a project pulls in anything precompiled: a Python wheel with a compiled C extension, a Node.js native addon, a downloaded vendor binary — many of these link against glibc and either fail to run on Alpine or silently misbehave (subtle differences in DNS resolution and locale handling are common culprits, since musl's implementations diverge from glibc's in those areas specifically).

| Factor | `alpine` | `ubuntu:latest` |
|--------|----------|------------------|
| C library | musl libc | glibc |
| Base image size | ~5 MB | ~75 MB |
| Precompiled binary compatibility | Often breaks (needs musl-built or static binaries) | Broad compatibility, "just works" |
| Package manager / ecosystem | `apk`, smaller repo, faster installs | `apt`, largest package ecosystem |
| Debugging tools available by default | Minimal (BusyBox utilities) | Full GNU coreutils, more familiar |
| CVE/security patch cadence | Small footprint = smaller attack surface, but slower community CVE tracking historically | Large, well-tracked CVE database, frequent patches |

The practical decision usually comes down to what the application actually needs. A statically-linked Go binary with no C dependencies runs beautifully on Alpine and gets a genuinely tiny image. A Python or Node application with several native-extension dependencies often loses more engineering time chasing musl-specific build failures and debugging tool gaps than it saves in registry storage or pull time — in which case a slim glibc-based image (`ubuntu`, or a `-slim` variant) is usually the better trade, or building against Alpine's own toolchain (`apk add --virtual .build-deps`) deliberately to get compatible binaries.

<Callout variant="tip" title="Key Takeaways">
Choose Alpine when your dependency chain is musl-compatible (statically linked binaries, pure-language packages); choose glibc-based images when you depend on precompiled binaries or native extensions, since the size savings aren't worth chasing compatibility bugs.
</Callout>
